# Nexus Logging Standards & Guidelines

This document establishes the project-wide logging standards for the **Nexus** platform. All developers and AI assistants must strictly follow these rules to ensure consistency, security, and production observability.

---

## 1. Structured Logging Vocabulary

Every log message emitting structured key-value pairs (via SLF4J 2.0+ fluent API) must use this exact vocabulary. In production, these fields are parsed natively into JSON keys by the Spring Boot ECS console formatter.

| Field Name | Description | Accepted / Example Values |
| :--- | :--- | :--- |
| `event` | The high-level category of the execution boundary | `api_request`, `integration_call`, `event_processing`, `scheduled_job` |
| `executionType` | The runtime execution environment | `http`, `async`, `schedule`, `event` |
| `operation` | The specific logical action or endpoint | `POST /api/v1/auth/login`, `sendVerificationEmail`, `AuthEventRetryBuffer.drain` |
| `correlationId` | Unique request tracking identifier | `123e4567-e89b-12d3-a456-426614174000` |
| `durationMs` | Operation execution duration in milliseconds | `45` (integer) |
| `outcome` | General result of the operation | `SUCCESS`, `FAILURE` |
| `statusCode` | HTTP response status code (HTTP execution only) | `200`, `400`, `500` |
| `errorCode` | Stable machine-readable error code if any | `AUTH_001`, `VALIDATION_FAILED`, `INTERNAL_ERROR` |

---

## 2. Correlation ID vs. Trace ID Terminology

* **`correlationId`**: Unique request-scoped correlation identifier generated by `CorrelationIdFilter` or propagated from callers (`X-Correlation-Id` header). Stored in MDC.
* **`traceId` (MDC alias)**: A deprecated alias for `correlationId` kept for backward compatibility with existing log patterns and client responses.
* **Intended Migration Path**:
  * **Current**: Map both `correlationId` and legacy `traceId` in MDC.
  * **Future**: Remove `traceId` alias and use `correlationId` only.
  * **Distributed Tracing**: If OpenTelemetry/Micrometer Tracing is introduced, reserve `traceId` and `spanId` exclusively for distributed tracing spans.

## 3. Boundary & Exception Logging Ownership

To prevent duplicate log statements and double stack traces in logs, we establish clear exception ownership rules:

```
+-----------------------------------------------------------------------------------+
|                                  HTTP Boundary                                    |
|                                                                                   |
|  +---------------------------+              +----------------------------------+  |
|  |  ApiRequestLoggingFilter  |              |      GlobalExceptionHandler      |  |
|  |  (Logs: HTTP completion,  |              |  (Logs: Stack trace only on 5xx; |  |
|  |   duration, and outcome)  |              |   Logs single-line on 4xx/WARN)  |  |
|  +---------------------------+              +----------------------------------+  |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                               Services & Repositories                             |
|                                                                                   |
|            (Propagate exceptions directly; do NOT log stack traces)               |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                        Jobs, Events, & Integration Boundaries                      |
|                                                                                   |
|  +---------------------------+              +----------------------------------+  |
|  |     ExecutionObserver     |              |      Async/Scheduled Terminal    |  |
|  |  (Logs: status, duration,  |              |  (Must log unexpected stack trace|  |
|  |   outcome, no stack trace)|              |   if no handler is above it)     |  |
|  +---------------------------+              +----------------------------------+  |
+-----------------------------------------------------------------------------------+
```

### 3.1 HTTP Request Boundary
1. **`ApiRequestLoggingFilter`**: Owns logging request-summary logs. It emits exactly one `api_request` log per HTTP request containing HTTP status, duration, and outcome. **It never logs exception stack traces.**
2. **`GlobalExceptionHandler`**: Owns HTTP exception details and stack traces.
   * **Unexpected System Errors (5xx)**: Logged at `ERROR` level with the full stack trace.
   * **Security/Operational Failures (401, 403, 429)**: Logged at `WARN` level without a stack trace.
   * **Validation & Domain Errors (400, 404, 409, 410)**: Logged at `DEBUG` level without a stack trace (or ignored if noise is a concern).
3. **Services & Repositories**: Must propagate exceptions. They must *never* log exceptions they do not handle or recover from.

### 3.2 Async, Scheduled, and Event Boundaries
1. **`ExecutionObserver`**: Centralized component used to wrap integration calls, events, and background jobs. It records success/failure outcomes and execution metrics. It never logs stack traces.
2. **Terminal Async/Scheduled Boundaries**: If an exception escapes the execution thread (e.g. from an event listener or scheduled task) and no global handler is above it, the terminal boundary or wrapper must log the unexpected failure with the full stack trace to ensure diagnostic details are not lost.
3. **Sensitive Exception Messages**: Exception messages may contain sensitive or raw database details. Log only `errorType` and stable `errorCode` by default. Do not print `exception.getMessage()` in logs unless the message is explicitly sanitized or verified to be safe.

---

## 4. MDC Propagation & Restoring

To prevent context leakage between pooled threads:
1. Capture the MDC parent context map.
2. Set it on the execution thread.
3. Execute the task.
4. **Restore the thread's original MDC state in a `finally` block.**
5. All custom and framework executors must be customized using `MdcTaskDecorator` to apply this pattern.

---

## 5. Metric Cardinality Rules

* **Never use unbounded values** (such as emails, user IDs, tenant IDs, correlation/trace IDs, exception messages, raw URLs, or database keys) as Micrometer/Prometheus metric tags.
* Ensure all metric tags (e.g. `event`, `operation`, `outcome`) come only from bounded, controlled, static values to prevent Prometheus memory exhaustion.

---

## 6. Examples & Anti-patterns

### 6.1 Correct Structured API Log
```java
log.atInfo()
   .addKeyValue("event", "api_request")
   .addKeyValue("executionType", "http")
   .addKeyValue("operation", "POST /api/v1/auth/register")
   .addKeyValue("correlationId", correlationId)
   .addKeyValue("durationMs", durationMs)
   .addKeyValue("statusCode", 201)
   .addKeyValue("outcome", "SUCCESS")
   .log("API Request Completed: method=POST path=/api/v1/auth/register status=201 durationMs={} outcome=SUCCESS", durationMs);
```

### 6.2 Correct Execution Observer Usage
```java
executionObserver.observe(
    "integration_call",
    "smtp",
    "sendVerificationEmail",
    true, // Log success at INFO
    () -> {
      mailSender.send(msg);
      return null;
    }
);
```

### 6.3 Anti-patterns
```java
// Anti-pattern 1: Duplicate Exception logging in Service
try {
  userRepository.save(user);
} catch (Exception e) {
  log.error("Failed to save user", e); // WRONG: Logs duplicate stack trace
  throw new DomainException("DB_ERR", "Save failed", e);
}

// Anti-pattern 2: String concatenation
log.info("Request path: " + path + " completed in " + duration + "ms"); // WRONG: Use parameterized or key-value logging

// Anti-pattern 3: Dynamic high-cardinality metric tag
Timer.builder("nexus.exec").tag("email", userEmail).register(registry); // WRONG: Metric cardinality explosion!
```
