## 2. Prioritized findings

Severity reflects impact on the requirements the story actually states. Overlapping findings from the three analysis passes are merged into one entry.

### P0: correctness or security defects in shipped stories (fix first)

#### P0-1. Frontend silent refresh deadlocks and leaves the tab without a working refresh (US-004, US-003) — Critical [R][V]
- **Files:**
  - `F/features/auth/auth.service.ts:172-196`: `refresh()` → `fetchMe()` → `GET /v1/users/me`.
  - `F/core/http/auth.interceptor.ts:22`: `AUTH_PATHS` contains only login, refresh and logout.
  - `F/core/http/auth.interceptor.ts:100-120`: the proactive branch.
- **Defect:**
  - The new session is stored only after `/users/me` returns.
  - `/users/me` is not an auth path, and the store still holds the old, nearly expired session. So the interceptor's proactive branch makes `/users/me` wait on `refreshInFlight`.
  - `refreshInFlight` is the very refresh that is waiting for `/users/me`. It is a circular wait with no timeout.
  - `finalize` never runs, so `refreshInFlight` stays non-null for the life of the tab. No later refresh is ever issued.
- **When it triggers:** any API call in the last 2 minutes of a token's life, which means every active session after about 13 minutes. Also any reactive 401, and any cold-start `authGuard` on an expired in-memory session.
- **Why tests miss it:**
  - Unit specs mock `AuthService`.
  - The e2e test `e2e/auth/session-refresh.spec.ts:76-84` only asserts `refreshCallCount >= 1`.
- **Fix (system design, not DSA):**
  - Make the refresh single-flight and owned by `AuthService`, shared by the guard and the interceptor.
  - Exempt the inner `/users/me` call with an `HttpContextToken`. Better: return the user and permission payload from `/login` and `/refresh` directly. That removes a round trip and the re-entrancy.
  - Add `timeout()` to the shared observable.

#### P0-2. Refresh-token rotation is not atomic, and revocation does not fence an in-flight rotation (US-004, US-005, US-007) — High [V]
- **Files:**
  - `B/identity/application/service/RefreshTokenUseCase.java:131-138`: `token.revoke(now); refreshTokenPort.save(token)` inside `try/catch (OptimisticLockingFailureException)`.
  - `B/identity/infrastructure/persistence/JpaRefreshTokenAdapter.java:30`: plain `repo.save`.
  - `B/identity/infrastructure/persistence/JpaRefreshTokenRepository.java:22-29`: bulk `UPDATE … SET revokedAt` that does **not** bump `version`.
- **Defects:**
  1. **The catch block is dead code.** The entity is already managed, so `save()` does not flush. The versioned UPDATE runs when the `@Transactional` proxy commits, outside the try.
     - The losing concurrent request gets a **500**, not 401 `AUTH_004`.
     - It has also already committed a `TOKEN_REFRESH_SUCCESS` audit row (`REQUIRES_NEW`).
     - `VerifyEmailUseCase.java:85` and `ResetPasswordUseCase.java:139` already do this correctly with an explicit `flush()`.
  2. **Revocation does not stop an in-flight rotation.** Logout, password reset and theft-detection revocation are bulk updates that leave `version` unchanged. A rotation that read the row before the revoke still matches `WHERE version=?` and inserts a new active token.
     - Result: a stolen-token session survives a password reset or theft revocation.
  3. **No grace window.** US-004 AC-3 requires one ("≤10 s"). Two tabs, or a browser session-restore, refreshing near-simultaneously trigger reuse detection. That revokes the whole family and logs every tab out.
- **Fix:**
  - Replace read-modify-write with one conditional statement: `UPDATE refresh_tokens SET revoked_at=?, version=version+1 WHERE id=? AND revoked_at IS NULL`. If 0 rows change, return `AUTH_004`. Insert the successor only after that.
  - This one change closes defects 1 and 2, because the predicate re-checks exactly the state that revocation changes. It is the same pattern RBAC revoke already uses well.
  - For defect 3, store `replaced_by` / `rotated_at`. When the immediately previous token is presented within N seconds, return a non-revoking "already rotated" response.
  - On the client, serialize refresh across tabs with `navigator.locks` plus `BroadcastChannel`.
- **Tests that hide this:** `T/identity/application/service/RefreshTokenRotationIT.java:207-214` counts *any* exception as a pass.

#### P0-3. Connection-pool starvation: virtual threads + default pool of 10 + nested `REQUIRES_NEW` + Argon2/Redis inside transactions (US-003, US-004, US-006, US-007, US-008, US-010) — High [V][T]
- **Files:**
  - `R/application.yml:17-25`: virtual threads on; no `hikari` settings, so the pool is 10 with a 30 s wait.
  - Class-level `@Transactional` on `LoginUseCase.java:53`, `RefreshTokenUseCase.java:47`, `RegisterUserUseCase.java:41`, `ResetPasswordUseCase.java:35`.
  - Argon2 (19 MiB, t=2) runs inside those transactions.
  - `B/identity/application/service/SecureEventService.java:52,74,95,130,148`: `REQUIRES_NEW` asks for a second connection while the first is still held.
  - Token minting calls Redis (up to about 4 s of timeouts) inside the login transaction (`JwtRs256Service.java:106-110` → `RoleResolutionService.java:59,66`).
- **Why it matters:**
  - Virtual threads remove the old implicit concurrency cap. At 10 or more concurrent logins, every connection is held by an outer transaction waiting for an inner one, so everything stalls for 30 s and then fails.
  - ADR 0009 states its own precondition, "pool ≥ 2 × max concurrent login threads". With virtual threads there is no maximum, so that precondition cannot hold.
  - The repo already shows the problem: `AuthEventLoadIT` runs with a test-only pool of 400 because 140 was exhausted.
  - The EPIC-001 NFRs (login 100 RPS, refresh 200 RPS) cannot be met with the shipped configuration.
- **Fix:**
  - Hash and verify, and resolve permissions or touch the cache, **outside** the transaction. Wrap only the DB work in a `TransactionTemplate`.
  - Write success-path audit rows in the outer transaction. Only failure-path events need `REQUIRES_NEW`.
  - Bound Argon2 with a `Semaphore` sized to CPU cores. Today the pool is accidentally the only bound on Argon2 CPU and memory.
  - Set `maximum-pool-size` and a `connection-timeout` of 2–5 s explicitly.
  - Map pool timeouts to 503 + `Retry-After` instead of the generic 500 (`GlobalExceptionHandler.java:191`).

#### P0-4. Lockout counter loses updates and leaks account existence; lockout semantics deviate from the AC (US-006) — High [V]
- **Files:**
  - `B/identity/application/service/SecureEventService.java:95-122`: `findById → recordFailedAttempt() → save()`, with a catch for `ObjectOptimisticLockingFailureException`.
  - `B/identity/domain/AuthConstants.java:21`: `LOCKOUT_WINDOW_SECONDS` is declared but never referenced.
- **Defects:**
  - **The catch block is dead code**, for the same reason as P0-2: the flush happens at the `REQUIRES_NEW` commit.
    - Concurrent bad-password requests against an **existing** account return 500. Unknown emails always return a clean 401.
    - That difference is an account-existence oracle, which defeats the dummy-hash anti-enumeration work.
  - **Increments are lost under concurrency.** With K parallel requests per wave, only about one increment per wave commits, so an attacker gets about 5×K guesses before lockout, not 5.
  - **No 15-minute decay.** Five failures spread over weeks still lock the account. The AC says "5 consecutive within 15 min".
  - **Re-lock after expiry.** After a lock expires, a single typo immediately locks the account again: the DB row is still `LOCKED` with count 5, so it increments to 6.
- **Fix (classic atomic-counter pattern, which ADR 0009 already lists as an option):**
  - Use one statement: `UPDATE users SET failed_attempt_count = IF(last_failed_at < now − window OR status_lock_expired, 1, failed_attempt_count + 1), last_failed_at = now, status/locked_until = IF(count+1 ≥ 5, …) WHERE id = ?`, then read the count back.
  - Wrap the transactional call itself so the "never 500" contract holds.
- **Tests that hide this:** `T/identity/application/service/SecureEventServiceConcurrencyTest.java:29-37` is mock-only, and its comment ("1–2 extra attempts") is wrong.

#### P0-5. Rate limiting: eviction bug, per-instance state in prod, and load-balancer address collapse (US-006, US-007, US-018) — High [V]
- **Eviction bug [V]:**
  - `B/identity/infrastructure/security/InMemoryRateLimitStore.java:47-62,103-110` builds the eviction sweep from `ip-window-seconds` (60) and applies it to **every** key.
  - The `USER:` and `FORGOT_USER:` buckets use `user-window-seconds: 900` (`R/application.yml:200-202`).
  - So the per-account limit of 5 per 15 min is really 5 per 1–2 min: 7–15× weaker against distributed-IP brute force.
  - **Fix:** keep each key's window with its deque, or let the sweep remove only empty deques. `tryConsume` already prunes when a key is accessed.
- **Per-instance in prod [V]:**
  - `store-type: memory` is the base default (`R/application.yml:198`), and `application-prod.yml` does not override it. ADR 0019 D3 says prod must use Redis.
  - With N replicas every limit is multiplied by N.
  - `docker-compose.yml` does not set `REDIS_HOST` for the backend, so in the `full` profile the cache and rate-limit Redis calls fail silently.
  - `RateLimitRoleChangeThrottleAdapter` keeps `throttledUntil` per JVM.
- **Behind a load balancer:**
  - The IP key is `request.getRemoteAddr()` (`LoginRateLimitFilter.java:112`). Behind a load balancer every client shares one bucket.
  - **Fix:** use `ForwardedHeaderFilter` / `RemoteIpValve` with a trusted-proxy CIDR allow-list.
- **Ordering and memory (DSA):**
  - The filter parses the body, computes the HMAC and creates a `USER:` key **before** it knows whether the IP is already over its limit (`LoginRateLimitFilter.java:138-148`).
  - A throttled IP sending random emails therefore grows the map at the raw request rate (about 250–300 B per key).
  - **Fix:**
    - Check the cheap IP bucket first.
    - Bound the map (Caffeine `maximumSize` + `expireAfter`).
    - Pre-size the deque to `maxAttempts`.
  - The per-user bucket also counts successful logins, so 5 legitimate logins from several devices return 429. Count only failures in that bucket.
- **Appropriate as built:** the sliding-window **log** is the right algorithm for limits of 5–30. A token bucket would not be materially better here.

#### P0-6. Last-admin protection can be bypassed: predicate drift and write skew (US-017, US-018, US-015) — High [V][T]
- **Predicate drift [V]:**
  - The lockout and the zero-admin health indicator count as an administrator anyone holding `TENANT_ADMIN`, or any role carrying **all three** of `role:write`, `user:write`, `tenant:write` (`B/rbac/domain/RbacDangerousPermissions.java:14`; `RoleAssignmentService.java:566-568,724-728`).
  - Since US-018 M2, assigning or revoking a role also requires `user:role:assign` (`RoleAssignmentService.java:1092-1118`).
  - `V6` deliberately backfills that permission only onto roles holding the full pre-V6 catalogue.
  - **Failure scenario:**
    1. Admin A holds `TENANT_ADMIN`. User B holds custom role R, which has only the three dangerous permissions.
    2. A revokes their own `TENANT_ADMIN`. The lockout check counts B, so the revoke passes.
    3. B cannot assign roles, and the A3 rule stops B from attaching `user:role:assign`. The tenant can no longer administer roles.
    4. The health indicator stays UP. Break-glass (ADR 0025) is not implemented.
- **Write skew [T]:**
  - Revoke classifies roles from a plain snapshot read (M10) taken *before* its `FOR UPDATE` lock (M11).
  - A concurrent detach of `tenant:write` from R commits in between.
  - The revoke still counts B, and both transactions commit, leaving zero qualifying admins.
  - ADR-0021 records this race (RES-28) only for after M3, but it is reachable today.
- **Root cause:** four different definitions of "administrator" are in use:

  | Definition | Location |
  |---|---|
  | ANY dangerous permission | `RbacAdminEquivalence.isAdminEquivalent` |
  | ALL three dangerous permissions | `isFullyAdminEquivalent` |
  | The whole catalogue | `RbacAdministrators.isAdminDefining` |
  | The literal role name | `RoleManagementService.java:390-417` |
- **Fix:**
  - **Interim:** add "and holds `user:role:assign`", by permission id, to the lockout and health predicates. This only makes them stricter.
  - **Structural:**
    - Ship M3 (one definition: holds the whole catalogue).
    - Take one **per-tenant RBAC mutex** as the first statement of every admin-affecting mutation, for example `SELECT … FOR UPDATE` on a `rbac_tenant_lock(tenant_id)` row.
    - The mutex makes every later read consistent, and it also replaces the large lock set in P1-1.

#### P0-7. Permission cache: non-atomic writes can leave entries that never expire (US-010, US-015) — High (low likelihood, unbounded impact) [V]
- **Files:**
  - `B/rbac/infrastructure/cache/RedisPermissionCacheAdapter.java:100-108`: `writeSet` sends `DEL`, `SADD`, `EXPIRE` as three separate commands.
  - `:52-64`: `get` sends 2× `HASKEY` + 2× `SMEMBERS`, also non-atomically.
  - Freshness is fingerprinted on role names only (`RoleResolutionService.java:60`).
  - Detach never evicts; `RoleManagementService` has no cache port.
- **Defects:**
  - If `EXPIRE` fails after `SADD` succeeds, the key never expires. Every later login or refresh then re-mints a permission that has since been detached, until the user's set of role names changes.
  - A concurrent `put` can also be read as new roles paired with old permissions.
  - The "≈30 min worst case" staleness documented for US-015, and planned as UI copy in US-019 D4 and US-020, is therefore wrong.
- **Is the cache worth it?** Resolution only runs at login and refresh, never per request.

  | Path | DB queries | Redis round trips |
  |---|---|---|
  | Cache hit | 1 | 4 |
  | Cache miss | 2 | 10 |
  | No cache | 2 (could be 1 joined query) | 0 |

  The cache adds latency and a consistency hazard and saves almost nothing. This is **over-engineering for the actual access pattern**.
- **Fix:**
  - Preferred: remove the cache (ADR-0022 D9 already contemplates this) and merge the two resolution queries.
  - If it stays: store one serialized value with `SET key value EX ttl` (atomic, one round trip, cannot lose its TTL), outside the DB transaction, with a 100–250 ms timeout.

#### P0-8. Audit "never blocks auth" contract does not hold; failure-path audits are rolled back (US-008, US-002) — High [T]
- **Files:**
  - `B/identity/infrastructure/persistence/JpaAuthEventAdapter.java:52-62`: `try { save } catch (DataAccessException) { retryBuffer.enqueue }`.
  - `VerifyEmailUseCase.java:68-102` and `ResendVerificationUseCase.java:116-132`: `record(...)` then `throw`, inside a class-level `@Transactional`.
- **Defects:**
  - Every caller is inside a transaction, so the INSERT runs at flush or commit, *outside* the try. Privilege drift (ADR 0012), lock-wait timeouts and oversize values all propagate as 500s, or roll back the business transaction.
  - Exceptions that do reach the catch have already marked the transaction rollback-only, so the caller's commit then fails with `UnexpectedRollbackException`.
  - `VERIFICATION_FAILED` and `RESEND_THROTTLED` rows are always rolled back with the exception that follows them. `ResetPasswordUseCase` documents and avoids exactly this trap.
- **Fix:**
  - Make the best-effort write self-contained: `TransactionTemplate(REQUIRES_NEW)` *inside* the adapter, with try/catch around the whole `execute` and `saveAndFlush`, or an autocommit `JdbcTemplate` insert.
  - Keep `recordOrThrow` for the RBAC atomic case (ADR 0024), which is correct.
- **Tests that hide this:** `T/identity/infrastructure/audit/AuditStoreDownIT.java:137-139` stubs `save()` on a spy, which bypasses flush and transaction semantics.

#### P0-9. Access-token revocation was designed but never built, and the planned data structure is the wrong granularity (US-005, US-007) — Medium-High [V]
- **What exists:**
  - ADR 0008 / ADR 0016 D4 adopt a Redis jti denylist. No denylist exists in the code.
  - `token_version` is minted and parsed (`JwtRs256Service.java:125,195`) but **never compared**. Its only consumer is `/users/me`.
  - The US-007 design claims that incrementing it "invalidates future JWTs". Nothing enforces that.
  - So after logout, password reset or theft detection, access tokens stay valid for up to 900 s.
- **DSA point:**
  - A per-jti denylist can only revoke the single token presented at logout. The server never stores issued jtis, so it cannot denylist the user's *other* access tokens.
  - Every revocation in this system is per-user (global logout, reset, family theft).
- **Fix:** use a per-user watermark: `jwt:nbf:{userId}` = epoch seconds, with TTL = access-token TTL.
  - Logout, reset and theft revocation each do one `SET`.
  - Verification does one `GET` and rejects `iat < nbf`.
  - O(1) per request, memory O(users revoked in the last 15 min).
  - The `perm_epoch` claim already validated by US-018 M6 can share the same mechanism.

#### P0-10. Angular reactive refresh and guards: logout on any replay error, a stale auth signal, parallel guards (US-004, US-013) — High/Medium [R][V]
- **Reactive refresh [R][V]:**
  - In `F/core/http/auth.interceptor.ts:146-154`, `catchError` sits **after** `switchMap(next(...))`, so it also catches errors from the replayed request.
  - Any 403, 404, 409 or 500 after a token refresh clears the session, navigates to login, and rethrows a misleading 401.
  - The proactive branch (`:111-119`) orders this correctly.
- **Stale auth signal [R][V]:**
  - `F/core/auth/auth.store.ts:34-37`: `computed(() => … Date.now() < s.expiresAt)`.
  - `Date.now()` is not a signal, so the value is memoized and `isAuthenticated` never turns false on expiry. `authGuard` then admits expired sessions straight into P0-1.
  - **Fix:** use a plain method, or compare `expiresAt` inside the guard.
- **Parallel guards [R]:**
  - Angular evaluates a `canActivate` array **in parallel**, not sequentially as the JSDoc in `F/core/guards/permission.guard.ts:13-25` claims.
  - `[authGuard, permissionGuard]` therefore reads empty permissions before the cold-start refresh finishes, and sends entitled users to `/access-denied` on reload.
  - This is latent today, because no route uses `permissionGuard`. But the documented usage pattern is the broken one, and the contract spec (`permission-guard-contract.spec.ts:46-54`) accepts it.
  - **Fix:** have `permissionGuard` await the shared session-restore observable.
- **Cancellable guard refresh:**
  - `authGuard` refreshes outside the interceptor's single-flight (`auth.guard.ts:27-30`), so its request can be cancelled by navigation after the server has already rotated.
  - The next refresh then presents a revoked token, and the whole family is revoked (P0-2).

### P1: DB design, scalability and smaller correctness gaps

#### P1-1. `user_roles` locking reads lock every past assignment (US-016, US-017) — Medium [T]
- **What exists:**
  - M5, M5b and M11 (`B/rbac/infrastructure/persistence/JpaUserRoleRepository.java:104,125,271`) are locking reads using `FORCE INDEX (fk_user_roles_role)`.
  - Revoked rows are kept forever (soft delete).
  - Under REPEATABLE READ, InnoDB next-key-locks every scanned index record. That includes revoked rows and other users' rows.
- **Cost:** the lock footprint is O(all past and present holders of every role carrying any dangerous permission). `user:write` was narrowed by US-018, so it can now sit in widely held helpdesk roles.
- **Fix:**
  - Either the per-tenant mutex from P0-6 (preferred; it removes this whole protocol),
  - or a composite index `(role_id, revoked_at, user_id)` forced in all three statements, selecting ids only instead of `SELECT *`.
- The same index makes US-019 B6 `memberCount` cheap.

#### P1-2. Denial audit opens a second connection while holding X-locks (US-014, US-016) — Medium [T]
- **What exists:**
  - `recordDenial` (`REQUIRES_NEW`) runs after M11 has taken its locks (`RoleAssignmentService.java:1030`).
  - The denial throttle is check-then-record, so a burst of simultaneous requests all pass the check.
- **Failure scenario:** about 10 concurrent denied revokes (with a pool of 10) deadlock the pool for 30 s, and admin rows stay locked for that time.
- **Fix:** record the denial after rollback (`TransactionSynchronization.afterCompletion`), or enqueue it to the existing retry buffer.

#### P1-3. Token tables grow without bound; the family revoke scans the whole chain (US-001, US-003, US-004) — Medium [V]
- **What exists:**
  - No purge job exists for `refresh_tokens` or `auth_tokens`.
  - Every rotation inserts a row: about 96 per active family per day, or about 370k rows/day at 10k users.
  - `revokeByFamilyId … AND revokedAt IS NULL` is served only by `idx_refresh_tokens_family_id(family_id)` (`V2:51`). Every call examines and locks the whole chain.
- **Fix:**
  - Change that index to `(family_id, revoked_at)`, mirroring the existing `(user_id, revoked_at)` index.
  - **Use the UUIDv7 property:** primary keys are time-ordered, so retention can be a batched `DELETE … WHERE id < uuidv7_floor(now − 14d − grace) LIMIT 5000` on the clustered PK. No new `expires_at` index is needed. This is a real benefit of ADR 0005 that is not yet exploited.
  - For append-only `auth_events` (triggers block `DELETE`), use `PARTITION BY RANGE` on monthly UUIDv7 boundaries and `DROP PARTITION`.

#### P1-4. Over-indexed audit table and an extra SELECT per insert (US-001, US-008) — Low-Medium [T]
- **Unused indexes:**
  - `auth_events` has 3 secondary indexes (`V2:88-90`), but `JpaAuthEventRepository` has no finders. The table with the most writes pays 4 B-tree inserts per row with no reader in the code.
  - `idx_users_tenant_id_status` (`V2:30`) and `idx_auth_tokens_user_id_type_consumed_at` (`V2:71`) are unused as well.
  - **Fix:** defer the `auth_events` indexes until the audit UI or query story arrives. Use the `consumed_at` index for P1-6.
- **Extra SELECT per insert:**
  - `AuthEvent` has an assigned UUID and no `@Version`, so Spring Data's `save()` calls `merge`, which SELECTs before every INSERT.
  - **Fix:** implement `Persistable<UUID>` with `isNew()=true`. Treat a duplicate key on retry-drain as success.

#### P1-5. The common-password denylist never matches anything (US-006 AC-4) — Medium [V]
- **What exists:**
  - `R/security/common-passwords.txt`: the longest entry is **11** characters, and **0** entries are ≥12.
  - `MIN_LENGTH = 12` is checked first (`PasswordPolicyService.java:26,61`), so the `HashSet` lookup can never reject anything.
  - The AC asks for a top-100k list, or the k-anonymity API.
- **DSA, where it genuinely matters:** the structure is correct for 379 entries. A realistic breached-password corpus filtered to ≥12 characters (10⁵–10⁶ entries) would cost about 60–100 MB of heap as `HashSet<String>`. Better options:
  - A **Bloom filter**: about 1.2 MB per 1M entries at 1% false positives. A false positive only means "choose another password", which is acceptable.
  - A sorted `long[]` of 64-bit hashes with binary search: 8 MB, O(log n), exact.
  - The HIBP range API.

#### P1-6. Leftover reset tokens stay valid; verify-email accepts RESET tokens (US-007, US-002) — Medium [T]
- **What exists:**
  - Up to 3 live reset tokens per hour can exist. A successful reset consumes only the token that was presented (`ResetPasswordUseCase.java:138`).
  - `VerifyEmailUseCase.java:66-85` never checks the token type, unlike reset at `:103`.
- **Fix:**
  - On a successful reset: `UPDATE auth_tokens SET consumed_at=? WHERE user_id=? AND type='RESET' AND consumed_at IS NULL`. The existing unused index already covers it.
  - Add a type check to verify.

#### P1-7. Registration: concurrent duplicates return 500, and the endpoints have no rate limit (US-002) — Medium [T]
- **Duplicate race:**
  - Check-then-insert is guarded correctly by `UNIQUE(tenant_id,email_hmac)`.
  - The violation surfaces at commit as `DataIntegrityViolationException` with no handler, so it returns 500. That breaks the uniform response required by AC-4.
  - **Fix:** `saveAndFlush` inside a try, and on violation take the existing duplicate path.
- **No rate limit:**
  - `/register`, `/verify-email` and `/resend-verification` are not covered by `LoginRateLimitFilter.java:98-105`.
  - Every register call runs Argon2, and every duplicate sends an email.
  - The threat model assumed "the thread pool bounds concurrency", which virtual threads invalidate.
  - **Fix:** add `REGISTER_IP` and `REGISTER_USER` buckets, plus a per-`emailHmac` limit on account-exists emails.

#### P1-8. Mail sending is unbounded and has no timeouts (US-002, US-007) — Low-Medium [T]
- **What is right:** `@Async @TransactionalEventListener(AFTER_COMMIT)` (`MailEventListener.java:41-80`).
- **What is wrong:**
  - The executor is a virtual-thread `SimpleAsyncTaskExecutor` with no concurrency limit (`AsyncConfig.java:39-43`).
  - JavaMail connect and read timeouts are unset, which means they wait forever.
- **Fix:**
  - Set `spring.task.execution.simple.concurrency-limit` to about 10–20.
  - Set SMTP timeouts to 5–10 s.
  - Set `await-termination=true`.
  - An outbox is only needed if email loss becomes unacceptable.

#### P1-9. Smaller items — Low
- **Lua sliding window** (`R/scripts/sliding_window_rate_limit.lua:14-23`):
  - It uses the app node's clock. Use `redis.call('TIME')` instead.
  - Its member `now..'-'..math.random(100000)` can collide within the same millisecond and undercount. Pass a unique id from Java.
  - The atomicity is correct.
- **Throttle windows mix two clocks:** `created_at` comes from the DB clock, but the throttle bounds come from the app's `Instant` (`ResendVerificationUseCase.java:113`, `ForgotPasswordUseCase.java:99`). Set `created_at` from the injected `Clock`.
- **JWT verification** (`JwtRs256Service.java:154-158`):
  - It uses a single key and ignores `kid`, so key rotation invalidates every in-flight token. US-003 AC-5 asks for overlap. Use a `Map<kid, PublicKey>` locator.
  - It builds a new `JwtParser` per request. Build it once.
- **Zero-admin health indicator** (`JpaUserRoleRepository.java:330-366`):
  - It scans all tenants with a correlated subquery, every 30 s per instance.
  - `r.name = :adminRoleName` cannot use the `(tenant_id, name)` index.
  - Move it to a scheduled job that publishes a gauge.
- **Counting by transfer:** `RoleManagementService.java:216` fetches all holder ids just to call `.size()`. Use `COUNT(*)`.
- **Unbounded `roles[]` claim** (`JwtRs256Service.java:120`): an extreme user could exceed the 8 KB header limit. Cap the claim or drop it, since only `/users/me` reads it.
- **Logout cookie path accepts revoked tokens** (`LogoutUseCase.java:72-84`): an old, already revoked cookie can still trigger a global sign-out. Resolve the user only from an active token.
- **Request logs lack `tenantId`:** `ApiRequestLoggingFilter` runs after the JWT filter has cleared the MDC.

## 3. Over-engineering: complexity that exceeds the requirements

| Area | Evidence | Assessment |
|---|---|---|
| Redis permission cache (US-010) | §P0-7 table | Costs more round trips than it saves, and introduces an unbounded-staleness bug. Remove it. |
| `REQUIRES_NEW` for **success** audit events | `SecureEventService` for `LOGIN_SUCCESS`, `TOKEN_REFRESH_SUCCESS`, … | Only failure events need to survive a rollback. This choice directly causes the pool hazard (P0-3) and the false-success audit rows (P0-2). |
| Audit retry buffer apparatus (US-008) | Two lanes, six metrics, escape-hatch flag (`AuthEventRetryBuffer`) | The data structure is sound, but its placement means it rarely catches real failures (P0-8). A self-contained best-effort insert with one bounded queue would cover more with less code. |
| RBAC assign/revoke path (US-016 to US-018) | `RoleAssignmentService.java`: 1,343 lines; about 12–13 sequential round trips per privileged revoke; byte-ordered lock acquisition; `FORCE INDEX` hints | One tenant mutex plus one admin predicate (M3) would remove M7, M8, M10, M5b and M12 and the lock-ordering machinery, and fix P0-6 and P1-1. |
| ADR-0022 freshness design (US-018 M7, not built) | Three Redis connection factories, a four-state machine, a replay queue, a 1 s prober | The core idea is right: a per-user monotonic epoch, O(1) per request. Before building the state machine, compare it against "no cache + epoch watermark + fail-open-and-alert". |
| jti denylist (ADR 0008/0016) | — | Wrong granularity for global revocation. A per-user watermark is simpler and actually works (P0-9). |
| Unused indexes | §P1-4 | Write cost with no reader. |

**Places where DSA or system-design additions would *not* help** (deliberately not recommended):
- **Permission lookups as `Set`, `EnumSet` or bitset**, in the frontend directive or the backend evaluator: about 8 permissions, memoized in a `computed`. Not worth it.
- **Token bucket instead of a sliding-window log for login limits:** no material gain at limits of 5–30.
- **ShedLock today:** the only `@Scheduled` job drains its own node's buffer, so running on every node is correct.
- **Paginating role lists now:** bounded by the 500-role cap. It is already planned in US-018 C2.
- **Microservice extraction, CQRS, event sourcing:** nothing in the stories needs them.

## 4. Appropriately applied (keep)

- **UUIDv7 `BINARY(16)` PKs** (ADR 0005): append-only clustered inserts, compact keys, and they enable PK-range retention (P1-3).
- **Email blind index:** HMAC over normalized email plus `UNIQUE(tenant_id, email_hmac)` gives O(log n) lookup and per-tenant uniqueness without plaintext. The record-typed `EmailCipher` avoids spurious dirty checks.
- **Opaque tokens:** 256-bit `SecureRandom`, stored as SHA-256 with a unique index. Using a fast hash, not Argon2, is correct for high-entropy secrets.
- **Single-use verify and reset:** `@Version` + explicit `flush()` inside the try is the correct atomic consume, and is the model P0-2 and P0-4 should follow.
- **RBAC one-active-assignment rule:** a STORED generated `active_key` + unique index emulates the partial unique index MySQL lacks, backed by a CHECK and a delete trigger. `saveAndFlush` turns the duplicate race into a clean 409.
- **RBAC revoke and detach:** a conditional `UPDATE … WHERE revoked_at IS NULL` whose row count is the guard. No `@Version` is needed.
- **Per-request authorization:** an O(1) set lookup on JWT claims with zero DB access. RS256 verification is about 50 µs. Stateless, so it scales horizontally.
- **Grant-subset check (ADR-0021):** compares by id; a `HashSet` of holdings, then a scan of the target, O(|held| + |target|). It fails closed.
- **Last-admin algorithm itself:** counts distinct holders, excludes by assignment id, O(H), with deterministic lock order (no deadlocks). The problems are its scope and its predicate, not the algorithm.
- **Atomic RBAC audit (ADR 0024):** `MANDATORY` propagation for success events; cache eviction and logs run after commit.
- **Rate-limit primitives:** `ConcurrentHashMap.compute` gives a per-key atomic check-and-add, and the Lua ZSET script is atomic. The sliding-window log fits small limits.
- **Retry buffer structure:** two bounded `ArrayBlockingQueue` lanes, O(1) non-blocking `offer`, isolation so a flood cannot evict LOCKOUT events.
- **Frontend tokens:** the access token lives in memory only; the refresh cookie is `HttpOnly; Secure; SameSite=Strict` and path-scoped; the CSP is strict. Origin-checked token attachment.
- **Frontend single-flight:** `shareReplay(1)` without `refCount` (so one unsubscriber can't cancel a rotation), and the interceptor order is correct.
- **Context propagation:** `RequestContext` is an explicit record, not a ThreadLocal. `MdcTaskDecorator` restores the prior MDC. No `synchronized` blocks exist, so there is no virtual-thread pinning.
- **ArchUnit-enforced layering and tenant-query rules:** zero runtime cost and they catch drift at build time.
