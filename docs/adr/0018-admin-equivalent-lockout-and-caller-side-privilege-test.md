## Context

ADR-0017 made `RoleAssignmentService.assign()`/`revoke()` gate on what a role *does* — literally named `TENANT_ADMIN`, **or** carrying any member of `RbacDangerousPermissions.NAMES` — rather than on what it is called. It applied that shift to the **target** role only, and recorded two things it deliberately did not do:

> *"That rule is applied to the **target** role only. The **caller**-side admin test deliberately remains name-based … This asymmetry is a decision, not an oversight … Making the caller-side test privilege-based is a separate, larger decision that belongs with RES-3; **do not assume this ADR made it.**"* — ADR-0017, follow-on rule 2

> *"Last-admin-style lockout protection still covers only the literally-named `TENANT_ADMIN`. Extending it to admin-equivalent custom roles is tracked separately (US-016 RES-3); **do not assume this ADR covers it.**"* — ADR-0017, follow-on rule 6

Both gaps were live and exploitable-by-accident. A tenant whose only administrator held a custom, admin-equivalent role could be revoked straight to zero administrators, with **no** preventive guard (the lockout guard only evaluated when the revoked role was literally named `TENANT_ADMIN`) and **no** detective signal (`RbacZeroActiveAdminsHealthIndicator` matched the same literal name). Symmetrically, a user holding such a role was *subject to* ADR-0017's gate but could never *pass* it, so a tenant's last administrator could be provably lockout-protected and simultaneously unable to administer the tenant at all.

This is the ADR that closes both. It also resolves, rather than inherits, the pre-existing lock cycle ADR-0017 named and accepted (US-016 RES-10), because the mechanism this ADR adopts would otherwise have widened it.

Seven decisions were taken. Each had a cheaper-looking alternative, rejected for a stated reason.

## Decision

### D1 — Two named admin-equivalence predicates, one permission set

`rbac.domain` gains `RbacAdminEquivalence`, hosting exactly two static predicates:

- **`isAdminEquivalent(roleName, permissionNames)`** — *target* side. Literal `TENANT_ADMIN`, **or ANY** member of `RbacDangerousPermissions.NAMES`. Identical to ADR-0017 D1's shipped gate condition, and now the single predicate behind the lockout guard, the health indicator **and** the gate's own `privileged` condition.
- **`isFullyAdminEquivalent(roleName, permissionNames)`** — *caller* side. Literal `TENANT_ADMIN`, **or ALL THREE** of `role:write`, `user:write`, `tenant:write`.

`RbacDangerousPermissions` remains the **single source of truth for the permission set** and gains only two combinators (`carriesAny`, `carriesAll`). Neither predicate redefines the set; they differ only in how it is combined. A separate domain type rather than private service methods, for the reason `RbacDangerousPermissions`'s own Javadoc already states: policy that two services and a health indicator depend on must be directly unit-testable under the `*.domain.*` coverage gate.

**Rejected:** one predicate for both sides (see D2 — it is vacuous); a `boolean isAdminEquivalent(roleId)` port method (see D3); deriving admin-equivalence from `is_system_role` (orthogonal, already rejected by ADR-0017 D1).

> **[Gate 2 amendment, 2026-09-18 — RC-18.1, threat model T-E30 part 3.]** `carriesAll` must be specified and implemented as **a per-name, case-insensitive `anyMatch`**: for each of the three names independently, does the collection contain a case-insensitive match? It must **never** be a count (`…filter(contains).count() >= 3` returns `true` for `["user:write","user:write","user:write"]` — a fail-**open** shape) and must **never** be `containsAll` (case-sensitive — fails closed, but silently, and would deny a legitimate `Role:Write` variant). `carriesAny` does not share this trap. The duplicate-bearing input is not reachable through M10 today (`pk_role_permissions` plus `uq_permissions_name` forbid duplicates), which is precisely when the property is cheap to pin and expensive to discover later. Mechanically enforced by MC-B's three added regression assertions (design §11.2).

### D2 — The caller-side test is **strictly narrower** than the target-side test, and that is the decision, not an inconsistency

`requireActiveTenantAdmin` now passes iff the caller holds an active assignment of a role satisfying `isFullyAdminEquivalent`. It is **not** the target-side predicate. Four independent reasons, any one sufficient:

1. **A symmetric ANY caller test is vacuous, provably.** Both verbs sit behind `@RequiresPermission("user:write")`; a caller can only hold `user:write` via an active assignment of a role that carries it; `user:write` is itself in `RbacDangerousPermissions.NAMES`. So "the caller holds an admin-equivalent role" is **true for 100 % of callers who can reach this code** — including the exact non-admin attacker ADR-0017 was written about. It would not be a weaker gate; it would be no gate, while compiling cleanly and reading as "symmetric".
2. **The two sides ask different questions.** The target side asks *"is this role a lever on who administers the tenant?"* — ANY is right, because each of the three permissions is independently sufficient to escalate further, which is why US-015 defined the set that way. The caller side asks *"is this principal an administrator?"* — holding one escalation-capable permission is not that. ALL-three is the closest permission-shaped statement of "this role is a full stand-in for `TENANT_ADMIN`" available without a new schema concept.
3. **The two sides fail in opposite directions.** Target-side drift fails **closed** (a spurious 409/403). Caller-side drift fails **open** (it grants administrative capability). Asymmetric predicates for asymmetric failure modes is the correct engineering response.
4. **It is the narrowest change that closes the filed gap.** US-016 RES-9's own wording describes exactly this population: *"a user holding a custom role that carries all three dangerous permissions … is subject to this gate but can never pass it."*

**Mechanically enforced, not reviewed:** a unit assertion that a caller whose only role carries exactly `user:write` is **denied**, plus four shipped integration tests that seed exactly that caller and assert 403. If any of them is ever "fixed" to assert success, ADR-0017 has been silently undone.

**Rejected:** the literal symmetric reading (vacuous — reason 1); an explicit admin-equivalence marker column on `roles` (removes the guesswork entirely, but costs a migration, a management API surface and its own decision — recorded as a residual, not taken); descoping the caller-side fix (contradicts a stakeholder-approved Gate 1 resolution).

> **[Gate 2 amendment, 2026-09-18 — threat model T-E30 part 1, informational.]** The predicate was attacked directly at Gate 2 Step B and **survived**: no ALL-three role can exist that a literal `TENANT_ADMIN` did not deliberately create, because each of the three attaches is AC11-gated on an active literal `TENANT_ADMIN`, `role_permissions` has no other application writer, `roles` carries no `UPDATE`/`DELETE` grant, `permissions` is `SELECT`-only, and `RbacRoleNames.RESERVED` blocks the name half. What the predicate does **not** bound is the *population* that ends up holding such a role without anyone deciding to grant it — that is US-016 RES-1(b), recorded below under "what this ADR does not close".

### D3 — Dangerous-permission **names** still may not cross `UserRoleAssignmentPort` — ADR-0017 D2 is upheld, not argued against

The service needs to know which of the tenant's roles are admin-equivalent. The new port method returns **`(roleId, permissionName)` pairs for one tenant**; the service applies the `rbac.domain` predicate and passes back a set of **role ids** for the locked read. No port method takes a `Set<String> dangerousNames` parameter, and the adapter hardcodes no permission name.

This costs one extra round trip relative to pushing an `IN (:dangerousNames)` filter into SQL. That cost is paid deliberately: ADR-0017 D2's rule ("not hardcoded in the adapter … and not passed in as a parameter either") is what keeps the policy in one unit-tested place and removes the "a future caller passes a stale set" failure mode. A future story that pushes the filter into SQL must argue against this decision explicitly.

**One deliberate, stated asymmetry.** `RbacZeroActiveAdminsHealthIndicator` **does** pass `RbacRoleNames.TENANT_ADMIN` and `RbacDangerousPermissions.NAMES` into its repository query. That is legal and unchanged in kind: the indicator is infrastructure that injects the repository **directly and does not go through the port at all**, and it already passes the role name this way today. D3 binds the **port**, not this component. The names still originate in `rbac.domain` and are never hardcoded in the repository.

**Rejected:** `boolean isRoleAdminEquivalent(roleId)` on the port (a verdict crossing the port — the exact shape ADR-0017 D2 rejected for M7); injecting `RoleManagementPort` into `RoleAssignmentService` (would hand a read-only collaborator write authority over `role_permissions` — rejected in writing three times now); giving the persistence adapter a `JpaRolePermissionRepository` (would hand the *assignment* adapter `save`/`delete`/`deleteAll` over the one RBAC table with both `INSERT` and `DELETE` grants). The tenant-scoped permission query is therefore hosted on `JpaRoleRepository`, which the adapter already injects — the adapter's constructor gains **zero** dependencies.

> **[Gate 2 amendment, 2026-09-18 — RC-17.1 disposition. D3 is NOT reopened.]** The threat model's RC-17.1 asks for the bypass canary to be given a derivation independent of the gate's own input, and illustrates it with a SQL shape that would take the dangerous-permission names as a port parameter. **That illustration is not adopted, because it would contradict this decision one day after it was accepted.** The design instead satisfies RC-17.1's *property* — an independent driving index, an independent statement, independent scoping, and no input shared with the gate — with a port read (**M12**) that returns `(roleId, permissionName)` pairs for the **caller's own active assignments**, driven off `fk_user_roles_user`, with the domain predicate applied service-side exactly as M10's result is. No names cross the port; D3 stands unamended. The one axis this does **not** buy is a second *combinator* implementation: `isFullyAdminEquivalent` remains shared between gate and canary, and the design records that honestly in RES-18 rather than claiming more independence than M12 delivers.

### D4 — The lockout invariant is **distinct holders**, tenant-wide, excluding the row being revoked

The guard blocks iff:

> the set of **distinct `user_id`s** holding an active assignment of **any** admin-equivalent role in the tenant, **excluding the assignment row being revoked**, is **empty**.

The shipped predicate counted **assignment rows** of **one** role (`size() <= 1`). That was correct only because `uq_user_role_active` makes rows and holders 1:1 *within a single `role_id`*. Across a union it is false: a user holding both the literal `TENANT_ADMIN` and a dangerous custom role contributes **two rows and one holder**, so a row-count union check would read "not the last holder" and let the tenant be zeroed — the exact failure this ADR exists to prevent, arrived at by a straightforward-looking per-role extension.

The distinct-holder form covers three previously separate edge cases structurally rather than by ordering rules: a single user holding two admin-equivalent roles; two users each holding a different one; and concurrent revocation of two different admin-equivalent roles.

Consequently `privileged` — not the name match — now drives the lock, the lock-hold timer **and** the guard. That is provably the right set: a revocation can only reduce the tenant's admin-equivalent holder set if the revoked role is itself admin-equivalent. So the gate condition, the lock condition and the lockout condition remain **one condition**, preserving ADR-0017 D4's "one condition, one call site" property rather than forking it — and the benign path costs nothing at all.

**Rejected:** counting distinct holders in SQL (a locking read over `DISTINCT`/aggregate projections is implementation-defined under JPA, and the row-exclusion is awkward in JPQL; doing the set arithmetic in the service keeps the predicate unit-testable without a database).

- **[Amended 2026-09-24 — `07-security-review.md` H-1, found at Phase 7 code audit.]** **The "any admin-equivalent role" population above is the wrong population for this invariant, and the shipped guard checking it was a regression, not a refinement.** D2 (below) narrows the *caller* gate to `namedAdminRoleId ∪ fullyAdminEquivalentIds` precisely because an ANY-only holder (a role carrying just one dangerous permission) can never pass it. But the lockout guard, as shipped, still counted that same ANY-only holder as a "remaining administrator" — so a tenant could retain one while losing its last holder able to ever pass the caller gate again, silently and permanently, while this guard and `RbacZeroActiveAdminsHealthIndicator` (which shared the same ANY predicate) kept reporting healthy. **The invariant above is corrected in place: the distinct-holder set is the tenant's CALLER-QUALIFYING holders (`namedAdminRoleId ∪ fullyAdminEquivalentIds` — the same population D2 admits), not every ANY-admin-equivalent holder.** The **lock** itself is unchanged (still the broader ANY union, acquired for the deadlock-freedom reasons D5/D6 below establish) — only the in-Java distinct-holder filter over what the lock already covers is narrowed, via a `roleId` field added to the locked-holder projection. `RbacZeroActiveAdminsHealthIndicator`'s two support queries are re-scoped identically, so the preventive and detective controls continue to cover the same population (this ADR's own "Benefits" claim), just the corrected one. Fixed same-day; see `docs/features/US-017/03b-threat-model.md` RES-24.

### D5 — One statement, one lock: an ascending-sorted `role_id` IN-list, and the materialised-flag alternative is rejected

The guard acquires a **single** `PESSIMISTIC_WRITE` read over the tenant's admin-equivalent role ids **plus the target role id**, sorted **ascending**, driven off `fk_user_roles_role`, with **no join to `roles`** (joining would widen the lock beyond `user_roles`). The shipped single-role lock method is **removed** — the new one strictly supersedes it, and leaving both would ship a second locking-read site and a second index-discipline site.

- **One statement, not a loop of N locks.** A loop creates N acquisition points and makes correctness depend on the caller remembering to sort and on no early return between acquisitions.
- **Ascending order is a port contract, not a caller convention.** Every transaction supplies the same total order, so acquisition across transactions is totally ordered by `(role_id, index position)` and no cycle can form among these statements — including when two concurrent transactions compute **different** lock sets because a concurrent attach/detach changed the tenant's roles. A total order does not require identical sets.
- **The target role is always in the lock set** when the gate applies, so any disagreement between the per-role permission read and the tenant-scoped one fails *toward more locking*, and the subsequent `INSERT`/`UPDATE` are contained.

**Rejected — a materialised per-tenant "has ≥1 active admin-equivalent holder" flag** (floated at Gate 1 as the simpler alternative): it is simpler for locking and much harder for everything else — a new table, a `GRANT` that Flyway does not manage, a write on every assign/revoke/attach/detach path, and a new consistency problem whose failure mode is a security control silently reading a stale flag. It trades a solved problem for an unsolved one.

> **[Gate 2 amendment, 2026-09-18 — RC-20.7, threat model T-D15 part 3.]** *"Ascending"* is under-specified as written and must name its ordering. `List.sort` on `UUID` uses `UUID.compareTo`, which compares `mostSigBits` as a **signed** long; MySQL compares `BINARY(16)` **unsigned**. The two coincide for every id in the system today (seeded ids have a clear high bit; UUIDv7 keeps it clear until ≈ year 6429), so the divergence is latent rather than live. The port contract therefore reads: **ascending means unsigned byte-wise order of the 16-byte representation, matching `BINARY(16)`** — not `UUID.compareTo`. MC-E asserts that comparator specifically, because an MC-E that merely asserts "sorted ascending" would pass under a comparator that does not match the database's order and give false assurance about the exact property this decision rests on. Note also that the real guarantee comes from the *plan*: an ascending range scan on `fk_user_roles_role` acquires in index order regardless of the IN-list's order, so the Java sort is belt-and-braces and the belt is plan stability — MC-C is extended to assert `key = fk_user_roles_role` for IN-lists of size 1, 2 and ≥ 20.

### D6 — The caller-side read stays **inside** the lock, so ADR-0017 D4's containment proof is extended rather than replaced

ADR-0017 D4 proved deadlock freedom on three pillars: the exclusive set lock is acquired first; the gate's shared read is *contained* inside it because both statements drive off the same index (InnoDB locks **index records**, not logical rows, so containment is a property of the *plan*); and `REPEATABLE READ` gap locking serialises the critical section.

Widening the lock to N ranges and the caller read to a set preserves all three, for one structural reason: **every role that can make the caller pass is admin-equivalent** (ALL ⊆ ANY), so the caller-qualifying role ids are a **subset** of the locked set. Every index record the caller read requests is therefore already exclusively locked by the same transaction, and InnoDB grants a shared request on a record the same transaction already holds exclusively — no upgrade, no wait. The caller read keeps its `FORCE INDEX` on the same index the set lock drives off, and both are re-asserted by an `EXPLAIN` integration test; a plan mismatch remains an Architect-level escalation, not a test to relax. `REPEATABLE READ` remains asserted mechanically.

**Rejected:** leaving the caller read outside the lock as a second, independent acquisition. Those would be genuinely new acquisitions on records the set lock never touched, reintroducing exactly the shared-then-exclusive ordering hazard ADR-0017 D4 was written to prevent.

### D7 — The pre-existing lock cycle (US-016 RES-10) is **closed**, not inherited: both verbs acquire the same lock first

RES-10 is the cycle between `assign(TENANT_ADMIN)` — a shared lock on the caller's own row, then an insert-intention lock in the same range — and `revoke(TENANT_ADMIN)`'s exclusive next-key range lock, acquired in the opposite order. It reproduced against real MySQL **5 runs out of 5** and forced a thread out of the concurrency harness rather than being fixed.

Widening the exclusive lock from one range to N makes that cycle reachable from workloads that are safe today: assigning a **dangerous custom role** now inserts into a range that a concurrent revocation exclusively locks. Silently inheriting the old risk acceptance would therefore ship a known, widened availability regression on the exact method the risk was filed against.

**Decision: `assign()` acquires the same set lock, first, on the privileged path.** The rule becomes:

> Every transaction that performs a privileged role change in a tenant acquires exactly one lock first — the exclusive set lock over the ascending-sorted admin-equivalent role ids — and every other lock it takes is contained inside that region.

Under it, two privileged transactions in the same tenant conflict at that lock and serialise there, so their subsequent acquisitions cannot interleave into a cycle; transactions in different tenants take disjoint ranges; a *benign* role change takes no such lock and touches ranges no lock set contains; and RES-10's original cycle is eliminated at the root, because the assign path's shared read and insert-intention are now inside a region it already holds exclusively.

**Cost, stated plainly:** privileged assigns and privileged revokes in the same tenant now fully serialise. Justified because these are rare, already-admin-gated administrative operations on an endpoint family deliberately left un-rate-limited *precisely because only privileged principals reach it*, the denial path is already rate-bounded, and the alternative is shipping a widened deadlock. The lock-hold timer is extended to cover both verbs so the cost is measured rather than assumed.

**This is proved empirically, not by review**, per ADR-0017's own follow-on rule: the mixed-workload concurrency harness is reshaped to **restore the `assign(TENANT_ADMIN)` thread RES-10 forced out**, and its passing over repeated runs is the closure evidence. A residual deadlock is an Architect-level escalation; **a retry-on-deadlock policy is explicitly not pre-approved** — ADR-0017 rejected that option on this path, and converting an ordering defect into a retry policy would be the same mistake.

> **[Gate 2 amendment, 2026-09-18 — RC-20.1 and RC-20.5, threat model T-D13 and T-D15. The decision stands; two of its stated justifications are corrected.]**
>
> **(a) The reachability clause above is factually wrong and is withdrawn.** *"Only privileged principals reach it"* is false for the path that matters: the set lock is acquired at check 4.5 and the authorization gate is check 5, so **the lock is taken before the authorization decision on both verbs**, by callers who are about to be denied — the exact non-admin `user:write` population ADR-0017's gate exists to deny. The ordering is **correct and must not be changed**: the set lock must precede the caller read or D6's containment proof collapses and the shared-then-exclusive hazard returns. What is corrected is the claim, not the code. **The real bound is US-016 D14's per-`(tenantId, actorUserId)` denial throttle**, which runs before any lock or read. That bound carries US-016 **RES-11(c)**'s caveat: under the default in-memory store it is **per-replica**, so the effective bound is `max-denials × replicas`. **A multi-replica deployment must therefore set `store-type=redis` (or divide `max-denials` by replica count) — for this design that is a deployment prerequisite, not guidance.** The composed amplification is recorded as design RES-19 (Medium) and measured by a first-class `{operation="assign", outcome="denied"}` lock-hold timer series.
>
> **(b) The total-order claim is restated per index.** As written it reads as unqualified; the analysis supports it only over one index. Correct statement: the acquisition order is **totally ordered with respect to `fk_user_roles_role`**; acquisitions in `uq_user_role_active` (the STORED generated `active_key`), in `fk_user_roles_user`, and in the clustered index are **serialised for privileged × privileged pairs by the set-lock conflict**, and are **unchanged-in-kind from the shipped design for privileged × benign pairs**. No cycle was constructible in either case, but "not constructible by review" is not the standard this decision sets for itself — so the concurrency harness gains a **benign `assign`/`revoke` thread** against the same users the privileged threads touch. Without it the harness exercises only privileged × privileged, which is the case the mutual-exclusion argument already covers, and proves nothing about the remainder.

### D8 — Detaching a dangerous permission becomes admin-gated, symmetrically with attaching one

`RoleManagementService.detachPermission` gains the same admin gate `attachPermission` has: when the permission being detached is a `RbacDangerousPermissions` member, the caller must hold an active `TENANT_ADMIN` assignment. It is placed before the pairing-existence check, mirroring attach's ordering, and reuses the read the method already performs, so no statement is added on the ordinary path.

The reason the shipped asymmetry ("detaching reduces privilege") no longer holds: **this ADR makes admin-equivalence a mutable input to a security guard.** `roles.name` cannot change at runtime — the application holds no `UPDATE`/`DELETE` on `roles` — but `role_permissions` has both `INSERT` and `DELETE`, so before this change any `role:write` holder could flip a role out of admin-equivalence concurrently with a lockout evaluation. Detaching a dangerous permission does not merely reduce privilege; it removes a role from the protected set.

One stated behavioural narrowing: a non-admin detaching a dangerous permission that is **not attached** now receives 403 rather than 404. That matches attach's ordering and removes an attachment-existence oracle.

**Ruling on the remaining race:** the tenant-scoped permission read **must** be non-locking (the application holds `SELECT` only on `permissions`, so a locking read would be rejected in production and pass every containerised test), so admin-equivalence is evaluated against the transaction's `REPEATABLE READ` snapshot. A `role_permissions` change committing after that point does not affect the decision, and both directions are safe: a later detach yields at worst a spurious 409 (fail-safe over-protection), and a later attach yields an unprotected new admin-equivalent role whose zero-holder state is caught by the detective control on its next run. That is why the preventive and detective halves ship together.

**Rejected:** gating on "is this the role's last dangerous permission" (needs a second read, still races, and is not symmetric with attach); locking `role_permissions`/`permissions` (impossible in production, invisible to every test).

> **[Gate 2 amendment, 2026-09-18 — threat model T-I14, under-claimed benefit; and the gate's own population.]** Two corrections of emphasis, neither changing the decision. **First, the benefit is understated.** The headline break is not the 404 → 403 ordering change; it is that **a non-admin `role:write` holder can no longer detach a dangerous permission at all** — today that call succeeds with 204. The full response matrix confirms the new 403 is returned whether or not the pairing exists, so the attachment-existence oracle that exists today for dangerous permissions is *removed* and none is created. **Second, this gate's population is not a boundary.** "After this ADR, flipping a role out of admin-equivalence requires an active literal `TENANT_ADMIN`" is true only if read as *"an active literal `TENANT_ADMIN`, **or anyone who can become one in a single request**"* — see the reworded mint-side entry under "what this ADR does not close". For the TOCTOU ruling above the conclusion is unchanged, because both populations are administrators.

## Consequences

**Benefits.** A tenant can no longer be revoked to zero administrators through any sequence of role revocations, regardless of what its administrative role is called, and the condition is evaluated over distinct holders rather than rows. The detective control sees exactly the population the preventive control protects, with **no application-maintained staleness** — the decisive property for a control whose purpose is catching a bypass. A holder of a fully admin-equivalent custom role can now administer the tenant, closing the state in which a tenant's last administrator was lockout-protected yet powerless. The pre-existing lock cycle is closed rather than widened. The mint side gains a symmetric detach gate, so the guard's own input is no longer mutable by any `role:write` holder, and a non-admin can no longer detach a dangerous permission at all. No migration, no grant change, no new dependency, no endpoint, DTO, error code, feature flag, cache key, or frontend change; no Redis.

> **[Gate 2 amendment, 2026-09-18 — RC-22.1, threat model T-D16.]** The original text claimed **"zero staleness"**. That is false and is corrected above to *"no application-maintained staleness"*. `/actuator/health` carries a shipped **30 s response cache** (`management.endpoint.health.cache.time-to-live`), added by `07-security-review.md` M-2 **for this exact indicator** because the endpoint is `permitAll`, carries no rate limit, and runs a cross-tenant scan on every hit. The decision (live query, no materialisation, no cache of our own) is unaffected — 30 s is immaterial for a control whose remediation is DBA-level — but the *argument* mattered: as originally written it is an argument a future engineer could cite to **remove a security control**. The TTL bounds an anonymous cost-amplification path and the widened two-query, four-table form makes it **more** load-bearing, not less. It is recorded as a named security control in the design (§8.2) and in `monitoring.md`, alongside the liveness/readiness group exclusion as a **protected property** — this indicator must never be swept into a probe group, or a widened DOWN becomes an outage.

**Trade-offs.** This is the **first authorization loosening in this epic** — every prior RBAC story removed capability, and this one grants it to a population that does not have it today; that is why it carries its own threat model. Privileged assigns and revokes in the same tenant now fully serialise, and the shipped lock-hold timer's name is henceforth historical because it covers both verbs. One revocation that is blocked today becomes permitted (revoking the literal `TENANT_ADMIN` from a target who still holds another admin-equivalent role) — a false positive being removed, but a behaviour change nonetheless. A non-admin detaching an unattached dangerous permission receives 403 instead of 404. The health check runs two queries over four tables instead of one over two.

**What this ADR does *not* close (rule 5):**

- **[Amended 2026-09-18 — RC-16.1, threat model T-E28.]** The **mint-side** admin test — on `attachPermission` and on this ADR's new `detachPermission` gate — **remains name-based**. The asymmetry ADR-0017 recorded is **relocated, not eliminated**: a fully admin-equivalent caller can assign and revoke privileged roles but cannot attach or detach dangerous permissions. **This is narrower by construction, but it bounds nothing and must not be read as a containment.** A fully admin-equivalent caller may self-assign the literal `TENANT_ADMIN` role in a **single request** — newly permitted by D2, and definitionally correct under it — and is thereafter a mint-side administrator. It is recorded here for **definitional consistency, not as a control**; a future reviewer deciding whether to widen the mint side must not conclude there is a safety property to preserve. The promotion itself is now signalled (`RBAC_ADMIN_MINTED_BY_NON_NAMED_ADMIN`, paged on self-target), because before that signal the single most sensitive operation this ADR newly permits produced no distinguishable record at all.
- **[Added 2026-09-18 — RC-15.1, threat model T-E27, High.]** **US-016 RES-1(b) / T-E21 — the standing attach-after-assign pre-positioning primitive — is not closed by this ADR, and this ADR materially amplifies it.** Any `user:write` holder may self-assign a benign custom role today (legitimately; no gate applies, correctly) and be silently escalated whenever an administrator later attaches dangerous permissions to that role. Before this ADR the payoff was admin-equivalent *permissions*, effective only at the next token mint (≈ 30 min) and insufficient to pass the caller gate. After it, the payoff is **caller-side administrative capability, effective on the next request from a live DB read, and the literal `TENANT_ADMIN` role one self-assignment later.** Likelihood is unchanged; impact increases substantially. **This is recorded against the existing RES-1(b) entry — it does not open a competing one** — and that entry's **owner (Md Nisar Ahmed), its 2026-11-27 review date and its hard expiry at Epic 3 kickoff carry forward unchanged**. Mitigation is detection, not prevention: US-016 D13's shipped holder-count signal on `attachPermission` is extended so that the moment a role crosses the ALL-three threshold is itself reported (`RBAC_ROLE_BECAME_FULLY_ADMIN_EQUIVALENT`, paged when the role already has holders) — the only moment at which anyone can see a mass silent promotion to administrator.
- The caller-side predicate is **narrower than "admin-equivalent"**: a role carrying `role:write` + `user:write` but not `tenant:write` is arguably admin-equivalent and still cannot administer. The remedy — an explicit admin-equivalence marker on the role — was rejected here as a materially larger change. This fails **closed**.
- A tenant with **no admin-equivalent role at all** remains invisible to the detective control, exactly as before. That is a provisioning defect, not a lockout, and reporting it would turn a rare page into a routine one during tenant bootstrap.
- `listActive`'s `assignedBy` redaction **remains literal-name-based**, so a fully admin-equivalent caller may revoke a role but not see who granted it. Redaction is a disclosure decision whose population was never analysed for this predicate.
- Admin-equivalence is evaluated against a **snapshot**: a role that *becomes* admin-equivalent after the deciding transaction's first read is not protected by that transaction's guard. The attach requires an administrator, and the detective control is the backstop.
- **[Amended 2026-09-18 — RC-17.3, threat model T-E29.]** The gate and its bypass canary **share the ALL/ANY combinator** (`RbacAdminEquivalence`). The *inputs* are now independent — the canary derives the caller's qualification from its own read (M12, driven off a different index, with different scoping), so an over-broad tenant-scoped resolution no longer silences the detector that exists to notice it. What remains shared is the domain predicate itself, whose one fail-open shape is pinned by D1's amendment and MC-B. The canary's name half remains independent of both. The runbook's *"this canary detects a bypass **inside** the gate, not **around** it"* caveat is extended to name the shared combinator explicitly.
- **[Amended 2026-09-24 — `07-security-review.md` M-1, found at Phase 7 code audit.]** The independent input above (M12/M4) was, as shipped, read from `assign()`'s **post-commit** runnable — i.e. after the new row was already committed. On a self-assignment where the target role is itself fully admin-equivalent (literal `TENANT_ADMIN` or ALL-three), that read then sees the very row the request just created, making `callerIsAdmin="false"` structurally **unreachable** for exactly the population this canary most needs to catch a bypass for. This is a timing defect, not an independence defect — RC-17.1/RC-17.3's input-independence property (above) is unaffected. **Fixed:** the M4/M12 read now runs before the INSERT and its result is carried into the post-commit runnable, so it reflects the caller's state immediately before this request, not after. Fixed same-day; see `03b-threat-model.md` RES-25.
- **[Added 2026-09-18 — RC-19, threat model T-R10.]** A **blocked lockout still produces no durable audit row**. That decision stands — `LastAdminRoleException` is a business-rule conflict by an authorized actor, and widening `ROLE_ASSIGNMENT_DENIED` would falsify a shipped contract and change the `auth_events` population US-014's alerting is tuned on. But the compensating control is now **conditional in writing**, as US-015 RES-10 and US-016 RES-6 both required for this same shape: the WARN markers `RBAC_LAST_ADMIN_REVOCATION_BLOCKED`, `RBAC_PRIVILEGED_ROLE_CHANGE_BLOCKED` and `RBAC_DANGEROUS_PERMISSION_DETACH_BLOCKED` **must be retained at least as long as `auth_events` — minimum 1 year**, the figure taken from `docs/observability-standards.md`. The scenario that forces this is a compromised sole-admin account repeatedly attempting to destroy the tenant's last admin access: every attempt is *blocked*, so there is no `ROLE_REVOKED`, no denial row, and no durable record of any kind — only WARN lines. **Ops sign-off on the retention figure is a merge-checklist item**; naming it is an Architect act, honouring it is not.
- Enforcement remains "check at the moment of the operation": **no existing assignment is re-validated**, and nothing already granted is revoked by this change.

**Follow-on rules for future work:**

- **Never substitute one admin-equivalence predicate for the other.** The target-side test is ANY; the caller-side test is ALL. An ANY caller test is vacuous, because every caller who reaches these verbs holds `user:write`, which is itself in the dangerous set. Any new call site must state which side it is on and why. **[Amended 2026-09-18]** And the ALL combinator must be a per-name case-insensitive `anyMatch` — never a count, never `containsAll` (D1's amendment).
- **A lockout-style invariant over more than one role must be expressed over distinct principals, never over rows.** Row counts and holder counts coincide only within a single role id.
- **Any transaction performing a privileged role change in a tenant must acquire the admin-equivalent set lock first, in ascending role-id order, in a single statement.** Adding a new verb to this family without that acquisition re-opens the cycle this ADR closed. The acquisition order is a port contract, and its proof is a multi-threaded integration test that includes a concurrent `assign` of the literally-named admin role — do not remove that thread again. **[Amended 2026-09-18 — RC-20.5/20.6/20.7]** State the order **with respect to a named index**: it is total over `fk_user_roles_role` only. Acquisitions in `uq_user_role_active`, `fk_user_roles_user` and the clustered index are serialised for privileged × privileged by the set-lock conflict and are unchanged-in-kind for privileged × benign — and the harness must carry a **benign** thread, or it proves only the case the mutual-exclusion argument already covers. "Ascending" means **unsigned byte-wise order of the 16-byte representation**, not `UUID.compareTo`. Plan **stability** across IN-list cardinalities is part of the claim, not a fixture detail.
- **A lock acquired before an authorization decision is reachable by unauthorized callers, and must be costed and bounded as such.** Ordering the lock before the gate is correct here (containment depends on it) — but any design that does so must state the real reachable population and name the control that bounds it, rather than asserting that only privileged principals arrive. Where that bound is a throttle with a per-replica store, the multi-replica deployment configuration is a **prerequisite of the design**, not operational advice.
- **A control whose input is mutable at runtime must gate the mutation, or state which side of the commit wins.** Both were done here; either alone would have been insufficient.
- **A detection signal derived to disagree with a gate must be re-derived whenever the gate's predicate changes, must not be collapsed into the gate, and must not consume the gate's own primary input.** A canary that cannot legitimately disagree is not a canary; a canary that disagrees on every legitimate operation is a pager; **and a canary that shares the input whose corruption it exists to detect is neither.** Where full independence is not achievable, name the axis that remains shared rather than claiming the property outright.
- **[Added 2026-09-18 — RC-15/RC-16.]** **A change that increases the payoff of an accepted, owned residual must re-rate that residual in the same change**, citing the existing register entry and carrying its owner, review date and expiry forward — never opening a competing entry. A risk register that silently accrues value on entries nobody re-read is worse than no register.
