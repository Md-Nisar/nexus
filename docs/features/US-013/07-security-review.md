## 2. Adversarial pass — the specific things this review was asked to break

### 2.1 Authorization / IDOR — is the guard or directive *structurally incapable* of being an authorization boundary?

**Tested by asking whether application code can ever *read* the permission verdict.** A misuse-as-authorization requires a readable answer.

| Surface | Verdict readable by app code? | Basis (read, not assumed) |
|---|---|---|
| `permissionGuard` | **No.** | `permission.guard.ts:39` is a bare `CanActivateFn` const. It is not injectable, holds no module state, and its only return values (`true` / `Router.createUrlTree`) go to the Angular Router. Nothing is exported but the function itself. |
| `HasPermissionDirective` | **No.** | `has-permission.directive.ts:65` — `granted` is `private readonly`; there is **no** `output()`, no exported signal, no host binding, no public method, no exported property. The sole observable effect is `ViewContainerRef.createEmbeddedView` / `.clear()` (`:83–95`). A consuming component cannot obtain the boolean. |
| `AuthStore.permissions()` | **Yes** — public, synchronous, readable by anything. | This is the real (and only) R-1 vector, exactly as the threat model concluded. **Its `@security` JSDoc survived implementation intact** (`auth.store.ts`: *"UX only… Never an authorization decision"*), as did the field-level warning on `AuthUser.permissions` (`shared/types/auth.ts:44–50`: *"never gate data access or trust decisions on this value"*). Both are load-bearing and must never be trimmed. |

**Actual consumers of `permissions()` in production code — grep-verified, exhaustive:** exactly **two**, `permission.guard.ts:52` (a router decision) and `has-permission.directive.ts:66` (DOM instantiation). **Neither is a data-access, tenancy, cryptographic, or capability decision.** No component, service, interceptor, or resolver anywhere in `src/` reads the permission list, and **no route in the shipped route table uses `permissionGuard` yet** (grep-verified — the story is infrastructure-only), so there is no existing consumer to inherit a mistake from.

**IDOR:** not applicable in the strict sense, and stated explicitly rather than skipped — this diff issues **zero HTTP requests**, constructs **zero URLs**, and reads **zero request-supplied or route-supplied identifiers** (`route.data['permission']` is a compile-time literal in the bundle, not user input). There is no object to fetch and therefore no object-level check to get wrong. Object-level authorization remains a server-side concern, unchanged and enforced by US-011.

**Enforcement point unchanged — verified:** zero backend diff (§0.1). `@RequiresPermission` / `TenantAwarePermissionEvaluator` are exactly the artifacts US-011's audit verified fail-closed on every branch, with cross-tenant escalation proven closed end to end through the real filter chain by `CrossTenantPermissionIT`. Every client-side bypass route catalogued in the threat model §4.1 (override the `/users/me` response, write the signal, skip the guard via `router.navigate()`, ignore the UI and call the API) therefore still terminates in a `403 RBAC_001`. **The bypass is trivial and remains consequence-free.**

### 2.2 Tenant isolation — stated explicitly, not skipped

**Zero cross-tenant data flow is introduced.** `tenantId` appears in this diff in exactly one place: `shared/testing/auth.fixtures.ts:13` (`tenantId: 'tenant-456'`, a test fixture default). No production file in the changeset reads, writes, compares, propagates, or branches on a tenant identifier. The guard and directive compare a permission string against an in-memory list belonging to the *current* session only; there is no collection, no filter, no query, and no second tenant's data present in the browser to leak across. The tenant-provenance invariant (`permissions[]` and `tenant_id` originate from the same signed token) lives entirely server-side, is untouched, and is regression-locked by US-011's `JwtRs256ServiceTest` provenance test. **No tenant-isolation finding.**

### 2.3 Injection (A03) — `AccessDeniedComponent`'s template

**No injection surface. Confirmed by reading the template, not by assuming Angular protects it.**

- The template (`access-denied.component.ts:39–75`) contains **zero interpolations** — no `{{ }}`, no `[property]` binding from any data source. Every string is a compile-time literal. The component **injects no state whatsoever**: its only dependency is a `viewChild` on its own `<h1>`. There is no `AuthStore`, no `AppError`, no `Router` state, no query-parameter read — so there is no attacker-influenced value that could reach the DOM at all, escaped or otherwise.
- **Both `<a>` hrefs are static, as required:** `routerLink="/dashboard"` is a literal string (not a bound `[routerLink]` expression, so no array/`UrlTree` can be injected), and `href="mailto:support@yourcompany.example"` is a literal attribute, not `[href]` — Angular's URL sanitiser is not even engaged, and no dynamic scheme (`javascript:`, `data:`) can be substituted.
- **Repository-wide grep: zero `innerHTML`, zero `[innerHTML]`, zero `outerHTML`, zero `DomSanitizer`, zero `bypassSecurityTrust*` anywhere in `src/`.** No XSS sink exists in the application for a hostile `requiredPermission` (or any other server-controlled string) to reach, even if a future template wrongly rendered it — interpolation would yield inert text.
- **No other injection class applies:** no SQL/JPQL (no backend diff, no query), no command execution, no `eval`/`new Function`, no template compilation from data, no LDAP. `toAppError` assigns named keys explicitly with no spread of the untrusted body and no dynamic key, so **prototype pollution is closed** (re-verified on the modified lines).
- **Log injection (CRLF):** the only new log call site passes a compile-time event name as the message and two bounded values in `context` — the permission string (closed vocabulary) and a query-stripped path. Nothing attacker-controlled is concatenated into a log message. The one place a server-controlled string *could* reach a log message (`GlobalErrorHandler`'s `JSON.stringify`) escapes control characters by construction. **No log-forging route.**

### 2.4 Input validation — is the `typeof` narrowing on `route.data['permission']` sound?

**Yes. Walked hostile-input-first rather than happy-path-first.** The check is `const required: unknown = route.data['permission'];` followed by `if (typeof required !== 'string' || required.length === 0) return true;` (`permission.guard.ts:48–50`).

- Typed `unknown`, not `any` and not `string` — so **no false type claim is made** about an index-signature read, and the compiler forces the narrowing before use. This is the correct pattern and mirrors M-2's fix in the interceptor.
- The narrowing is **exhaustive against every hostile shape**: `undefined` (key absent), `null`, `42`, `true`, `{}`, `[]`, a `Symbol`, or an object with a hostile `toString`/`valueOf` all fail the `typeof` test and return early. Crucially, `required` is **never coerced** — no template-string interpolation, no `String()`, no `+` concatenation — so no `toString`/`Symbol.toPrimitive` getter on a hostile object is ever invoked, and nothing can throw or side-effect from the check itself. The empty string is rejected by the explicit `.length === 0` test.
- After the guard, `required` is provably a non-empty `string`, so `Array.prototype.includes(required)` (`:52`) is a plain value comparison that cannot throw and cannot coerce. `authStore.permissions()` is `readonly string[]` and **never `undefined`** (`?? NO_PERMISSIONS`), so `.includes` cannot throw on a null receiver either — this is AC-4's "degrades gracefully" property, and it holds even if a stale session object were ever missing `permissions` entirely.
- Matching is **exact and case-sensitive** (`includes`, not a regex, not `startsWith`, not a wildcard match), so no permission-string prefix or glob confusion is possible — e.g. holding `roles:readonly` does not satisfy `roles:read`.
- **Fail-open on a missing/empty `permission` is a deliberate, documented, requirements-level accepted decision** (`01-requirements.md` R-2 resolution; design §6.2; threat model §4.7) and is **not** flagged here. Its only control is no longer human memory: M-1's contract spec now turns a typo'd or omitted `data.permission` into a **red build** for every statically-declared route. Fail-*closed* would convert a config typo into a user-facing outage, which is strictly worse for a non-security control.
- Spec coverage is genuinely hostile, not decorative: missing key, non-string (`42`), and empty string each have a dedicated fail-open test (`permission.guard.spec.ts:68–81`).

### 2.5 `AppError.requiredPermission` — is it rendered, logged, or forwarded anywhere?

**Independently verified across the whole frontend, not just the diff. Answer: no production code reads it at all.**

Exhaustive grep for `requiredPermission` across `src/` and `e2e/` yields **13 hits, and every one is accounted for**: 2 producer lines in `api-error.interceptor.ts` (the M-2 narrowing), 1 `ProblemDocument` interface field, 1 `AppError` interface field plus its JSDoc, 1 prohibition comment in `access-denied.component.ts`, and 6 lines inside `api-error.interceptor.spec.ts`. **Zero template interpolations, zero `[attr]`/`[href]`/URL constructions, zero `logger.*` calls, zero analytics calls, zero `router.navigate` parameters, zero Web Storage writes.** The field ships **inert**: it is written once by the interceptor and read by nothing outside its own spec, so there is no existing misuse for a future engineer to copy. The prohibition is carried at four discoverable points (field JSDoc, guide section, guide review-checklist line, and the Access Denied component's own `@security` note), and the one *mechanical* leak path that does exist is documented at the field itself and ticketed — see **SEC-3**.

Also confirmed: the interceptor's **own** log call does **not** include `requiredPermission` (it logs `errorCode`, `status`, `statusText`, `url` only), so a hostile value cannot reach a log line through the interceptor.

### 2.6 Secrets, credentials, and internal hostnames

**Every new file grepped and read. No hardcoded credential, API key, token, private key, connection string, or internal hostname.**

- The only string literals resembling credentials are test fixtures with obviously fake values, in test-only files: `accessToken: 'test-access-token'` (`shared/testing/auth.fixtures.ts:29`) and the query-string literal used at `permission.guard.spec.ts:84` — the latter is the *payload of the assertion that the query string is stripped*, i.e. it exists precisely to prove that secrets in a URL never reach the log. Neither is a real credential and neither is reachable from the production bundle.

The `TODO(PM)` marker is retained in place (`access-denied.component.ts:63–64`) and the release-checklist item stands. **No security action.** Recorded as **SEC-5** for traceability only.
- No `.env`, no `application-*.properties`, no config file, and no `APP_CONFIG` default is touched. No new environment variable, no new URL, no new endpoint. **Configuration continues to come from `APP_CONFIG` / `src/environments/`**, and no feature file hardcodes a URL.
- The new guide content actively **hardens** this surface: M-5(b)'s "no secrets in a permission-gated component" clause plus the matching review-checklist line address the exact failure mode (**A02** / **A01**) that route gating invites developers toward.

### 2.7 Test-fixture module — the hard build-breaking constraint

**Verified by reading the current file, not the design's claim.** `shared/testing/auth.fixtures.ts` imports **exactly two modules**: `{ computed, signal, Signal, WritableSignal }` from `@angular/core`, and `{ AuthSession, AuthUser }` from `../types/auth`. **Zero `vitest`, zero `@angular/core/testing`, zero `@playwright/test`, zero `vi`/`describe`/`expect` references.** This matters beyond hygiene: `tsconfig.app.json` includes `src/**/*.ts` and excludes only `src/**/*.spec.ts` with `"types": []`, so a test-framework import in this non-spec file would **break `npm run build`**. The constraint holds. The write-side omission (`setSession`/`clearSession` absent, documented at `:53–57`) is what keeps it holding — specs needing spies spread the stub and add their own. **Prod bundle delta is zero**: nothing in the application import graph references this module (grep-verified — only three spec files import it).

### 2.8 Denial of service / rate limiting

**No DoS surface, and rate limiting is not applicable — stated explicitly.** The guard performs **zero I/O**: one synchronous `Array.prototype.includes` over a list of roughly 20 elements per navigation. The directive is protected against DOM churn by a `computed()` value-equality short-circuit plus a `hasView` bookkeeping flag, and this is **mechanically proven** rather than asserted — `has-permission.directive.spec.ts:85–98` sets a *fresh array with identical contents* and asserts the retained `nativeElement` reference is unchanged, i.e. no teardown and recreate. A denial triggers one lazy-chunk fetch of a static asset. **This changeset adds no server endpoint, authenticated or otherwise**, so there is nothing to throttle and no unauthenticated cost-amplification path (`SECURITY.md` §8's table is unaffected). The one client-side self-DoS vector — a navigation loop if `/access-denied` were nested under a gated ancestor — is closed by M-5(c) in both the guide and the route's own JSDoc.

### 2.9 Repudiation / logging & monitoring (A09)

The new `logger.debug('Permission check denied navigation', …)` is `debug`-level and therefore **inert in production** (`environment.ts` sets `logLevel: 'warn'`, so `minLevel` is 2 and `enabled('debug')` is `0 >= 2`, false). It correctly goes through `LoggerService` rather than `console` (`no-console` is an ESLint error outside `logger.service.ts`/`main.ts`, which is what makes AC-4's "no console error" mechanically true). It is deliberately **not** treated as security evidence: it is client-attested, forgeable, and suppressible, and the authoritative denial record remains the backend's `nexus.rbac.permission_denied` counter and WARN log (US-011, unchanged). The directive logs nothing at all, which is the right call — per-change-detection logging across N instances would be pure noise. **No repudiation gap and no audit-log regression:** this story removes, weakens, or reroutes no existing audit event.

## 4. Findings

### [Low] SEC-1 — The denial log strips the query string but **not** the URL fragment, leaving T-06's channel partly open
**File:** `nexus-frontend/src/app/core/guards/permission.guard.ts:60`
**Issue:** M-3 implements T-06's fix exactly as specified — `state.url.split('?')[0]` — but `RouterStateSnapshot.url` is the **fully serialized** URL, which includes the fragment as well as the query string (`DefaultUrlSerializer` emits `path?query#fragment`). Splitting on `?` alone therefore leaves a fragment intact: an attempted navigation to `/gated#access_token=…` or `/gated#email=user@example.com` logs the fragment verbatim. The inline comment's own justification — *"it is unbounded and future-controlled"* — applies verbatim to the fragment, which is equally unbounded and equally future-controlled. Neither the threat model (§4.5's channel sweep) nor `06-code-review.md` identified this sub-channel; both stopped at the query string. The spec (`permission.guard.spec.ts:83–92`) asserts only the `?` case, so nothing would catch a fragment regression.
**Risk:** Today, **nil** — no route in the shipped table uses a fragment for anything, and the log line is `debug`-level and prod-inert. Forward-looking, this is the same standing invitation T-06 described: the first navigation that carries an identifier, an email, or (in some OAuth/implicit-flow patterns) a token in the fragment writes it to a developer console, against the org PII-in-logs policy. **A09**, and PII-policy-adjacent.
**Fix:** Split on either delimiter — `route: state.url.split(/[?#]/)[0]` — update the inline comment to say "query string and fragment", and extend the existing spec by one case asserting on an input such as `/gated#email=user@example.com`. One expression, one test case; cannot regress.

**Post-report update: FIXED.** `permission.guard.ts` now splits on `/[?#]/`, the inline comment names both the query string and the fragment, and `permission.guard.spec.ts` asserts the fragment-stripping case. Re-verified against current file contents.

### [Low] SEC-2 — M-1's route-table contract spec inspects only `canActivate`, so a `canActivateChild: [permissionGuard]` usage escapes the mechanical control entirely
**File:** `nexus-frontend/src/app/core/guards/permission-guard-contract.spec.ts:42–60` (and the `KNOWN LIMITATION` note at `:27–31`)
**Issue:** `findPermissionGuardViolations` reads `route.canActivate` only. Angular offers a second, entirely legitimate registration point for a `CanActivateFn` — `canActivateChild`, which is in fact the idiomatic way to guard a whole subtree from a parent route. A future route table using `canActivateChild: [permissionGuard]` (or `canActivateChild: [authGuard]` on a parent with `canActivate: [permissionGuard]` on a child) is invisible to this walk: in the first shape, the guard's `data.permission` and `authGuard` composition are **never checked at all** — silently reverting M-1 to the human-memory control it was created to replace; in the second, the ancestor's `authGuard` is not credited, producing a **false-positive red build** on a legitimate pattern (the same class of bug the ancestor-guard remediation just fixed, reached through a different property). The `KNOWN LIMITATION` comment names only the `loadChildren` gap, so a future maintainer has no warning about this one. Grep confirms `canActivateChild` appears **nowhere** in the codebase today, so nothing is currently unchecked.
**Risk:** Not attacker-triggerable and not a breach — the server still enforces every operation, so the impact is a route that ships client-side-ungated (a confusing UI plus a false sense of coverage) or an entitled user misrouted to `/access-denied` on cold start (availability). The deeper risk is the one T-03 was written about: **erosion of the "UX only" posture into an assumed control that silently is not applied.** **A04**, **A01**-adjacent, defense-in-depth.
**Fix:** Treat the two arrays as one guard set in the walk — build the guard list from both `route.canActivate` and `route.canActivateChild` for the presence and `data.permission` checks, credit a `canActivateChild` `authGuard` when computing the ancestor flag for descendants, and add one synthetic-table test per shape. At minimum, if the scope is left as-is, extend the `KNOWN LIMITATION` comment to name `canActivateChild` explicitly so the gap is discoverable.

**Post-report update: FIXED.** `findPermissionGuardViolations` now checks `route.canActivateChild` as its own guard array (not just `canActivate`), credits a `canActivateChild` `authGuard` toward descendants' ancestor flag, and a route's own `canActivate` `authGuard` toward its own `canActivateChild` check. Synthetic-table tests cover both shapes. Re-verified against current file contents.

### [Low] SEC-3 — A full `AppError` (including `requiredPermission`) can still reach a **production-level** log via `GlobalErrorHandler`'s wholesale `JSON.stringify` — documented and ticketed, but open
**File:** `nexus-frontend/src/app/core/errors/global-error-handler.ts:57–69` (`getErrorMessage`) and `:31–38` (`logger.error`), reached from `nexus-frontend/src/app/core/http/api-error.interceptor.ts` (rejects with a plain object, not an `Error`)
**Issue:** Carried forward from T-05 and **re-verified as still live in the current code, not merely quoted from the threat model.** `getErrorMessage` falls through to `JSON.stringify(error)` for any non-`Error` value, and that string is interpolated into the message passed to `logger.error(...)`. Three mechanics confirmed by reading the files: `logger.error` **is enabled in production** (`logLevel: 'warn'` gives `minLevel` 2, and `error` outranks `warn`); `sanitizeParams` scrubs `context` only and never the message string; and `SENSITIVE_KEYS` matches key *names* inside `context`, never message content. So an `AppError` left unhandled (a `subscribe()` without an error callback, an unhandled rejection, a throw in a template expression) serializes `requiredPermission`, `traceId`, `correlationId`, `message`, and `details[]` into one production log line. `app.config.ts` explicitly anticipates wiring an error-tracking SDK to this exact handler.
**Risk:** Today, low-sensitivity self-disclosure to the reporting user's own browser console; **no remote sink exists** (grep-verified: zero analytics, beacon, or Sentry code in `src/`), and every current consumer supplies an error callback. Tomorrow, the day the anticipated Sentry ticket lands, the full `AppError` ships to a third party by default — mechanically violating the field's own "do not send it to analytics" contract. **A09**, **A01**-adjacent information disclosure. Not exploitable in this changeset; a defense-in-depth gap and a booby trap for the next telemetry ticket.
**Fix:** **Correctly out of scope for this 3-point, frontend-only story — do not fix here.** Both halves of the required mitigation are already in place and were verified: the constraint is discoverable at the field (`shared/types/app-error.ts:74–80` `@remarks`, M-5(d)) and the hardening is recorded as a backlog item (`03-design.md` §16.3, M-6). **The binding condition for closure: that ticket must land *before* any remote error-tracking sink is wired to `GlobalErrorHandler`** — the handler must stop `JSON.stringify`-ing non-`Error` values wholesale, and any telemetry integration must **allow-list** `AppError` fields rather than forwarding the object.

### [Informational] SEC-4 — Pre-existing backend dependency-check failure (Critical CVEs in transitive Spring Boot dependencies) — out of scope for US-013, raise as its own ticket
**File:** `nexus-backend/pom.xml` (transitive) — **no US-013 file involved**
**Issue:** `./mvnw -Psecurity dependency-check:check` in `nexus-backend/` is a **BUILD FAILURE**: `netty-transport-4.2.15.Final.jar` and `tomcat-embed-core-11.0.22.jar` — both transitive Spring Boot dependencies — carry Critical CVEs (CVSS 9.1), breaching the `SECURITY.md` §11 gate (block CVSS ≥ 7; this project's gate is configured at ≥ 9.0).
**Risk:** Real platform risk (**A06**), but **entirely pre-existing and wholly unrelated to this story** — independently confirmed by the **verified zero-line backend diff** (§0.1): US-013 changes no Java file and no `pom.xml`, so it neither introduces nor worsens this exposure in either direction.
**Fix:** **Not a US-013 blocker and must not be smuggled into this story's diff.** Raise a standalone backend dependency-hygiene ticket to bump the Spring Boot / Netty / Tomcat baseline to a patched line and re-run the gate. The frontend side is clean for comparison: `npm audit --omit=dev --audit-level=high` reports **0 vulnerabilities**, and `package.json`/`package-lock.json` are untouched by this story. (The separate, pre-existing 15-finding **dev/build-toolchain** `npm audit` set recorded in `03b-threat-model.md` §8 also remains out of scope — zero production-bundle exposure, local-only preconditions.)

### [Informational] SEC-5 — `mailto:support@yourcompany.example` placeholder — confirmed non-issue, no security action
**File:** `nexus-frontend/src/app/shared/pages/access-denied/access-denied.component.ts:63–71`
**Issue / Risk:** Confirmed as tasked and **not re-litigated**. A static compile-time literal `href` (not `[href]`) on an RFC 2606 reserved, non-resolvable domain. It collects no input, submits nothing, and exfiltrates nothing; `mailto:` is neither neutralised by nor relevant to Angular's URL sanitiser (only `javascript:`/`data:` are). No injection, no SSRF, no open redirect. The only consequence of shipping it is a support request going nowhere — an availability/UX defect.
**Fix:** No security action. The `TODO(PM)` marker is present and correct; the release checklist is the right owner.

### [Informational] SEC-6 — Pre-existing, NOT this story: `details` is copied unvalidated from the problem document **and is rendered**
**File:** `nexus-frontend/src/app/core/http/api-error.interceptor.ts` (`toAppError`, the `details` copy) reaching `nexus-frontend/src/app/features/auth/registration-form/registration-form.component.ts`
**Issue:** M-2 fixed the new field, but the adjacent, pre-existing one remains: `isProblemDocument` validates only `code`, and `details` is copied unvalidated. Unlike `requiredPermission`, `details` **is** rendered — its entries are iterated and each `message` is pushed into a form control's errors and displayed. A hostile or compromised backend could send `details` as a non-array (a `TypeError` breaking the form's error path) or with attacker-chosen strings (escaped by interpolation, so text injection only — no XSS, since no sink exists).
**Risk:** Low, and requires a hostile backend or a broken TLS assumption. Cited only because it demonstrates that M-2's "validate on copy" habit has already been needed once on a field that is actually rendered.
**Fix:** **Out of scope for US-013 — correctly not fixed here.** Already carried as threat-model R-d: a future `core/http` hardening ticket should validate the full `ProblemDocument` shape, including `details` element shapes, rather than only `code`.

## 7. Verdict

### APPROVED

- **Blockers: 0.** Nothing in this changeset is exploitable, and — the load-bearing point — **nothing in it can be made exploitable by an attacker**, because every artifact it adds lives entirely inside the browser's already-untrusted zone. The authorization trust boundary is not crossed, moved, duplicated, or weakened, and the backend diff is verified empty.
- **High: 0. Medium: 0.**
- **Low: 3 at time of writing, 1 open as of the post-report update above** — SEC-1 (fragment not stripped from the denial log) and SEC-2 (`canActivateChild` escapes M-1's contract spec) were new to this pass and have since been fixed and re-tested (see the "Post-report update" notes on each finding). SEC-3 (`GlobalErrorHandler` serialization path) remains open, accepted, and ticketed as M-6.
- **Informational: 3** — SEC-4 (pre-existing backend CVE gate failure, own ticket), SEC-5 (`mailto:` placeholder, confirmed non-issue), SEC-6 (pre-existing unvalidated-and-rendered `details`, forward-flag).
- **Required threat-model mitigations: 6 / 6 present** (§1), each verified against the current file contents rather than a prior pass's claim. The recommended-only R-a was adopted early as a bonus.

**Auth, cryptography, and PII were each explicitly reviewed and are attested in §0.2 — none was approved silently.** No authentication path is added or modified, and `AuthStore.setSession`'s only two production callers were traced; no cryptography and no client-side randomness exist anywhere in the diff (`Math.random` grep-verified absent); and every new field was traced end to end for PII, with the denial log confirmed to carry exactly two bounded, closed-vocabulary values and one residual sub-channel (SEC-1) recorded. Negative claims were **grep-verified rather than trusted**: zero `sessionStorage` writes, zero telemetry/analytics/Sentry sinks, zero `innerHTML`/`bypassSecurityTrust*`/`DomSanitizer` anywhere in `src/`, zero production readers of `AppError.requiredPermission`, and zero test-framework imports in `shared/testing/auth.fixtures.ts`. Tenant isolation was checked explicitly rather than waved through as "obviously fine" — the diff contains no production reference to a tenant identifier at all. Production frontend dependency audit: **0 vulnerabilities**, with an untouched lockfile.

**The story's central claim survives a second, code-level adversarial pass: this is UX polish, not a security boundary — and the implementation makes that structurally true rather than merely documented.** The guard's verdict reaches only the Router; the directive's verdict is `private` with no output, no host binding, and no exported signal; and the only readable trust surface (`AuthStore.permissions()`) carries its `@security` warning intact at both the store and the type. Enforcement remains solely server-side `@RequiresPermission`.

Two commendations, because they are why this review is short on findings. The **no-query-parameters denial redirect** keeps RBAC internals out of the address bar, history, bookmarks, and `Referer`, and additionally forecloses an enumeration oracle — it must not be "improved" later. And the **stateless, context-free, unguarded Access Denied page** is a genuinely good security decision masquerading as a simplification: because it injects nothing and renders byte-identical output for every visitor, it cannot leak which permission was missing, which URL was attempted, or whether the resource exists.

**Recommended (non-blocking) follow-ups:** fold SEC-1 and SEC-2 into this branch if convenient (two expressions, two test cases); otherwise carry them as Low backlog items. Raise SEC-4 as its own backend dependency-hygiene ticket. Ensure M-6's `GlobalErrorHandler` ticket lands **before** any remote error-tracking sink is wired.
