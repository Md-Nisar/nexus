# US-009 — Threat Model (STRIDE)

_Output of `/design` security-reviewer pass (Phase 3b). Gate 2 deliverable. Each threat → mitigation → task. Reviewed alongside `03-design.md` before implementation._

**Scope (new attack surface introduced by this design only):** the four net-new RBAC tables in `V5__rbac_schema.sql` (`permissions`, `roles`, `role_permissions`, `user_roles`) with their seed DML (§2.2); the `active_key` STORED generated column + `uq_user_role_active` as a security control (§2.2, ADR-0013 D2); the DELETE-only `trg_user_roles_no_delete` trigger and its deliberate asymmetry vs. `auth_events` (§2.2); the new `com.example.nexus.rbac` bounded context (4 entities + 4 repositories, §4); the base-profile `default-tenant-id` fallback (§5, ADR-0014 D5); and the `nexus_app` grant extension across the three provisioning artifacts + the AC9 manual smoke check (§6, ADR-0014 D6). This story ships **no runtime code, no controllers, no enforcement** — so most threats are assessed as *invariants the schema does or does not establish for the future consumers* (US-010 JWT population, US-012 assignment, US-015 role management), where a schema-level gap is far cheaper to fix now than after those stories ship.

**Verification basis (re-read at threat-model time, not trusted from the design doc):**
- `V2__identity_schema.sql:92-110` — confirmed `auth_events` has **both** `trg_auth_events_no_update` and `trg_auth_events_no_delete`; `user_roles` will copy only the DELETE one.
- `nexus-database/mysql/init/02-grants-post-schema.sql` — confirmed grants list **only** `auth_events`, `users`, `refresh_tokens`, `auth_tokens`; **none** of the 4 RBAC tables exist in any grant today (blast radius of the grant gap confirmed).
- `TestcontainersConfiguration.java:101-143` — confirmed the grants callback runs as `root` and grants only the 4 identity tables; the general app connection is the container `test` user, so CI structurally cannot exercise `nexus_app`.
- `application.yml:105` — confirmed **no fallback** today (`${NEXUS_IDENTITY_DEFAULT_TENANT_ID}`); `application-dev.yml:40` and `application-smoke.yml:40` hardcode the sentinel; `TestcontainersConfiguration:167-168` registers it dynamically.
- **`default-tenant-id` is live-consumed** by `RegistrationController:82,130`, `LoginController:89`, `PasswordResetController:70`, and `DevDataInitializer:62-72` — the sentinel tenant is the tenant every self-registered EPIC-001 user is written into, **not** an inert placeholder. Independently re-confirmed by reading `RegistrationController.java` directly (`@Value("${nexus.identity.default-tenant-id}") UUID defaultTenantId` injected at L54, passed at L82 and L130). This materially raises the severity of the sentinel-related threats below.
- Confirmed **no `com.example.nexus.rbac` package** exists anywhere (`Glob` returned zero) — genuinely new attack surface.
- Standard applied: `SECURITY.md` (§3 tenant-from-JWT-never-from-client, §7 PII, §10 audit-log shape, §12 OWASP checklist).

**Severity scale** (qualitative, CVSS-like, consistent with `US-008/03b-threat-model.md`): Critical / High / Medium / Low.

## STRIDE Analysis

### S — Spoofing

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-S1 | **Predictable, shared bootstrap-tenant sentinel becomes a "default identity."** `00000000-0000-7000-8000-000000000001` is hardcoded in the migration seed **and** (per §5) newly promoted to the base-`application.yml` fallback, so it is the same value in dev, Testcontainers, smoke, and prod unless explicitly overridden. It is the tenant `TENANT_ADMIN` (all 7 permissions) is seeded into, and — verified in live code — the tenant every self-registered user is written into (`RegistrationController:82,130`). | Sentinel value (§2.1, §5); `roles`/`user_roles.tenant_id` (§2.2) | An attacker who knows the well-known sentinel (public in ADR-0014, the `V5` header comment, and config) targets the one tenant guaranteed to contain a fully-privileged admin role and all bootstrap users | Medium | The sentinel is a *tenant identifier*, not an authorization token; per `SECURITY.md §3` the effective `tenant_id` for any request must come from the authenticated principal/JWT, never client input, so knowing the value alone grants nothing without a valid session for a user in that tenant. It is a valid UUIDv7 shape (not guessable-as-a-secret because it isn't a secret). | **NEW (forward-looking, US-010):** when US-010 populates the JWT `tenant_id` claim it MUST source it from `user.getTenantId()` (matching the existing `SECURITY.md §3` pattern), and MUST NOT fall back to the sentinel for a user whose tenant is unresolved — an unresolved tenant must **deny**, never default into the admin-bearing tenant. Record as a US-010 security acceptance criterion. |
| T-S2 | **Forged/misattributed role assignment via `assigned_by`.** `user_roles.assigned_by` records "who granted this role" for non-repudiation, but the schema only enforces that it is *a* real user (FK to `users(id)`), not that it was the *actual* actor or an authorized admin. | `user_roles.assigned_by` (§2.2, §4.4) | A future write path (US-012) or a leaked `nexus_app` credential inserts a row naming an arbitrary innocent admin as `assigned_by` to frame them | Low (this story) → Medium (once US-012 writes) | FK `fk_user_roles_assigner` guarantees `assigned_by` references a real user. Server-side population of `assigned_by` from the authenticated principal is a US-012 obligation, not enforceable in schema-only US-009. | **NEW (cross-story, US-012):** `assigned_by` MUST be set from the authenticated caller's principal, never from request input; add a US-012 test asserting this. Documented here as a tracked downstream obligation. |

### T — Tampering

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-T1 | **`user_roles` UPDATE grant is table-wide, so "revoked_at is the sole mutation path" has NO database-level enforcement.** ADR-0014 D6 grants `nexus_app` `SELECT, INSERT, UPDATE` on `user_roles` (verified needed for the revoke path), and §2.2 deliberately installs **no `BEFORE UPDATE` trigger** (so `revoked_at` can be set). The invariant that *only* `revoked_at` ever changes is enforced **solely by the JPA mapping** (`insertable=false, updatable=false` on the other columns, §4.4) — which a raw SQL path, bulk script, or leaked credential bypasses entirely. A raw `UPDATE user_roles SET assigned_by=?, assigned_at=?, user_id=?, role_id=? …` is fully permitted by the grant and blocked by nothing. | `user_roles` grant (§6, ADR-0014 D6) + no-UPDATE-trigger decision (§2.2) | Leaked `nexus_app` credential, an admin SQL tool, or a future bulk-migration mutating immutable columns to rewrite assignment history (change who was assigned, when, by whom) | Medium | Partial only: the JPA layer never *intends* to write those columns; the `active_key` unique index blocks the specific "flip `revoked_at` back to NULL to double-activate" case (recompute collides — verified logic). But nothing protects `user_id`/`role_id`/`assigned_by`/`assigned_at` from a raw UPDATE. This is strictly **weaker** than `auth_events`, which blocks *all* UPDATE via trigger (`V2:98-103`). | **DESIGN CHANGE — RESOLVED at Gate 2 (ADR-0015 D7):** grant tightened to column-scoped `UPDATE (revoked_at)` only, restoring `auth_events`-equivalent immutability for every other column. See ADR-0015. |
| T-T2 | **`active_key` "active" semantics may silently diverge from a consumer's notion of "active."** The generated column defines active as `revoked_at IS NULL` (§2.2). If any future consumer (US-010 JWT resolution, US-012) treats an assignment as active when `revoked_at IS NULL OR revoked_at > NOW()` (a scheduled/future revocation), then multiple rows with **future** `revoked_at` all compute `active_key = NULL`, coexist without collision, yet are all "effectively active" — defeating the sole DB guarantee of "one active assignment per (user, role)." | `active_key` generated column + `uq_user_role_active` (§2.2, ADR-0013 D2) | A future feature (scheduled revocation / validity windows) sets `revoked_at` to a future timestamp; the "one active" invariant is silently bypassed with no error | Medium (latent; depends on future consumer) | Today no consumer sets a future `revoked_at`; the design's own tests (§8.3) exercise only NULL/past. But the invariant is undocumented and unconstrained at the schema. | **RESOLVED at Gate 2:** added `CHECK (revoked_at IS NULL OR revoked_at >= assigned_at)` to `V5` + an explicit invariant comment ("revocation is immediate/past-dated, never scheduled") in the migration header and ADR-0013, forcing any future scheduled-revocation feature to revisit `active_key`'s definition rather than silently break it. |
| T-T3 | **Generated column cannot be forged directly — verify this holds under bulk import.** The security value of `active_key` rests on it being `GENERATED ALWAYS … STORED`; if a bulk import or migration could write an arbitrary `active_key`, two active rows could be made non-colliding. | `active_key` (§2.2, §4.4) | Raw SQL / bulk load attempting to supply an explicit `active_key` value, or JPA attempting to write it | Low | MySQL **rejects** explicit non-DEFAULT values for a `GENERATED ALWAYS` column (insert/update errors), so the column cannot be forged from any SQL path; JPA maps it `insertable=false, updatable=false` (§4.4) so Hibernate never writes it. The guarantee is robust against the raw-write vector. | Existing mitigation (schema + §4.4 mapping). **NEW TASK:** add a negative test asserting an explicit `INSERT … (active_key) VALUES (…)` is rejected, so a future migration author can't accidentally "fix" it into a plain column. |
| T-T4 | **Seed-data tampering / drift between the migration literal and the config fallback.** The sentinel tenant appears independently in `V5` seed DML and `application.yml` (§5); ADR-0014 D5 accepted they can drift if either changes alone, scoping `TENANT_ADMIN`/`MEMBER` to a tenant the runtime never resolves. | `V5` seed (§2.2) + `application.yml` fallback (§5) | An edit to one literal but not the other (human error), silently breaking the Epic-3 admin gate | Low | **Superseded by the T-E2 resolution below** — the base-`application.yml` fallback is removed entirely (ADR-0015 D8); dev/smoke/Testcontainers already hardcode the identical literal independently, so there is no longer a base-config copy of the sentinel to drift *from*. Residual drift risk is now scoped only to "the migration literal vs. each non-prod env's own hardcoded literal," identical in kind to any other environment-specific config and no worse than before this story. | Accepted (ADR-0014 D5, as amended by ADR-0015 D8) + PR-checklist item: any change to the sentinel must update the migration and every non-prod env file consistently. No code control. |

### R — Repudiation

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-R1 | **No `revoked_by` / revocation actor is recorded.** `user_roles` captures `assigned_by`/`assigned_at` for the grant, but revocation happens via `UPDATE revoked_at` (§2.2) with **no column recording who revoked**. A malicious or careless admin can revoke another user's role (e.g., de-privileging an account before an attack) and later deny doing so — the trail shows only *that* it was revoked, not *by whom*. | `user_roles` columns (§2.2, §4.4) | An insider revokes a role and repudiates the action; no attributable record | Low–Medium | Partial: the *authoritative* security audit trail is `auth_events` (US-008), where US-012 is expected to emit a `ROLE_REVOKED`-type event with the actor. `user_roles` itself is state, not the audit log. But the design does not state that a revocation audit event is mandatory, leaving a gap if US-012 forgets. | **NEW (cross-story, US-012):** US-012's revoke path MUST emit an `auth_events` record naming the revoking principal (mirroring how assignment should audit `assigned_by`); flag as a US-012 acceptance criterion. |
| T-R2 | **DELETE-only trigger preserves the append-only history correctly (positive control, verified).** The concern would be a hard delete erasing assignment history to repudiate a past privilege. | `trg_user_roles_no_delete` (§2.2) | Attempt to `DELETE FROM user_roles` to erase evidence of a past assignment | Low (mitigated) | Two independent layers: (a) `BEFORE DELETE` trigger `SIGNAL SQLSTATE '45000'` blocks all deletes incl. multi-row (whole-statement abort — the design's `UserRolesAppendOnlyIT` proves this, §8.4); (b) ADR-0014 D6 grants `nexus_app` **no DELETE** on `user_roles` — defense-in-depth identical to the `auth_events` pattern. History is append-only. | Existing design mitigation (§2.2, §6) + `UserRolesAppendOnlyIT` (§8.4). No new task. **Reviewer note:** same `root`/DBA residual as US-008 T-T4 applies (a DB superuser can `DROP TRIGGER` + delete) — see Accepted Risks. |

### I — Information Disclosure

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-I1 | **PII in the new tables.** AC / `SECURITY.md §7` require no PII beyond necessity. | All 4 RBAC tables (§2.2, §4) | Sensitive data stored where it needn't be | Low | **Verified clean:** `permissions`/`roles`/`role_permissions` hold only metadata (names, descriptions, timestamps). `user_roles` holds only `UUID`s (`user_id`, `role_id`, `tenant_id`, `assigned_by`) + timestamps — **no email, name, IP, or credential**. UUIDv7 PKs are non-secret identifiers, not PII. No PII surface introduced. | No new task (verified no PII). **Reviewer note:** explicitly reviewed — see reviewer note at end. |
| T-I2 | **Predictable seed identifiers leak structure.** The 9 seed UUIDv7 literals and the sentinel are sequential/low-entropy (`…000000000001`…`…00000000000b`) and publicly documented. | Seed literals (§2.1) | An attacker enumerates or references seeded role/permission IDs directly | Low | Row IDs are not authorization inputs; access to a role/permission requires an authenticated, tenant-scoped session (US-011 enforcement, out of scope here). Predictable PKs for *seeded reference data* are conventional and low-risk (contrast: user/session IDs, which are runtime UUIDv7 from `UuidGenerator`). | Accepted — seed-reference-data IDs are intentionally well-known. No task. |
| T-I3 | **Error/constraint messages leak schema internals.** The trigger message and unique/FK violation surfaces. | `trg_user_roles_no_delete` message, `uq_*`/FK names (§2.2) | Triggering a violation to read constraint names/messages | Low | The trigger message (`user_roles is append-only; use revoked_at to soft-delete`) is an operational hint, not sensitive. Downstream stories must map these to RFC-7807 `code`+`traceId` (per CLAUDE.md) and not echo raw SQLSTATE/constraint names to clients — a US-011/012/015 obligation, since US-009 has no REST surface. | **NEW (cross-story):** US-012/015 must translate `DataIntegrityViolationException` / `SQLSTATE 45000` into the RBAC problem-detail codes (`RBAC_00x`) without leaking constraint names. Noted for those stories (design §8.1 already lists the DB error contracts). |

### D — Denial of Service

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-D1 | **No unauthenticated runtime path exists in this story.** DoS via cost amplification requires a reachable endpoint. | Entire story (schema-only, §7) | N/A — no controllers, no unauthenticated path | N/A | US-009 ships zero runtime surface (§1, §7 explicit N/A). The migration runs once at deploy. There is nothing to flood. | No task — explicitly reviewed, no DoS surface added. |
| T-D2 | **Soft-delete row accumulation (`user_roles`) — latent storage-growth amplification.** Because revocation never deletes and re-assignment inserts a new row, a repeated assign→revoke→reassign loop grows `user_roles` unboundedly; all revoked rows carry `active_key = NULL` and coexist. | `user_roles` soft-delete model (§2.2) | A future US-012 write path abused to churn assignments, bloating the table + index | Low (latent, US-012) | Inherent and intended (audit-preserving append-only). No `active_key` write-amplification since revoked rows share the NULL slot (unique index permits unlimited NULLs). Bounded in practice by US-012's own authorization + rate limiting. | **NEW (cross-story, US-012):** US-012 assign/revoke endpoints must be authenticated + rate-limited; flag as a US-012 abuse-resistance criterion. Not actionable in schema-only US-009. |

### E — Elevation of Privilege

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-E1 | **Co-tenancy of all bootstrap users with the all-powerful `TENANT_ADMIN` role.** `TENANT_ADMIN` (all 7 permissions) is seeded into the sentinel tenant (§2.2), and — verified live — every self-registered user is written into that same sentinel tenant (`RegistrationController:82,130`, `DevDataInitializer`). This is a **pre-existing EPIC-001 single-tenant-bootstrap reality**, not something US-009 introduces — US-009 seeds an admin role into a tenant that self-registration already populates. Once US-010 (JWT) + US-012 (assignment) ship, self-escalation to `TENANT_ADMIN` is exactly one assignment away — gated *only* by US-012's future "who may assign" check, with no schema-level backstop. | Seed scoping (§2.2) + pre-existing registration flow | A self-registered user in the sentinel tenant obtains a `TENANT_ADMIN` assignment through any gap in US-012's assignment authorization, since the role is present and same-tenant | Medium (latent) — depends entirely on US-012's enforcement | The `active_key` invariant and `roles UNIQUE(tenant_id,name)` are correctness controls, not authorization controls. There is **no** enforcement in US-009 preventing a member from being assigned `TENANT_ADMIN` — that is deliberately US-012's job. | **TRACKED, not a US-009 design change** (co-tenancy predates this story and is an Epic-3 multi-tenancy scope question, not a schema-seeding one). **Hard AC added to EPIC-002 for US-012:** the assign-role path MUST enforce that only an existing `TENANT_ADMIN` (or a platform bootstrap process) can grant `TENANT_ADMIN`, and MUST be tenant-scoped from the JWT. Recorded now, ahead of US-012's own Gate 1, so it isn't discovered late. |
| T-E2 | **Base-profile `default-tenant-id` fallback converts a fail-fast into a silent default into the admin-bearing tenant.** Today (verified) `application.yml:105` has **no** fallback, so an environment that forgets `NEXUS_IDENTITY_DEFAULT_TENANT_ID` **fails to start** (unresolved placeholder). §5 (as originally drafted) added the fallback to **base** `application.yml`, which applies to **all profiles incl. prod**. Since dev/test/smoke already hardcode the literal, the fallback's *only* net new effect was on prod / any un-configured env: instead of refusing to boot, it would silently run with the well-known sentinel — the tenant that holds `TENANT_ADMIN` and (via `RegistrationController`) receives real users. | `application.yml` fallback (§5, WS-3, ADR-0014 D5) | A prod/staging deploy that omits the env var silently boots writing real users into the public sentinel tenant, alongside the seeded admin role, instead of failing loudly | Medium (High if prod registration is enabled and unguarded) | **DESIGN CHANGE — RESOLVED at Gate 2 (ADR-0015 D8):** the fallback is removed from base `application.yml` entirely. Dev/Testcontainers/smoke already carry the literal in their own profile-specific config, so ADR-0014 D5's "by construction" guarantee is preserved for every environment that currently relies on it; prod retains its original fail-fast behavior on an unset tenant ID. See ADR-0015. | Resolved — see ADR-0015 D8. |
| T-E3 | **Grant drift / provisioning window (US-008 T-E2 analog), inverted direction.** The `nexus_app` grants for the 4 RBAC tables live in out-of-band artifacts (§6), and CI (Testcontainers) structurally cannot exercise `nexus_app` (verified — callback grants as root, app runs as `test`). | §6 out-of-band provisioning; AC9 smoke check | (a) Missing grant → runtime `Access denied` when US-010/012 first query; (b) operator "fixes" it by over-granting (e.g., `ALL PRIVILEGES`, or `DELETE` on `user_roles`), re-opening the hard-delete path the trigger+no-grant defense-in-depth closed; (c) prod still connects as `root` (US-008 T-E2 residual), voiding the whole least-privilege posture | Medium | **Direction differs from US-008 and is mostly self-protecting:** a *missing* RBAC grant fails **closed and loud** (`Access denied for user 'nexus_app'`) at first query — the AC9 `docker compose --profile full` smoke check (§6.2) detects it. So the plain missing-grant is an availability bug, not a silent security hole. The real EoP residual is the *over*-grant / still-on-`root` case, which the smoke check (a positive "can it read/write" test) does **not** detect. | **NEW TASKS:** (1) AC9 smoke check remains a mandatory Gate-3 DoD item (§6.2, §10.4) — confirmed adequate for the *missing*-grant case. (2) **Forward-looking (US-010, first runtime):** add a startup self-check / actuator indicator (analogous to `AuthEventDbPrivilegeHealthIndicator` and US-008 T-E2's proposal) that WARNs if the live connection can `DELETE` `user_roles` or holds `ALL PRIVILEGES`/is `root` — belongs to US-010 since US-009 has no runtime surface to host it. |
| T-E4 | **`nexus_app` can escalate privilege via data manipulation of role↔permission mappings.** ADR-0014 D6 grants `nexus_app` `INSERT` on `roles`, and `SELECT, INSERT, DELETE` on `role_permissions` (needed for US-015). A compromised app credential can therefore add `tenant:write`/`user:write` to the `MEMBER` role, or create a new all-powerful role — no DDL required. | `roles` + `role_permissions` grants (§6, ADR-0014 D6) | RCE/SSRF-positioned attacker with the `nexus_app` credential rewrites `role_permissions` to escalate a controlled account | Medium | Inherent to the grants US-015 genuinely needs; least-privilege bounds it (no DDL, no `GRANT`, no `user_roles` DELETE, `permissions` read-only so the closed permission set can't be extended). Blast radius is data-level privilege change, not schema takeover. Same residual class as US-008 T-E1. | Accepted residual, bounded by least-privilege (§6, ADR-0014 D6). **NEW TASK:** the WS-4 grant-scope smoke check should also assert `nexus_app` has **no** `DROP`/`ALTER`/`GRANT` and **no** `DELETE` on `user_roles` (exactly the ADR-0014 D6 / ADR-0015 shape, nothing more) — mirrors US-008 T-E1's privilege-scope assertion. |
| T-E5 | **`is_system_role` is a security-relevant flag with ZERO enforcement in this story — and could be mistaken for a completed control.** The flag is seeded `TRUE` for `TENANT_ADMIN`/`MEMBER` (§2.2) but nothing in US-009 reads or enforces it; immutability of system roles is US-015 AC7's job. In the interim, `is_system_role` does **nothing** — yet a reader of the schema may assume system roles are protected. | `roles.is_system_role` (§2.2, §4.2) | Between US-009 and US-015: a raw/credentialed path (or a prematurely-built endpoint) mutates a system role's permission set; the flag provides no protection | Low (this story) — no runtime path exists yet to trigger it; Medium if any role-mutation endpoint ships before US-015's enforcement | Interim risk is bounded because no role-permission-mutation **endpoint** exists until US-015 (which also adds the `RBAC_003` immutability check). The `roles` grant omits UPDATE/DELETE (a system role can't be renamed/deleted via `nexus_app`), but `role_permissions` INSERT/DELETE is grantable. | **NEW (documentation + sequencing):** explicitly record that `is_system_role` is **inert until US-015 AC7** — it is *not* a shipped control in US-009. Ensure no `role_permissions`-mutation endpoint ships before US-015's immutability enforcement. |
| T-E6 | **`TENANT_ADMIN` "all permissions" is a point-in-time snapshot, not a standing rule.** `INSERT INTO role_permissions SELECT id FROM permissions` (§2.2) grants `TENANT_ADMIN` every permission that exists *at V5 apply time*. A later migration adding a permission will **not** grant it to `TENANT_ADMIN` (the SELECT ran once). | Seed DML (§2.2) | A future `V6` adds `billing:write`; `TENANT_ADMIN` silently lacks it | Low | This is a privilege **gap**, which **fails closed** (admin missing a permission → access denied, never over-granted) — the safe direction. The only real risk is developer *confusion*: the self-documenting `INSERT…SELECT` reads as "admin always has everything," which is untrue for future permissions. | Accepted (fail-closed). **NEW TASK / convention note:** document in the `V5` header + ADR-0013 that each future permission-adding migration must **also** insert the corresponding `role_permissions` row(s) for `TENANT_ADMIN`; add a `RbacSchemaMigrationIT` assertion "`TENANT_ADMIN` holds *every* row in `permissions`" so a future omission fails a test rather than silently under-granting. |

## Accepted Risks (No Mitigating Task)

| ID | Risk | Rationale |
|----|------|-----------|
| T-R2 (residual) | A DB superuser (`root`/DBA) can `DROP TRIGGER trg_user_roles_no_delete` and hard-delete assignment rows | Out of scope for an in-app control; belongs to DB-server hardening / privileged-access management — identical to US-008 T-T4. `nexus_app` (the app-reachable principal) cannot do this (no DELETE grant, no DROP).
