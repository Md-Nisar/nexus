# US-008 — Threat Model (STRIDE)

_Output of `/design` security-reviewer pass (Phase 3b). Gate 2 deliverable. Each threat → mitigation → task. Reviewed alongside `03-design.md` before implementation._

**Scope (new attack surface introduced by this design only):** the `AuthEventType` enum and 4 literal renames (§2), the `user_agent` capture path + `RequestContext` 3-arg change (§3), the in-process `AuthEventRetryBuffer` + `AuditAlertPort` (§4), `tenant_id` population (§5), the `nexus_app` least-privilege DB role + out-of-band grant provisioning (§6), and the §7 decision to keep Logout/Register audit writes in the same outer transaction. Already-shipped US-001–US-007 auth functionality is **not** re-threat-modeled except where this design changes it (the Logout signature change, the §7 transaction-semantics decision).

**Verification basis:** threats below are grounded in direct reads of `AuthEvent.java`, `RequestContext.java`, `JpaAuthEventAdapter.java`, `V2__identity_schema.sql` (triggers + column types), `docker-compose.yml` (current `root`-credentialed connection), and `SECURITY.md` (the project security standard whose §10 audit-log shape and §7 PII rules this story implements).

**Severity scale** (qualitative, CVSS-like, consistent with `US-007/03b-threat-model.md`): Critical / High / Medium / Low.

## STRIDE Analysis

### S — Spoofing

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-S1 | Forged audit event — attacker writes a fabricated `auth_events` row to plant false evidence or frame a user | `JpaAuthEventAdapter` / `nexus_app` grant (§6) | Direct DB access via leaked `nexus_app` credentials, or app-layer injection that reaches the insert path | Medium | `auth_events` has no write API (impact §9); events are constructed server-side only; `user_agent`/`tenant_id`/`ip` are server-captured, not client-asserted. `nexus_app` holds INSERT but cannot UPDATE/DELETE existing rows (§6.1) so prior evidence can't be rewritten, only appended to. | Existing design mitigation (§6.1, §9). No new task beyond T-E1's credential-scope test. |
| T-S2 | Spoofed `User-Agent` mis-attributes a session to a different client | `RequestContext.userAgent` (§3.3) | Attacker sets arbitrary `User-Agent` header | Low | `user_agent` is explicitly treated as untrusted forensic context, never an authorization input (§3.4). It is captured verbatim (capped+escaped), never parsed for trust decisions. | Accepted — document in §3.4 that `user_agent` is advisory-only, never authz input. (No code task.) |

### T — Tampering

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-T1 | JSON injection into the native `metadata` JSON column via `User-Agent` | `RequestContext.toMetadataJson()` (§3.3/§3.4) | Malicious `User-Agent` containing `"`, `\`, or control chars to break out of the JSON string and corrupt/forge sibling keys (`traceId`, `ip`) | High | `jsonEscape` (verified in `RequestContext.java:29-36`) escapes `\ " \n \r \t`; the §3 design routes `userAgent` through the **same** `jsonEscape` already proven for `traceId`/`ipAddress`. The DB column is native `JSON`, so a malformed value would also be rejected at insert. | **NEW TASK (04-tasks):** Unit test `RequestContext.toMetadataJson()` with `User-Agent` payloads containing `"`, `\`, `},{`, and embedded JSON — assert output is valid escaped JSON and no `metadata` key injection. Parser-validate the result. |
| T-T2 | `User-Agent` exceeding column width corrupts the insert / truncation splits a multi-byte UTF-8 char | `RequestContext` 512-cap (§3.3), `AuthEvent.userAgent VARCHAR(512)` (§3.1) | 10 KB `User-Agent` header; or a 512th-byte cut through a multi-byte sequence producing invalid UTF-8 that `utf8mb4` rejects | Medium | 512-char cap applied at the `RequestContext` boundary (§3.3) before insert; column width is the storage-side backstop (§3.1 comment). | **NEW TASK:** Verify truncation is by **character** (not byte) and uses `String` length semantics so it never splits a code point; unit test with a multi-byte UA at the boundary and an over-cap UA → row persists, value ≤512 chars, valid UTF-8. |
| T-T3 | Mutation/deletion of committed audit rows (the core tamper-evidence guarantee) | `auth_events` triggers (`V2:98-110`) + `nexus_app` grant (§6) | DBA-level action, app-layer bug, or leaked credential attempting UPDATE/DELETE | High | **Defense-in-depth, two independent layers:** (a) existing `BEFORE UPDATE`/`BEFORE DELETE` triggers `SIGNAL SQLSTATE '45000'` (verified `V2:98-110`); (b) new — `nexus_app` is granted only `INSERT, SELECT` on `auth_events` (§6.1), so the *application's* connection cannot issue UPDATE/DELETE at all, even if a trigger were dropped. | Existing design mitigation (§6.1) + existing `AuthEventsAppendOnlyIT` (trigger proof) + **NEW TASK** (already in design §6.4 / task-seed 14): privilege-level `*IT` running as `nexus_app` asserting UPDATE/DELETE on `auth_events` are denied at the grant level, distinct from the trigger proof. |
| T-T4 | **Security-theater check — `root`/DBA can still bypass both layers.** A `root`-credentialed connection (today's `docker-compose` default, `DB_USERNAME: root`, line 29) can `DROP TRIGGER` and `DELETE`. WS-2 does not constrain `root`. | `docker-compose.yml:29`, §6 topology | An attacker who obtains `root` DB creds, or a malicious DBA | Medium | WS-2's value is **real but bounded**: it removes the *application connection* (the largest RCE/SSRF-reachable attack surface) from the set of principals that can mutate audit rows — the app moves from `root` to `nexus_app` (§6.2 flips `DB_USERNAME`). It does **not** and cannot stop a separately-obtained `root`/DBA principal — that is out of scope for an in-app control and belongs to DB-server hardening / privileged-access management. This must be stated explicitly so the control is not over-claimed as full immutability. | **NEW TASK / residual-risk note:** §6 must document that append-only is enforced against the *application principal* and the *trigger path*, NOT against `root`/DBA; recommend (ops runbook) that the migration/DDL credential is distinct, rotated, and not the app credential, and that prod `root` is locked down. Accepted residual: a compromised DB-superuser can still tamper. |

### R — Repudiation

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-R1 | **Phantom LOGOUT** — under the §7 same-TX decision, can a LOGOUT event be recorded without actual token revocation, letting a user falsely "prove" they logged out? | `LogoutUseCase` (§7.1) | Revocation rolls back after the audit row in the same TX | Low | The §7 decision **preserves** the documented atomicity invariant precisely to prevent this: audit write and revocation commit together in one TX. If revocation rolls back, the audit row rolls back too — no phantom LOGOUT. REQUIRES_NEW was *rejected* here specifically because it would re-introduce this repudiation gap. | Existing design mitigation (§7.1). **NEW TASK:** IT asserting that a forced revocation failure leaves NO LOGOUT row (atomicity holds). |
| T-R2 | **Suppressed REGISTER via late-stage rollback (TOCTOU-style).** Can a user get registered but suppress the `REGISTER` audit event by forcing an exception after the audit call but before commit? | `RegisterUserUseCase` (§7.1) | Craft input that triggers a post-audit exception in the same TX | Low | Under §7 same-TX semantics this is **not** an evasion: if a late exception rolls the TX back, BOTH the `users` INSERT and the `REGISTER` audit row roll back — the user is *not* registered either. There is no state where "registered + no audit" results from a same-TX rollback. This is strictly **safer** than REQUIRES_NEW (which could leave a REGISTER row for a non-existent user) and equivalent-or-better than today's already-shipped same-TX behavior. The only true loss path is a *persistence-layer* audit failure (DB down), which is caught and routed to the retry buffer (§4.3), not silently dropped. | Existing design mitigation (§7.1). **NEW TASK:** IT — registration that rolls back post-audit leaves neither a user row nor a REGISTER event (no partial state). |
| T-R3 | Audit events silently lost during an audit-store outage, weakening non-repudiation for events that occurred during the outage window | `AuthEventRetryBuffer` (§4), `JpaAuthEventAdapter` (§4.3) | DB outage during auth activity; buffer overflow (drop-newest) or pod crash with un-drained buffer | Medium | Synchronous insert is primary; on failure events are buffered and retried with backoff (§4.1); drops/exhaustion are **counted and alerted** (`nexus.audit.buffer.dropped`, `nexus.audit.retry.exhausted`, `AuditAlertPort`) so loss is *observable*, not silent. Accepted residual: in-flight buffer (≤1000 events) is lost on pod crash (§4.1, ADR 0011). | Existing design mitigation (§4); **NEW TASK** (design task-seed 14): audit-store-down `*IT` — auth succeeds, event buffered, drains on recovery; assert exhaustion/drop raises an alert. Document residual in ADR 0011. |

### I — Information Disclosure

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-I1 | **Log injection (CRLF / control chars) via `User-Agent` into a log line.** The §4.3 WARN log and §4.4 alert logs run on the audit path. | `JpaAuthEventAdapter.record` WARN (§4.3), `LoggingAuditAlertAdapter` (§4.4) | `User-Agent` containing `\r\n` + forged log lines to spoof log entries / break log parsing | Low–Medium | **Verified safe in current design:** `JpaAuthEventAdapter`'s WARN logs only `event.getEventType()` (enum `wireName`, NOT attacker-controlled) and `e.getMessage()` — **`user_agent` is never logged**. The alert adapter logs `AuditAlertType` + `bufferDepth` (§4.4) — no UA. The `SECURITY.md` baseline log-injection defense (`CorrelationIdFilter` charset allowlist) covers `traceId` but NOT `User-Agent` (§3.4 explicitly notes this) — so escaping is the only control, and the design correctly keeps UA out of all log lines. | **NEW TASK (defense-in-depth):** A test/assertion that NO log statement on the audit path interpolates `user_agent` (or any raw UA-derived string). If a future change adds UA to a log line, it must pass through `jsonEscape`/CRLF-strip first. Add to the §4.5 log-scrubbing test scope. |
| T-I2 | **Stored XSS via `user_agent` when EPIC-007 renders it.** Design §3.4 flags this as a downstream obligation. | `AuthEvent.userAgent` (§3.1/§3.4) | `User-Agent: <script>...` stored verbatim (escaped only for JSON, not HTML), rendered unescaped by a future audit viewer | Medium (deferred) | For **this story's storage layer**, 512-cap + JSON-escape is **sufficient** — the value is stored safely and cannot break the JSON column or bloat rows. JSON-escaping is NOT HTML-escaping: a `<script>` payload survives storage intact (correct — storage must not lossily mangle forensic data). The XSS risk materializes only at render. | Existing design mitigation (§3.4) defers escape-on-render to EPIC-007. **NEW TASK (cross-story obligation):** record an explicit EPIC-007 entry/ADR note: "`auth_events.user_agent` and `metadata` are attacker-controlled; any viewer MUST HTML-escape on render and apply CSP." This becomes a tracked downstream requirement, not silently assumed. |
| T-I3 | **PII leakage into `auth_events.metadata` via an injection path** (AC5 — "no PII beyond necessity"). Could a crafted email/token end up echoed into `metadata` at any of the 8 call sites? | All 8 emit sites, `RequestContext.toMetadataJson()` (§5) | A call site that inadvertently passes an email/token/raw password into `withMetadata(...)` or the UA path | Medium | **Verified:** `AuthEvent` has **no email field** (confirmed `AuthEvent.java` — only `userId` UUID); `RequestContext.toMetadataJson()` emits only `traceId`, `ip`, and now `userAgent` (§3.3) — none derived from email/token/password. No call site passes raw credentials into metadata (impact §9, requirements AC5). The only *new* injected field is `userAgent`, which is attacker-self-supplied (their own UA), not victim PII. | Existing posture confirmed. **NEW TASK** (design task-seed 14): `auth_events`-payload log-scrubbing test (AC5 / Test Scenario 4) — assert no email/token/password pattern appears in any `auth_events` column (incl. `metadata` and `user_agent`) across all 8 flows. This test did not previously exist for the payload specifically. |
| T-I4 | IP address (PII per `SECURITY.md §7`) stored in `auth_events.ip_address` + mirrored in `metadata` | `AuthEvent.ipAddress`, metadata (existing) | N/A — already-shipped behavior, unchanged | Low | Pre-existing and in-scope per `SECURITY.md §10` audit-log shape (`metadata.ip` is explicitly sanctioned). Not introduced by US-008. Access to `auth_events` is restricted to `SELECT` for `nexus_app` (§6.1); reader role/access-control for EPIC-007 is out of scope (requirements Gap 7). | No new task (pre-existing, sanctioned by SECURITY.md §10). Note reader-access-control as an EPIC-007 obligation. |
| T-I5 | `tenant_id` population leaks cross-tenant inference, or a NULL tenant on post-auth events causes mis-attribution in a future viewer | `AuthEvent.withTenantId` (§5) | EPIC-007 filters by `tenant_id`; mis-populated tenant exposes one tenant's events to another | Medium | §5 sources `tenant_id` from the authenticated/loaded principal (`tenantId` param or `user.getTenantId()`), never from client input — so it cannot be spoofed to read another tenant's view. Pre-auth/unknown rows stay NULL (consistent with `user_id` nullable pattern). | Existing design mitigation (§5). **NEW TASK:** `AuthAuditIT` assertion that post-auth events carry the **correct** tenant (matching the authenticated principal, not attacker-supplied) and pre-auth events are NULL. |

### D — Denial of Service

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-D1 | **Audit-buffer blind spot — flood-induced eviction of high-value events.** An attacker floods failed logins to fill the bounded buffer during a DB outage, causing real LOCKOUT events to be **dropped** while the buffer is saturated. | `AuthEventRetryBuffer` (§4.1) | Sustained failed-login flood concurrent with (or causing) audit-store degradation | High → **Mitigated (Low residual)** | **Resolved via the two-lane design adopted at Gate 2.** `AuthEventRetryBuffer` now splits its 1000-event capacity into a 200-event **priority lane** (`LOCKOUT`, `TOKEN_REFRESH_REUSE`, `PASSWORD_CHANGED`, `ACCOUNT_LOCKED_WRITE_FAILED` — routed via `AuthEventType.isPriority()`) and an 800-event **standard lane** (everything else, incl. `LOGIN_FAILURE`). Drop-newest applies *within* each lane independently — a `LOGIN_FAILURE` flood can fill and drop from the standard lane, but **cannot touch the priority lane's capacity**, so genuine `LOCKOUT` events are no longer at risk of eviction by login-failure noise. The drainer also processes the priority lane to completion before the standard lane each tick, so security-critical events get DB-write priority during recovery. Per-lane depth/age metrics and alert thresholds (§4.1) make any priority-lane backlog visible immediately (any priority-lane depth ≥1 for 1 min pages). | **Design updated (§4.1, §4.2) — priority lane is now part of the shipped design, not deferred.** Residual: the priority lane itself is still bounded (200) and could theoretically fill if `LOCKOUT`/`TOKEN_REFRESH_REUSE`/`PASSWORD_CHANGED` volume itself spikes during an outage — but that volume is inherently far lower than generic login-failure traffic, and any priority-lane depth ≥1 already pages, so this is a Low residual, not Medium/High. **Remaining task:** unit test asserting a standard-lane-only flood (sustained `LOGIN_FAILURE` enqueues past capacity) never reduces priority-lane available capacity or evicts a priority-lane entry. |
| T-D2 | Unbounded buffer → OOM, turning an audit-store outage into a full app crash | `AuthEventRetryBuffer` (§4.1) | Sustained DB outage with continued auth traffic | Medium | Buffer is **bounded** at 1000 (`ArrayBlockingQueue`, §4.2); `offer()` is non-blocking and rejects on full (drop-newest). Heap bounded ≈1 MB worst case (§4.1). Unbounded queue explicitly rejected (§4.6). | Existing design mitigation (§4.1, §4.6). **NEW TASK:** unit test bounded-capacity overflow behavior (enqueue past 1000 → returns false, drop counter increments, no unbounded growth). |
| T-D3 | **Auth-path latency injection via the failure path** — attacker degrades the audit insert (e.g., lock contention) to add latency to every auth request | `JpaAuthEventAdapter.record` (§4.3) | Induce slow/failed audit inserts to inflate auth response time | Medium | The catch+enqueue path is O(1) non-blocking (`offer`), bounded by the OQ-4 5 ms budget (§4.3); audit failure never blocks or rolls back the primary flow (`record` never throws). For REQUIRES_NEW paths the audit insert is a separate TX. **Residual:** the *synchronous insert itself* (healthy path) is still inline — a slow-but-not-failing DB adds real latency before the catch fires. | Existing design mitigation (§4.3). **NEW TASK:** load test (Test Scenario 5, design task-seed 16) asserting the failure-path enqueue stays within the 5 ms budget; add an assertion/alert if synchronous insert p99 latency degrades (depth/age gauges already cover the failure mode). |
| T-D4 | Scheduler thread death silently halts all retry draining (audit backlog never recovers) | `AuthEventRetryBuffer.drain()` (§4.2/§10.1) | An unhandled exception in `drain()` kills the single `@Scheduled` thread | Medium | §10.1: any unexpected exception inside the drainer is **caught, logged, and counted** so the scheduler thread never dies silently; `fixedDelay` prevents overlapping drains. | Existing design mitigation (§10.1). **NEW TASK:** unit test that a `drain()` iteration throwing does not propagate / kill scheduling (next tick still runs). |
| T-D5 | `user_agent` row-bloat / storage-growth amplification on a high-volume unauthenticated path (`LOGIN_FAILURE`) | `AuthEvent.userAgent` (§3.1) | Flood failed logins each carrying a 512-char UA | Low | 512-char cap (§3.3) bounds per-row size; existing login rate limiting (`SECURITY.md §8`: 5/5min per IP+username) bounds event volume; no index on `user_agent` (§3.1) so no index-write amplification. | Existing mitigations (§3.1, SECURITY.md §8 — pre-existing rate limit). No new task. |

### E — Elevation of Privilege

| ID | Threat | Affected component | Attack vector | Severity | Mitigation | Task |
|----|--------|--------------------|---------------|----------|------------|------|
| T-E1 | **`nexus_app` credential leak expands attacker capability** — does adding a new DB role give an RCE/SSRF-positioned attacker *more* than they had? | `nexus_app` grant (§6.1) | Attacker achieves RCE/SSRF in the app and obtains the runtime DB credential | High → reduced to Medium | **WS-2 strictly *reduces* this surface, doesn't expand it.** Today the app connects as **`root`** (`docker-compose.yml:29`) — a leaked app credential = full DB superuser (DROP, GRANT, cross-db). After §6.2 flips `DB_USERNAME` to `nexus_app`, a leaked app credential grants only `INSERT/SELECT` on `auth_events` and scoped DML on identity tables (§6.1) — **no DDL, no GRANT, no UPDATE/DELETE on audit rows.** The new role does NOT grant any privilege the app doesn't need (verified against §6.1 grant list — no FILE, no SUPER, no trigger privilege). So a leaked `nexus_app` credential cannot DROP the trigger or tamper audit rows — closing exactly the bypass the question raises. | Existing design mitigation (§6.1, §6.2). **NEW TASK:** privilege-scope test (§6.4 IT) asserting `nexus_app` has NO `DROP`, `ALTER`, `GRANT`, or UPDATE/DELETE on `auth_events` — i.e., the grant is exactly INSERT/SELECT + scoped DML, nothing more. **Make flipping `DB_USERNAME` off `root` a required task (§6.2), not optional** — the EoP reduction only lands once the app stops using `root`. |
| T-E2 | **Grant-drift / provisioning window** (§6.2) — grants live in out-of-band scripts, not Flyway. Some environment may run with an over-privileged (`root`) connection, leaving `auth_events` UPDATE/DELETE-capable. | §6.2 out-of-band provisioning | Dev/CI/prod drift; prod ships before the runbook step applies; CI never creates `nexus_app` so the privilege IT is skipped | High | **This is the weakest link in WS-2 and must be closed.** §6.2 correctly argues Flyway-as-grant-owner is fragile (grants are env-specific, run as migration user). But the consequence is a real window: if prod keeps `root` because the runbook step is missed, the entire WS-2 control is silently absent while tests (running as `nexus_app` in CI) pass. The triggers still hold (defense-in-depth), so append-only is NOT lost — but the *privilege-level* guarantee is. | **NEW TASKS:** (1) The privilege-level `*IT` (§6.4) MUST provision and run as `nexus_app` in CI/Testcontainers (§6.2 row 1) so the grant is actually exercised every build. (2) Add a **startup self-check / actuator indicator** that logs (WARN) if the live connection's user is `root` or can UPDATE/DELETE `auth_events`, so an un-provisioned environment is detectable at runtime. (3) ADR 0012 records the per-env provisioning + rotation steps and the explicit accepted residual that grant application is operational, not migration-enforced. |
| T-E3 | Migration credential confusion — `nexus_app` accidentally granted DDL so it can apply `V5`, re-opening UPDATE/DELETE on `auth_events` | §6.3 migration interplay | An operator grants `nexus_app` broad DDL to "make Flyway work" | Medium | §6.3 explicitly separates the runtime (`nexus_app`, no DDL) from the migration credential (DDL-capable, separate user/`root`). ADR 0012 records "never grant `nexus_app` DDL." | Existing design mitigation (§6.3, ADR 0012). **NEW TASK:** ADR 0012 explicitly states the migration credential is distinct from `nexus_app`; CI provisioning keeps them separate (covered by T-E2 task 1). |
| T-E4 | `tenant_id` set from client-controlled input → cross-tenant escalation in the audit stream | `withTenantId` call sites (§5) | Attacker influences the `tenantId` value written to an event | Low | §5 sources `tenant_id` exclusively from the authenticated principal (method param resolved from JWT/`user.getTenantId()`), never from request body/path — matching `SECURITY.md §3` ("tenant id comes from the JWT — never from request body or path"). | Existing design mitigation (§5) + SECURITY.md §3. **NEW TASK:** code-review/test assertion that no `withTenantId(...)` argument traces to client-supplied request data. |

## Accepted Risks (No Mitigating Task)

| ID | Risk | Rationale |
|----|------|-----------|
| T-S2 | Spoofed `User-Agent` mis-attributes a client | `user_agent` is advisory forensic context only, never an authorization input (§3.4). Capturing attacker-controlled UA is the intended behavior. |
| T-T4 | A separately-obtained `root`/DBA principal can still `DROP TRIGGER` + tamper audit rows | Out of scope for an in-app control; belongs to DB-server hardening / privileged-access management. WS-2 reduces the app-reachable surface; full immutability against a DB superuser is not achievable in-app. Bounded and documented (ADR 0012). |
| T-I2 | Stored-XSS payload in `user_agent` survives storage | Storage must preserve forensic data losslessly; escape-on-render is the correct layer and is EPIC-007's tracked obligation, not this story's. 512-cap + JSON-escape is sufficient for the storage layer. |
| T-I4 | IP address (PII) stored in `auth_events` | Pre-existing, explicitly sanctioned by `SECURITY.md §10` audit-log shape; not introduced by US-008. Reader access-control is an EPIC-007 obligation (requirements Gap 7). |
| T-D1 (residual only) | The 200-event priority lane could itself fill if `LOCKOUT`/`TOKEN_REFRESH_REUSE`/`PASSWORD_CHANGED` volume spikes independently during an outage | Low residual — priority-lane volume is inherently far lower than generic `LOGIN_FAILURE` traffic, and any priority-lane depth ≥1 already pages (§4.1), so saturation is caught immediately rather than silently. Standard-lane (`LOGIN_FAILURE` noise) saturation no longer threatens the priority lane at all — the original High-severity finding is mitigated by the two-lane design. |
| T-R3 (residual) | In-flight buffer (≤1000 events) lost on pod crash | Explicitly accepted in OQ-3 / §4.1 / ADR 0011 — no durable outbox/broker for MVP; observable via metrics; outbox is the documented zero-loss upgrade path. |

## Residual Risk Summary

| Residual | Severity after mitigation | Owner |
|----------|---------------------------|-------|
| DB-superuser (`root`/DBA) can tamper audit rows (T-T4) | Medium — bounded by DB hardening, out of app scope | Ops / DBA |

| Priority-lane saturation under an independent spike in security-critical event volume (T-D1, residual only) | Low — bounded, counted, paged at depth ≥1; original High-severity standard-lane-eviction risk is mitigated by the two-lane design | Accepted (ADR 0011) |
| Stored-XSS in `user_agent` at render time (T-I2) | Medium (deferred) — EPIC-007 obligation | EPIC-007 |
| Grant-drift if prod keeps `root` (T-E2) | High until startup self-check + CI provisioning land → Low after | This story (tasks above) |

The single most important new task this threat model surfaces beyond the existing design mitigations: **T-E2 — make `nexus_app` provisioning verifiable in CI and detectable at runtime**, because §6.2's out-of-band provisioning otherwise creates a silent window where the entire WS-2 control is absent in some environment while tests pass. The triggers prevent this from being a *loss of append-only*, but it is a loss of the *privilege-level* guarantee AC3 specifically calls for.
