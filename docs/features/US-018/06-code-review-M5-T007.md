## Held up
- Zero-admin check runs on the rows returned by the M11 set lock; the lock set comes from the same helpers as assign/revoke, in the target's tenant, ascending unsigned bytewise, one statement, nothing else locked. Break-glass never calls `assign()`.
- SUCCESS audit joins the grant transaction; FAILURE rows use their own transaction and never follow a SUCCESS (RC-40.5). Grant alert fires only after commit; refusal alert after its audit write.
- `RoleAssignmentService` visibility change preserves behaviour. No permission-cache eviction needed (`RoleResolutionService` compares the cached role set with the live one). No scope creep into T-008. Containment ArchUnit rule is not vacuous; no existing rule weakened.

## Medium
1. **Refusal FAILURE row can be lost in a short-lived CLI.** `recordBreakGlassRefusal` goes `SecureEventService.recordEvent` → `JpaAuthEventAdapter.record`, which catches `DataAccessException` and enqueues to the retry buffer (10 s drain, no shutdown drain, STANDARD drop-newest lane). The comment in `AuthEventType.java:59`, the `AuthEventTypeTest` Javadoc and design §7.2 claim the type is "never written on the buffered path"; that is false. The `RBAC_AUDIT_WRITE_LOST` path never fires for this case. The daily reconciliation only watches SUCCESS rows. *Fix (preferred):* `SecureEventService.recordEventOrThrowInNewTransaction` (REQUIRES_NEW + `recordOrThrow`) used only for break-glass refusals, caller logs `RBAC_AUDIT_WRITE_LOST`. *Minimum:* correct the comment, test Javadoc and §7.2 and add a T-008 risk "buffer must be drained or disabled in the break-glass profile". (Note: decision 2 on 2026-10-15 accepted this loss; the false "never buffered" wording must be corrected either way.)
2. **`grantFirstAdmin` accepts any `changeRef`, including null.** With null it grants and writes SUCCESS with no attribution (loses the only operator attribution, Decision 10 / T-R14); free text reaches `auth_events.metadata` and the log line. `targetUserId == null` throws `IllegalArgumentException` with no audit row. *Fix:* a `ChangeRef` value object validating the RC-47 pattern `^[A-Z][A-Z0-9]{1,9}-[1-9][0-9]{0,7}$`, signature `grantFirstAdmin(UUID, ChangeRef)`; at minimum `requireNonNull`/blank check now, with a unit test.
3. **T-008 hand-off covers only the deadlock.** Any other unexpected failure (SUCCESS-audit write failure, lost connection, commit failure) leaves no FAILURE row and no `RBAC_BREAK_GLASS_USED` page (T-R15). The disabled race IT asserts `containsExactlyInAnyOrder(0, 5)`; after T-008 the deadlock loser returns the new code, so re-enabling unchanged fails about 6 of 10 runs. *Fix:* reword the `04-tasks.md` bullet to map any `RuntimeException` from `grantFirstAdmin` to an audited, paged refusal (`UNEXPECTED_ERROR`, or `CONCURRENT_RUN` for `CannotAcquireLockException` / `DeadlockLoserDataAccessException`) written after the rollback; update the `@Disabled` text and planned assertion to exit codes in {{0,5},{0,<deadlock code>}} plus exactly one active row; T-008 needs a public refusal entry point outside the grant transaction (`refuse` is private).
