# US-012 — Monitoring

**Feature:** Role assignment / revocation API (`POST /DELETE /GET /api/v1/users/{userId}/roles[/{roleId}]`)
**Audience:** on-call engineer
**Source of truth:** this document describes what T-015 actually shipped, verified against the code below — not the design doc's plan. Where verification changed something from `03-design.md` §9, it is called out explicitly.

> **Amended 2026-09-13 by US-016** (`docs/features/US-016/03-design.md` §9.3, T-020; ADR-0017). US-016 generalises the `TENANT_ADMIN`-grants-`TENANT_ADMIN` rule into a **privilege-based gate on both `assign()` and `revoke()`**. The amendments touch §1, §2 and §5 only, and are marked inline. Every metric name, tag key, tag value and log field added below was re-verified this session against `RoleAssignmentService.java`, `GlobalExceptionHandler.java` and `RbacAuthEventAdapter.java` on `feature/US-016` — not taken from the design doc's prose.

## 1. Metrics

| Metric | Type | Tags | Emitted by | Notes |
|---|---|---|---|---|
| `nexus.domain.conflict` | Counter | `code` | `GlobalExceptionHandler#handleConflict` (`nexus-backend/src/main/java/com/example/nexus/common/web/GlobalExceptionHandler.java:61`) | Fires on **every** `ConflictException`, not just RBAC's. For this story: `code="RBAC_002"` (last-admin lockout, `LastAdminRoleException`) and `code="RBAC_004"` (duplicate active assignment, `DuplicateRoleAssignmentException`). Prometheus name: `nexus_domain_conflict_total`. |
| `nexus.rbac.permission_denied` | Counter | `permission`, `reason` | `GlobalExceptionHandler#handleInsufficientPermission` (`GlobalExceptionHandler.java:167`) | Pre-existing counter (an earlier story). This story adds two new `reason` values it can carry: `CROSS_TENANT_TARGET` (AC4) and `NOT_TENANT_ADMIN` — see `common/security/DenialReason.java`. **Amended by US-016:** `NOT_TENANT_ADMIN`'s population is no longer "AC8 assign-side grant of `TENANT_ADMIN`". It is now **an `assign` *or* a `revoke` of any *privileged* role**, where privileged means either (a) the role is literally named `TENANT_ADMIN` (`matchedOn="ROLE_NAME"` — the pre-US-016 population) or (b) the role carries any permission in `RbacDangerousPermissions.NAMES` (`matchedOn="DANGEROUS_PERMISSION"` — new). See `RoleAssignmentService#requireActiveTenantAdmin` and ADR-0017. Three consequences for triage: **(i)** this counter carries no `operation` or `matchedOn` dimension — use `nexus.rbac.privileged_role_change_blocked` below for either; **(ii)** the `operation` verb is now **persisted** in the durable audit row as `auth_events.metadata.operation` on `ROLE_ASSIGNMENT_DENIED` (US-016 D17, `RbacAuthEventAdapter.java:264`), so a denial stays attributable to its verb after log retention expires; **(iii)** it **also counts throttle-suppressed denials** (US-016 D14) — a suppressed request throws the same `InsufficientPermissionException(user:write, NOT_TENANT_ADMIN)` through this handler, so it increments here and emits the generic `errorCode=RBAC_001` WARN. What a suppressed request does *not* produce is the service-level `RBAC_PRIVILEGED_ROLE_CHANGE_BLOCKED` WARN, a `privileged_role_change_blocked` increment, or a durable audit row. Prometheus name: `nexus_rbac_permission_denied_total`. |
| `nexus.rbac.audit_write_failed` | Counter | `operation` | `RbacAuthEventAdapter`'s catch-all (`nexus-backend/src/main/java/com/example/nexus/identity/infrastructure/audit/RbacAuthEventAdapter.java:103`) | `operation` ∈ `{assign, revoke}`. Fires when a role change **committed** but its audit event could not be recorded (JSON serialization failure, or `SecureEventService`/`AuthEventPort` failure). **US-016 note:** on the *denial* path this tag keeps its own pre-existing value `"deny"`; that metric tag and the new `metadata.operation` field are **deliberately different axes** and must not be unified — no existing `audit_write_failed` dashboard changes. Prometheus name: `nexus_rbac_audit_write_failed_total`. |
| **`nexus.rbac.privileged_role_change_blocked`** *(new — US-016 D15)* | Counter | `operation`, `matchedOn` | `RoleAssignmentService#requireActiveTenantAdmin`, the single gate throw site (`nexus-backend/src/main/java/com/example/nexus/rbac/application/RoleAssignmentService.java:552`) | The precise counterpart to `permission_denied{reason="NOT_TENANT_ADMIN"}`: it fires **only** for a privilege-gate denial and carries the two dimensions triage actually needs. `operation` ∈ `{assign, revoke}`; `matchedOn` ∈ `{ROLE_NAME, DANGEROUS_PERMISSION}`. Bounded cardinality **2×2 = 4 series**; **no tenant tag** — the WARN below carries `tenantId` for correlation. Emitted from values the gate has already computed, so it costs zero extra queries. **Not incremented for throttle-suppressed requests** (by construction: the throttle short-circuits above this code). Prometheus name: `nexus_rbac_privileged_role_change_blocked_total`. |
| **`nexus.rbac.denial_throttled`** *(new — US-016 D14)* | Counter | `operation` | `RoleAssignmentService#requireNotThrottled` (`RoleAssignmentService.java:467`) | One increment per request *suppressed* by the per-`(tenantId, actorUserId)` denial throttle — i.e. an `assign`/`revoke` short-circuited to 403 **before** M1's X lock, before M7/M8/M5, and before the `REQUIRES_NEW` audit write, because that actor had already produced `nexus.rbac.denial-throttle.max-denials` (default **5**) gate denials inside `nexus.rbac.denial-throttle.window-seconds` (default **60**). Bounded at 2 series. The throttle **bounds cost; it is not an authorization control** — it can only ever turn a would-be success into a 403, never the reverse, and it fails *safe* (an unavailable store reads as "not throttled" and the authoritative gate still runs). **RES-11, expected and self-clearing:** a throttled actor is also denied *benign* role changes for the remainder of the window. Prometheus name: `nexus_rbac_denial_throttled_total`. |
| **`nexus.rbac.privileged_revoke_lock_hold`** *(new — US-016 D18)* | Timer | `outcome` | `RoleAssignmentService#stopLockHoldTimer` (`RoleAssignmentService.java:393`); sample started immediately after M1 returns (`RoleAssignmentService.java:309`) | Measures the **composed** interval during which `revoke()` holds M1's `FOR UPDATE` lock over the tenant's active `TENANT_ADMIN` rows — M8 + M5 + the `REQUIRES_NEW` denial-audit write + M6 — i.e. the whole window in which every *other* privileged role change in that tenant is blocked. Publishing the composed figure rather than the pieces is the point; do not instrument the halves. `outcome` ∈ `{denied, lockout, revoked, error}` (bounded, 4 values). **No tenant tag** (unbounded); correlate via the WARN. **Verified emission caveat:** the sample is started only on the `nameMatch` path, so a *dangerous-custom-role* revoke never appears in this timer — M1 is not taken there, so there is no lock hold to measure. Expected **p99 < 50 ms** for `outcome="denied"` (the worst case: two indexed reads plus a nested transaction on a second pooled connection). Prometheus names: `nexus_rbac_privileged_revoke_lock_hold_seconds_count` / `_sum` / `_max`. ⚠ **No `_bucket` series is published today** — see the alerting prerequisite in §2. |
| **`nexus.rbac.last_admin_lockout_blocked`** *(new — US-017 D15)* | Counter | `matchedOn` | `RoleAssignmentService`, at the `LastAdminRoleException` throw site | Precise counterpart to `nexus.domain.conflict{code="RBAC_002"}`: fires **only** for a blocked last-admin-equivalent-holder lockout and carries `matchedOn` ∈ `{ROLE_NAME, DANGEROUS_PERMISSION}` (widened by US-017 FR-1/D5 to cover any admin-equivalent role, not only the literal `TENANT_ADMIN`). Bounded at **2 series**; no tenant tag (unbounded) — correlate via the `RBAC_LAST_ADMIN_REVOCATION_BLOCKED` WARN (§5), which carries `tenantId`. Prometheus name: `nexus_rbac_last_admin_lockout_blocked_total`. |
| `nexus.audit.buffer.dropped` | Counter | `lane`, `reason` | `AuthEventRetryBuffer` (existing, pre-US-012) | Relevant here because `ROLE_ASSIGNED`/`ROLE_REVOKED` were added to `AuthEventType.PRIORITY` (T-R4 reversal of the design's original D10 — see `identity/domain/AuthEventType.java`), so role-change events use the `priority` lane, not `standard`. `lane="standard"` drops should **not** include role-change events; if they ever do, `PRIORITY` membership has regressed. **US-016 note:** `ROLE_ASSIGNMENT_DENIED` is deliberately **excluded** from the PRIORITY lane, which is what stops a denial flood from displacing `ROLE_ASSIGNED`/`ROLE_REVOKED`. Any future story that moves it into PRIORITY must re-open US-016 T-D10 first. Prometheus name: `nexus_audit_buffer_dropped_total`. |
| `http.server.requests` | Timer/Counter | `uri`, `method`, `status`, `outcome` | Micrometer auto-instrumentation | Free, standard coverage for the three new URIs: `/api/v1/users/{userId}/roles` (POST, GET) and `/api/v1/users/{userId}/roles/{roleId}` (DELETE). No new instrumentation code needed. |

**Verification note:** all metric names, tag keys, and tag values above were checked directly against the shipped source (`GlobalExceptionHandler.java`, `RbacAuthEventAdapter.java`, `AuthEventRetryBuffer.java`, `DenialReason.java`), not assumed from the design doc. Every metric name assumed in `03-design.md` §9.3 matched what was actually implemented — no renames were needed.

**US-016 verification note (2026-09-13):** the three new rows above were read out of `RoleAssignmentService.java` line by line, not copied from `docs/features/US-016/03-design.md` §9.2. Two places where the shipped code differs from that design's prose are recorded rather than smoothed over: **(a)** the design says a throttle-suppressed request produces "no `permission_denied` increment" — it does increment, because the suppression path throws the same `InsufficientPermissionException` through the same handler; what it suppresses is the *service-level* WARN, the D15 counter and the audit row. **(b)** the design describes the D18 timer without qualifying which revoke paths start it — the shipped code starts it only when `nameMatch` is true. Both are noted in the rows themselves so nobody builds a dashboard on the prose.

## 2. Alerts (Prometheus)

Per `03-design.md` §9.3. Expressions copied verbatim from the design and re-verified against the metric names/tags in §1 above — **all matched**, no adjustments required.

Convention in this table (unchanged by US-016): **one row per alert, one alert per tag value**, with the tag selector inside the expression and the tag value carried in the alert *name* — the shape `nexus.rbac.permission_denied` already uses for its two alerts (`…_self_escalation_attempt` / `…_cross_tenant_attempt`). The two new `privileged_role_change_blocked` alerts follow it.

| Alert | Expression | Severity | Meaning |
|---|---|---|---|
| `nexus_rbac_role_change_denied_not_admin` *(**renamed by US-016** from `nexus_rbac_self_escalation_attempt`)* | `increase(nexus_rbac_permission_denied_total{reason="NOT_TENANT_ADMIN"}[5m]) > 0` | ticket *(**demoted by US-016** from **page**)* | **The expression is byte-identical to the pre-US-016 alert and was not edited — deliberately.** US-016 adds no new `DenialReason` value (D6), so this one expression still matches **every** denial the generalised gate can produce: assign and revoke, name-matched and dangerous-permission-matched, throttled and un-throttled. That is the whole point of D6 — it is the **detection floor**, and it holds *without anyone having to remember to edit PromQL*. A rule that must be widened by hand every time the gate's population widens is a rule that eventually misses a denial; this one cannot. What changed is only the **name** (the old one claimed "self escalation", which was never quite what the expression matched and is now plainly wrong — most of the population is neither self-directed nor an escalation attempt) and the **severity**. Demoted to ticket because the post-US-016 population now includes a routine, correctly-denied action — a non-admin helpdesk operator trying to offboard an admin — which is not page-worthy and in most organisations outnumbers the attack. **The page has not been dropped, it has moved:** see `nexus_rbac_privileged_role_change_blocked_dangerous` below, which is the high-signal shape. Triage this alert *with* `matchedOn`/`operation` from that counter, not on its own. |
| **`nexus_rbac_privileged_role_change_blocked_dangerous`** *(new — US-016)* | `increase(nexus_rbac_privileged_role_change_blocked_total{matchedOn="DANGEROUS_PERMISSION"}[5m]) > 0` | **page** | Someone who is **not** an active `TENANT_ADMIN` tried to grant or strip a role that *carries* admin-equivalent authority (any member of `RbacDangerousPermissions.NAMES`). Near-zero legitimate base rate: a role only becomes dangerous by an admin's deliberate act, and the people who administer such roles are admins. This alert inherits the pager that `nexus_rbac_role_change_denied_not_admin` gave up. Split `operation` to see whether the attempt was an `assign` (escalation shape) or a `revoke` (sabotage / offboarding-abuse shape). |
| **`nexus_rbac_privileged_role_change_blocked_byname`** *(new — US-016)* | `increase(nexus_rbac_privileged_role_change_blocked_total{matchedOn="ROLE_NAME"}[5m]) > 0` | ticket | The literally-named-`TENANT_ADMIN` population — the pre-US-016 AC8 shape, plus the new revoke-side equivalent. Dominated by offboarding attempts by operators who hold `user:write` but are not admins. Reviewed, not paged. |
| **`nexus_rbac_denial_throttle_engaged`** *(new — US-016 D14; **promoted ticket → page** per `docs/features/US-016/07-security-review.md` M-1)* | `increase(nexus_rbac_denial_throttled_total[5m]) > 0` | **page** | One actor produced ≥ `max-denials` gate denials inside `window-seconds` and is now being short-circuited to 403 above the gate — before M1/M7/M8/M5, the audit write, or `privileged_role_change_blocked`. **Promoted from ticket because the throttle key is `(tenantId, actorUserId)` — the attacker themselves — so the attacker chooses when to enter the suppressed state:** burning a few cheap `matchedOn="ROLE_NAME"` denials first puts the actor in the suppressed window, after which every `DANGEROUS_PERMISSION` attempt for the rest of the window produces **no** WARN, **no** `privileged_role_change_blocked` increment, and **no** durable audit row — the page-severity `nexus_rbac_privileged_role_change_blocked_dangerous` alert below cannot fire on a suppressed attempt. Promoting *this* alert to page closes that gap: entering the suppressed state itself now always pages, regardless of what ordering the attacker chose, even though the specific `matchedOn` shape of the suppressed attempts stays unknown until correlated by hand. Triage: pull the actor from the single `RBAC_DENIAL_THROTTLE_ENGAGED` WARN and correlate to the ≤ `max-denials` durable `ROLE_ASSIGNMENT_DENIED` rows that precede it — if any carried `matchedOn="DANGEROUS_PERMISSION"`, they already paged separately; if not, treat this page as the only detection this window will produce for whatever comes next. Expect collateral: the same actor's *benign* role changes are also 403 for the rest of the window (RES-11) — expected, self-clearing, not itself a reason to stand down from the page. |
| **`nexus_rbac_privileged_revoke_lock_hold_slow`** *(new — US-016 D18; name chosen here, the design fixes only the threshold)* | `histogram_quantile(0.99, sum by (le) (rate(nexus_rbac_privileged_revoke_lock_hold_seconds_bucket[10m]))) > 0.25` | ticket | p99 composed X-lock hold above **250 ms over 10 m**, against an expected p99 of **< 50 ms** — 5× headroom. A sustained breach means pool pressure or lock queueing, both of which have their own signals; the lock hold is the thing that turns either into tenant-wide blocking of privileged role changes. ⚠ **Prerequisite, verified absent today:** nothing in `application.yml` and no `MeterFilter` bean configures `management.metrics.distribution.*`, so this timer publishes only `_count`/`_sum`/`_max` and **`…_seconds_bucket` does not exist** — this rule will silently never fire until `management.metrics.distribution.percentiles-histogram.nexus.rbac.privileged_revoke_lock_hold: true` is set. Until then use the interim expression `nexus_rbac_privileged_revoke_lock_hold_seconds_max > 0.25` (a max, not a p99 — coarser and spikier, but real). |
| `nexus_rbac_cross_tenant_attempt` | `increase(nexus_rbac_permission_denied_total{reason="CROSS_TENANT_TARGET"}[15m]) > 0` | ticket | A caller targeted a user/role outside their own tenant on any of the three verbs (AC4 denial). Could be a probe or a broken client. |
| `nexus_rbac_tenant_lockout_blocked` | `increase(nexus_domain_conflict_total{code="RBAC_002"}[15m]) > 0` | ticket | A caller tried to revoke a tenant's **sole active holder of an admin-equivalent role** and was blocked. **Meaning narrowed by US-016 (§6.4), then widened by US-016's own predicate replaced by US-017's (D5, FR-1):** under US-016 the guard was reachable only for self-revocation of the literally-named `TENANT_ADMIN`. **Under US-017 the same self-revocation proof re-derives (`03-design.md` §6.3) over every admin-equivalent role, not only the literal name:** to reach the guard the caller must already have passed the widened privilege gate, so the caller holds an active assignment of a role in the tenant's admin-equivalent set; that row is therefore necessarily in the widened lock (M11)'s holder set, so the distinct-holder guard firing forces `targetUserId == actor.userId()` exactly as before, just over a wider role population. `RBAC_002` therefore now means "**the tenant's sole admin-equivalent holder tried to remove their own last such assignment**" — for a tenant whose only admin-equivalent role is the literal `TENANT_ADMIN`, this is unchanged from the US-016 wording above. **The first runbook question is unchanged:** "is this an offboarding gap for the last admin-equivalent holder?" Remedy is to assign an admin-equivalent role to the incoming administrator *first*, then revoke. A **non-admin** attempting the same revoke still gets **403 before this 409** and shows up on the alerts above instead, never here. **Expression unchanged** — it was already gate-agnostic (`code="RBAC_002"`, not keyed on role name), so US-017's widening required no PromQL edit here. |
| **`nexus_rbac_last_admin_lockout_blocked`** *(new — US-017 D15/RC-19.2)* | `increase(nexus_rbac_last_admin_lockout_blocked_total[10m]) > 2` | **ticket** | Precise companion to the row above: `nexus.rbac.last_admin_lockout_blocked{matchedOn}` increments once per blocked lockout, at the same `LastAdminRoleException` throw site, carrying `matchedOn` ∈ `{ROLE_NAME, DANGEROUS_PERMISSION}`. This alert fires on **repeated** blocks in a short window — a one-off is an offboarding mistake, three in ten minutes is not (per the design's own reasoning, `03-design.md` §9.4). **Deliberately platform-wide, not per-tenant:** the counter carries only `matchedOn` — adding a `tenantId` tag would be unbounded cardinality, which D15's bounded-series discipline forbids — so attribution is by runbook, not by alert: pull `tenantId` from the `RBAC_LAST_ADMIN_REVOCATION_BLOCKED` WARN (§5) for the same time window. Prometheus name: `nexus_rbac_last_admin_lockout_blocked_total`. |
| `nexus_rbac_audit_write_lost` | `increase(nexus_rbac_audit_write_failed_total[5m]) > 0` | **page** | A committed role assignment/revocation has no audit trail. See runbook — this is a data-completeness incident, not a correctness incident. |
| `nexus_rbac_role_change_error_rate` | `rate(http_server_requests_seconds_count{uri=~"/api/v1/users/\\{userId\\}/roles.*",status=~"5.."}[5m]) / rate(http_server_requests_seconds_count{uri=~"/api/v1/users/\\{userId\\}/roles.*"}[5m]) > 0.01` | **page** | Standard >1%-for-5m 5xx bar on the three endpoints. See runbook — first check is a DB-privilege regression. |
| `nexus_rbac_audit_lane_drops` | `increase(nexus_audit_buffer_dropped_total{lane="standard"}[15m]) > 0` | ticket, informational | Should rarely fire now that `ROLE_ASSIGNED`/`ROLE_REVOKED` are in the `priority` lane (T-R4). A firing alert here does not directly implicate role-change events (they're no longer in `standard`), but tracks general STANDARD-lane pressure as a secondary signal. |

Not re-stated here but already alertable via existing, unrelated infrastructure: `nexus_rbac_permission_cache_unavailable` (informational, cache eviction fail-open) and the standard HikariCP pool-exhaustion alert (D14 already removes the "second connection held behind a row lock" hazard by construction — see §6 of `03-design.md`).

## 3. Health indicators

Both are Spring Boot `HealthIndicator` beans, visible on the aggregate `/actuator/health` (neither is added to a liveness/readiness `management.endpoint.health.group.*.include` list — a DB-grant drift or a lockout condition stays UP the overwhelming majority of the time, so neither is treated like Redis's routine-absence exclusion).

### `rbacDbPrivilege` — `RbacDbPrivilegeHealthIndicator`

`nexus-backend/src/main/java/com/example/nexus/rbac/infrastructure/health/RbacDbPrivilegeHealthIndicator.java`

Reports **DOWN** when the live DB connection's privileges on `user_roles` have drifted from the intended least-privilege grant set. Three independent checks, all OR'd:

1. `hasTableDeletePrivilege` / `hasGlobalDeletePrivilege` / `isRoot` — the pre-existing over-grant check (table-scoped or global `DELETE`/`ALL PRIVILEGES`, or connected as `root`).
2. **New in this story (T-015 / threat T-E12):** `hasBareTableUpdatePrivilege` — checks `information_schema.TABLE_PRIVILEGES` for a **bare, table-scoped** `UPDATE` grant on `user_roles`. The intended grant is column-scoped (`UPDATE (revoked_at)`, which only ever appears in `COLUMN_PRIVILEGES`, never `TABLE_PRIVILEGES`). Any row in `TABLE_PRIVILEGES` for `PRIVILEGE_TYPE = 'UPDATE'` means the column scoping has been silently widened — the exact failure mode that would re-permit the multi-column `UPDATE` R-1/D2 was designed to prevent, and which the *original* over-grant check (DELETE/ALL PRIVILEGES only) could not detect.

`Health.down()` details include `dbUser`, `isRoot`, `hasTableDeleteGrant`, `hasGlobalDeleteGrant`, `hasTableScopedUpdateGrant`, and an `issue` string identifying which condition fired. Returns `Health.unknown()` (never DOWN, never UP) if the self-check query itself fails — the check never blocks or crashes the app.

### `rbacZeroActiveAdmins` — `RbacZeroActiveAdminsHealthIndicator`

`nexus-backend/src/main/java/com/example/nexus/rbac/infrastructure/health/RbacZeroActiveAdminsHealthIndicator.java`

**Widened by US-017 (FR-2/D10-D12/D25), re-scoped by `06-code-review.md` H-1 (2026-09-24) — read this row as current, not the original T-015 shape.** Reports **DOWN** when any tenant has **at least one caller-qualifying role** — the literally-named `TENANT_ADMIN`, **or** a custom role carrying **ALL of** `role:write`/`user:write`/`tenant:write` (`RbacDangerousPermissions.NAMES`) — with **zero active holders of any of them**. **H-1 correction:** the indicator originally checked the broader ANY population (a role carrying just one dangerous permission), which let a tenant retain an ANY-only holder while losing its last caller-qualifying holder — the exact lockout this indicator exists to catch — while still reporting UP. Re-scoped to match D2's caller-gate predicate exactly. The indicator now injects `ZeroAdminTenantReader` (a narrow read-only interface, US-017 D25 — not `JpaUserRoleRepository` directly) and runs two tenant-set queries (`findTenantsWithAFullyAdminEquivalentRole` minus `findTenantsWithActiveFullyAdminEquivalentHolders`), differenced in Java, so the detective control now covers the **same population** the widened FR-1 lockout guard protects (**RES-3, closed end to end** — see `docs/features/US-017/03-design.md` §12.3). `Health.down()` details are `status`, `affectedTenantCount`, `issue` — **a count only, never a tenant-id list.**

**Correcting pre-existing drift in this document:** an earlier revision of this row said the DOWN detail included the list of affected `tenantIds`. That was never accurate — US-012's own M-1 (`07-security-review.md`) replaced the id list with a count before this feature ever shipped, specifically because `/actuator/health/**` is `permitAll` and would otherwise leak cross-tenant tenant ids to any authenticated `MEMBER`. The full id list is available only via the WARN log line (§5) — that is the only place an operator can read it from.

This is the only control that catches an admin-equivalent lockout from **any** cause — not just the specific concurrent-revocation race the widened locking guard (M11, `RoleAssignmentService`) already closes, but also a bug, a future grant change, a `roles.name` casing mismatch, or a raw-SQL path around the API entirely. It is a **detection** control, not a prevention control: by the time it reports DOWN, the tenant is already locked out (see runbook §2 for what to do). Returns `Health.unknown()` on a `DataAccessException`, same never-throws discipline as above.

**Protected properties (US-017 RC-22, RES-21/RES-22) — named here as security controls, not incidental configuration:**
- **`management.endpoint.health.cache.time-to-live: 30s`** (`application.yml`) bounds an anonymous cost-amplification path on this indicator — added by `07-security-review.md` M-2 because `/actuator/health/**` is `permitAll` and carries no rate limit, so without it an anonymous caller looping the endpoint forces an unbounded number of cross-tenant scans. US-017's FR-2 widens the query from one table to **two queries over four tables** (including `user_roles`, the largest RBAC table), making the TTL **more** load-bearing than it was at T-015. **Do not remove it or lengthen it without re-running the M-2 amplification analysis.**
- **`rbacZeroActiveAdmins` is excluded from the liveness and readiness probe groups** (`application.yml`'s `management.endpoint.health.group.*.include` lists carry only `livenessState`/`readinessState`; `Dockerfile` probes `/actuator/health/liveness`). This is what keeps a widened DOWN population (US-017 FR-2) a **page**, never a container-eviction outage. Both properties are asserted mechanically by `docs/features/US-017/03-design.md` §11.2's **MC-J**, so a future change cannot silently regress either one.
