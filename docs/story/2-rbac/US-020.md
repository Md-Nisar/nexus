### User Story
As a tenant administrator,
I want an Access Management console where I can see every role in my tenant, build custom roles from the permission catalogue, and grant or revoke roles for my users — with the impact of each change shown before I commit it,
So that I can run least-privilege access control for my organisation without API calls, support tickets or the risk of locking my tenant out of administration.

### Background / Context
EPIC-002 shipped the whole RBAC backend (US-009 – US-018 M2): code-seeded permissions, tenant-scoped roles, role-permission management (US-015), role assignment (US-012), and the grant-subset and self-assignment rules (US-018 A1–A4). The frontend has the guard and directive (US-013), but **no screen calls any RBAC endpoint**. Today a tenant administrator can manage access only with raw HTTP calls.

**Scope (resolved 2026-10-05).** The role-management UI is part of EPIC-002 by product-owner decision (EPIC-002 Open Decision #10). Epic 3 keeps tenant creation, tenant settings, and user provisioning and invites.

**Prerequisites live in US-019.** A gap review of this story's first draft (filed as US-019, then split) moved every missing API, frontend foundation, fixture and decision into **US-019**. Each criterion below names the US-019 items it needs (for example `needs US-019 B3`). This story is UI only.

**Industry baseline.** The design follows the pattern common to AWS IAM, Google Cloud IAM, Microsoft Entra ID, Okta, Auth0, Datadog, GitHub and Grafana:
- Five areas: Roles list, Role detail (Permissions / Members tabs), Permission catalogue, Users, and Access review.
- Assignment can be made from both sides: add a user to a role, or add a role to a user.
- Managed (system) roles are read-only, with "Clone to customise" (Datadog, Stripe).
- Permissions are grouped by resource, with readable labels and "sensitive" badges (AWS access levels, Entra PRIVILEGED, Datadog sensitive).
- Last-administrator lockout is prevented before submit (GitHub, Atlassian).
- A review step shows the diff and its impact ("2 permissions added, affects 14 members"). Vendors only partly do this, so it is a deliberate differentiator.
- Inline text says when a change takes effect (Azure documents its propagation delay).

Anti-patterns we avoid:
- direct user-to-permission grants;
- raw codes with no label;
- system roles that look editable;
- silent saves on high-impact roles;
- lockout errors found only on submit;
- implying changes are instant;
- colour-only cues.

**Backend facts the UI is built against** (verified at `9820d4e`):
- **Roles and permissions:** `GET/POST /api/v1/roles`, `GET /api/v1/permissions` and `GET/POST/DELETE /api/v1/roles/{id}/permissions[/{pid}]`, behind `feature.nexus-us015-rbac-role-management.enabled`.
- **Assignments:** `GET/POST/DELETE /api/v1/users/{userId}/roles[/{roleId}]`, behind `feature.nexus-us012-rbac-role-assignment.enabled`.
- **Lists** are unpaginated `{ data: [...] }`.
- **Errors** are RFC 7807, with `code`, `traceId`, `details[]` and `requiredPermission`. Every authorization rule returns the same `RBAC_001` 403, until US-019 B7.
- **Propagation:** a change reaches an affected user's session within the permission-cache TTL plus the access-token TTL. That is 900 s + 900 s, so about 30 minutes worst case, or immediately when they sign in again (US-019 D4). US-018 A9 will shorten this.

### Acceptance Criteria — story approved by the product owner 2026-10-05; not yet through Gate 1

Every criterion holds this rule: **frontend gating is UX only.** Every action is still enforced server-side by `@RequiresPermission` and the US-012, US-015 and US-018 service rules. Every server rejection is handled gracefully, even when the UI predicted success.

"Administrator" in this story always means `isAdministrator` from the live authorization profile (US-019 B4). It never means "`roles` contains `TENANT_ADMIN`", which misses admin-equivalent custom roles (US-017).

### Technical Notes (ARC)
- **Placement:** `src/app/features/access-management/`, containing `access-management.routes.ts` (lazy routes under the US-019 A2 shell), standalone `OnPush` components, signals, and component-local signal stores. Pages: `roles-list`, `role-detail` (routable tabs), `role-editor` (create/clone), `users-list`, `user-access`, `permission-catalogue`. Data access goes through `RbacApiService`, `UserDirectoryApiService` and `AuthorizationProfileService` in `features/access-management/data/`, typed per US-019 A11 and using `APP_CONFIG.apiBaseUrl` and `ViewState<T>`.
- **Route table** (all are children of the shell; `authGuard` sits on the shell, `permissionGuard` on each child, per US-019 A1):

  | Path | `data.permission` |
  |---|---|
  | `/admin/access/roles` | `role:read` |
  | `/admin/access/roles/new` | `role:write` |
  | `/admin/access/roles/:roleId` | `role:read` |
  | `/admin/access/users` | `user:read` |
  | `/admin/access/users/:userId` | `user:read` |
  | `/admin/access/permissions` | `role:read` |

  Tabs that need `audit:read` (Members, Effective permissions) are hidden from users without it, not routed.
- **Affordance inputs:** the US-019 B4 live profile (`roles`, `permissions`, `isAdministrator`) is loaded once when the console opens, re-read after G6 events, and never cached across sessions. `AuthStore` stays the source for nav visibility, because it is populated at sign-in.
- **Diff engine:** a pure `diffPermissions(current, staged) → { added, removed }` function with unit tests. The sequential fallback applies attaches before detaches, so a mid-way failure never leaves the role with less access than both the starting and target states.
- **No backend changes in this story.** Every API it needs is listed in US-019 Group B or US-018 M9.
- **Gates:** `npm run test:ci`, `npm run lint && npm run format:check`, and Playwright + axe under `e2e/access-management/` using the US-019 C2 persona fixtures.
- **Feature flag:** none on the frontend. Visibility follows permissions, and F6 covers disabled backends. Gate 1 may add an `AppConfig` toggle for a staged rollout.

|------|-----------|--------|-----------|
| Too large for one delivery unit (7 groups, ~45 criteria) | High | Med | Gate 1 splits it, e.g. (1) A1–A6 + G2/G7, (2) B1–B7 + G3–G5, (3) C1–C6 + G6, (4) F + remaining G, (5) Group D, (6) Group E. This file stays the traceability anchor |
| US-019 P0 items slip | Med | High | Groups A and F can start on US-019 A1–A5 alone, using recorded fixtures; Groups B and C wait for B1/B3/B4/B5 |
| Admins treat UI affordances as the security boundary, or a stale profile mispredicts | Med | Med | Server stays authoritative; every predicted-allow path handles 403/409 inline (Test Scenario 12); developer guide restates "UX only" |
| Non-atomic saves (until US-019 B8) leave a half-applied role | Med | Med | Attach-before-detach order, partial-failure summary, re-fetch, G3 convergence |
| Generic 403 text frustrates admins (until US-019 B7) | Med | Low | Most 403s are prevented up front (B6, C3, C4); trace reference shown |
| Members tab exposes the admin roster (US-018 RES-37) | Low | Med | Same `audit:read` gate as the API; US-019 D5 sign-off |

### Out of Scope
- Backend endpoints of any kind (US-019, US-018)
- User invitation, provisioning, deactivation, profile editing (Epic 3)
- Direct user-to-permission grants (an anti-pattern, not supported by the model)
- Time-bound or eligible (PIM-style) assignments (pending the US-018 C4 decision)
- Access-review campaigns with reviewer workflow and recertification
- Least-privilege recommendations
- A per-role audit History tab (needs an audit-read API; Epic 7)
- Bulk assignment across many users; CSV import
- Role hierarchy or inheritance, ABAC, resource-scoped assignments (EPIC-002 scope boundary)
- Platform / super-admin console
- i18n (copy is centralised through US-019 D3)
