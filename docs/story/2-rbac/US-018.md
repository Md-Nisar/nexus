### US-018 — Harden RBAC for production readiness (principal-architect review remediation)

| TYPE | PRIORITY | STORY POINTS | EPIC LINK | SPRINT | ASSIGNEE |
|------|----------|--------------|-----------|--------|----------|
| Feature | P0 for Group A (Epic 3 / GA blockers); P1 for Groups B–D | _(unestimated — pending Gate 1; expected to exceed a single sprint, see Risks)_ | EPIC-002: RBAC Foundation | _(unscheduled — Group A must land before Epic 3 kickoff)_ | _(Tech lead assigns)_ |

### User Story
As a platform security owner,
I want the RBAC module's authorization model, audit trail, revocation latency, operability and API completeness brought to production grade,
So that Nexus can onboard enterprise tenants with no open privilege-escalation paths, a complete and provable audit trail, near-immediate access revocation, and a supported way to recover a tenant's administration.

### Background / Context
A principal-architect review of EPIC-002 (US-009 – US-017) on 2026-09-26 rated the RBAC module **6.5 / 10 for production readiness**. Engineering rigor is high: tenant isolation is correct by construction, the schema is strong, and `mvnw verify -DskipITs` is green (1,099 tests, 0 failures, 1 skipped). The gaps are in the authorization model, audit, operability and API completeness, not in test discipline.

This story collects every gap from that review in one place, so it can be analysed at a single Gate 1 and split into implementation-sized stories there (see Risks). Findings are grouped by severity; IDs (G1–G5, M1–M8, F1–F6, D1–D5) match the review.

**Headline finding (G1).** The epic never adopted the standard anti-escalation rule used by Kubernetes RBAC and AWS IAM permission boundaries: *a caller may only grant or attach permissions they already hold*. Instead, US-015 → US-017 grew three layers of predicates (named `TENANT_ADMIN` / ANY dangerous permission / ALL three dangerous permissions), tenant-wide lock sets, canaries and detective signals. `RoleAssignmentService` is now 1,130 lines, and two escalation residuals are still open by the project's own accounting: **US-016 RES-1(b) / T-E27 (High)** and **US-017 RES-13**. The root cause is that `user:write` means both "edit users" and "manage role assignments", which is why `user:write` itself counts as "dangerous".

### Acceptance Criteria

#### Group A — Critical / High (Epic 3 and GA blockers)

| # | Criterion | Definition of Done | Priority | Notes |
|---|-----------|--------------------|----------|-------|
| A1 | **Role assignment is its own permission (G1)** | A new code-seeded permission (proposed `user:role:assign`) gates `POST`/`DELETE /api/v1/users/{userId}/roles`; `user:write` no longer confers role-assignment ability; `TENANT_ADMIN` is granted the new permission by migration | P0 | Removes the reason `user:write` is in `RbacDangerousPermissions`, and with it ADR-0018 D2's "vacuity" proof |
| A2 | **Grant-subset (no-escalation) rule on assign (G1)** | `assign()` denies with 403 + `RBAC_001` unless every permission on the target role is held by the caller, checked against a **live DB read** of the caller's active roles (never the JWT) | P0 | Replaces the hardcoded 3-permission "dangerous" list with a rule that covers every future permission automatically |
| A3 | **Grant-subset rule on attach (G1)** | `attachPermission()` denies with 403 unless the caller holds the permission being attached (live DB read) | P0 | Closes US-017 RES-13 (mint side is name-based today) |
| A4 | **No self-assignment for non-admins (G1)** | A caller cannot assign a role to themselves unless they hold a fully admin-equivalent role; attempt returns 403 and writes a `ROLE_ASSIGNMENT_DENIED` audit row | P0 | Closes the pre-positioning path behind US-016 RES-1(b) / T-E27 (self-assign a benign role, wait for an admin to make it dangerous) |
| A5 | **Retire superseded machinery (G1)** | An ADR records which ANY/ALL predicates, canaries and lock-set logic from US-016/US-017 become redundant under A1–A4, and removes them; the last-admin lockout guard (AC5) is kept; `RoleAssignmentService` shrinks materially | P1 | Follow-on to A1–A4, same ADR. Must not weaken any existing IT without explicit threat-model sign-off |
| A6 | **Audit writes are atomic with the change (G2)** | `ROLE_ASSIGNED`, `ROLE_REVOKED`, `ROLE_CREATED`, `ROLE_PERMISSION_GRANTED`, `ROLE_PERMISSION_REVOKED` are written in the **same transaction** as the mutation (or via a transactional outbox); an audit write failure rolls back the change; denial events keep their current `REQUIRES_NEW` path | P0 | Today they run in `afterCommit` through a best-effort, never-throw port, which contradicts Epic goal #3 (100% of events audited). `auth_events` is in the same database, so this is cheap |
| A7 | **First-admin bootstrap and break-glass (G3)** | An audited, supported mechanism (e.g. an admin CLI or one-time bootstrap token) can create a tenant's first `TENANT_ADMIN` and recover a tenant with zero admins; every use writes an audit event and fires an alert; no manual production SQL is required | P0 | Today recovery is a manual `INSERT` (`docs/features/US-012/runbook.md` step 4) |
| A8 | **Deny-by-default enforcement (G4)** | ArchUnit rule: every `@RestController` handler carries `@RequiresPermission` or a new `@PublicEndpoint`; the identity endpoints are annotated `@PublicEndpoint` as needed; a same-class self-invocation check flags direct calls to `@RequiresPermission` methods | P0 | This is EPIC-002 Open Decision #4 (still OPEN), an Epic 3 entry criterion |
| A9 | **Near-immediate revocation (G5)** | A per-user (or per-tenant) permissions epoch, stored in Redis, is embedded in the access token and checked by `JwtAuthenticationFilter` on every request (one O(1) lookup); revoke, attach and detach bump the epoch; a stale token gets 401 and the client refreshes; a revoked permission stops working within seconds, not 15–30 min | P0 | Define fail-open vs fail-closed behaviour for a Redis outage at Gate 1 |
| A10 | **Role-permission edits reach holders' cached permissions (G5)** | `attachPermission`/`detachPermission` clear the permission cache for every active holder of the role (or rely on A9's epoch bump) | P0 | Today a detached permission can live for up to 15 min in the cache plus 15 min in the token |
| A11 | **Token claims fully validated (G5)** | `JwtRs256Service.verify` rejects tokens whose `schema_version` ≠ `JwtClaims.CURRENT_VERSION` and tokens missing `tenant_id` (401, not an NPE/500 from `Map.of` in the filter) | P1 | |

### Technical Notes (ARC)
- **New ADR required** for A1–A5 (it supersedes parts of ADR-0017 and ADR-0018) and a second one for A9 (token freshness), following the US-015/US-016 precedent that changing a shipped authorization contract needs an ADR.
- A2/A3 read the caller's permissions from the DB inside the write transaction, never from the JWT (same principle as ADR-0017 T-E7).
- A6: evaluate same-transaction insert into `auth_events` vs a transactional outbox; ADR 0009's `REQUIRES_NEW` rule still applies to denial events that must survive rollback.
- A9 changes the frozen `JwtClaims` contract (new epoch claim) → bump `JwtClaims.CURRENT_VERSION` and update the contract test (per US-010 AC7 precedent).
- B2 and any new permission (A1) are new append-only migrations with matching updates to all three `nexus_app` provisioning artifacts (ADR-0014 D6).
- Feature flag: Gate 1 to decide per group; A8 and B3 need none.
