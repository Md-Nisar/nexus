### US-015 — Enable role and role-permission management API

|------|----------|--------------|-----------|--------|----------|

### User Story
As a platform development team,
I want an API to create tenant-scoped roles and manage the permissions attached to them,
So that Epic 3 (and any future admin UI) has a ready-made, tenant-isolated API to let a Tenant Admin build custom roles beyond the two seeded system roles.

### Background / Context
US-009 seeds exactly two roles per tenant (`TENANT_ADMIN`, `MEMBER`) via migration, with no way to create or modify roles afterward. This story completes the RBAC data model's CRUD lifecycle within the `rbac` bounded context established by US-009–US-012, rather than leaving it for a not-yet-scoped Epic 3 to build against RBAC's own tables. It is explicitly **non-gating**: the Epic 3 kickoff gate remains US-009 (seed) + US-012 (assignment) only, per the EPIC-002 Synthesis section. System roles (`is_system_role = TRUE`) must be immutable through this API — `TENANT_ADMIN` and `MEMBER` can never be edited or have their permissions changed or removed via these endpoints, only via a future migration.

**Forward-tracked from US-012's own code (`RoleAssignmentService` Javadoc, M-3 note) and confirmed at this story's Gate 1** (`docs/features/US-015/01-requirements.md` §7 OQ1/§11): AC8 in US-012 (only an active `TENANT_ADMIN` may grant the `TENANT_ADMIN` role) matches on the role **name**, not on the privileges a role confers. This story is the first one that lets a caller attach *any* permission — including `role:write`, `user:write`, or `tenant:write` — to a role, which combined with US-012's already-live assignment endpoint would let a differently-named role carry admin-equivalent power with none of AC8's protections. AC11 below closes this by reusing US-012's own `hasActiveAdminAssignment` check. Separately, the epic's compliance requirement ("role assignment/revocation events must be immutable and auditable") had no equivalent coverage for role/role-permission changes in this story's original scope — AC12 closes that gap by reusing the existing `RbacAuditPort`/audit pipeline (US-012/US-014).

### Technical Notes (ARC)
- New `RoleManagementService` in the existing `com.example.nexus.rbac` bounded context, alongside `RoleAssignmentService` (US-012) — same package, same tenant-scoping style (explicit `tenantId` parameter, not a Hibernate filter)
- System-role protection: check `is_system_role` before any mutating operation on a role or its `role_permissions`; throw a dedicated `SystemRoleImmutableException` mapped to `409 + RBAC_003` in `GlobalExceptionHandler`
- **Cache fan-out (new relative to US-012):** revoking/assigning a *user's* role invalidates one `permissions:{tenant_id}:{user_id}` key (US-012). Editing a *role's* permissions here affects every user currently holding that role. Options: (a) query all active `user_roles` for the `role_id` and bulk-delete their cache keys on every `role_permissions` write, or (b) accept the existing 15-min TTL / 7-day refresh lag as sufficient and document it identically to US-012's revocation lag. Pick (a) if role-permission edits are expected to be rare-but-security-sensitive; (b) is simpler and consistent with the epic's already-accepted cache lag elsewhere — default to (b) unless ADR-0013 says otherwise.
- Endpoints all protected by `@RequiresPermission` (US-011); no new enforcement mechanism needed
- Feature flag required: No new *business-facing* flag — but per the established per-story kill-switch convention (every prior `rbac` controller ships behind one, e.g. US-012's `feature.nexus-us012-rbac-role-assignment.enabled`), this story's controller(s) must be gated behind `feature.nexus-us015-rbac-role-management.enabled`, defaulted `false` in `application.yml` and enabled per-env in `application-{profile}.yml`, consistent with US-012
- **AC11 (dangerous-permission gating):** `RoleManagementService`'s permission-attach path checks the target permission's name against a small fixed set (`role:write`, `user:write`, `tenant:write`) before insert; if present, calls `UserRoleAssignmentPort#hasActiveAdminAssignment(actor.userId(), tenantAdminRoleId, actor.tenantId())` — the same fresh, locking DB read US-012 AC8 uses, not a JWT-claim check (JWT `permissions[]`/`roles[]` can be up to ~15 min stale). Denial reuses `InsufficientPermissionException` with a new `DenialReason` (e.g. `NOT_TENANT_ADMIN`, already defined for US-012 AC8 — reuse, don't duplicate).
- **AC12 (audit):** extend `RbacAuditPort` (or add a sibling port method set) with `recordRoleCreated`, `recordRolePermissionGranted`, `recordRolePermissionRevoked`, following the exact same post-commit, best-effort pattern `RoleAssignmentService.registerPostCommitSideEffects` already uses for `ROLE_ASSIGNED`/`ROLE_REVOKED` — never transactional with the primary write, never blocking/throwing on failure. New `AuthEventType` constants required (mirrors US-012/US-014's `ROLE_ASSIGNED`/`ROLE_REVOKED` addition).

### Dependencies
- Blocked by: US-009 (schema), US-011 (permission enforcement pattern), US-012 (`hasActiveAdminAssignment` reused by AC11; `RoleAssignmentService`'s tenant-scoping/post-commit-side-effect patterns), US-014 (audit pipeline reused by AC12)

- External: Redis (if cache fan-out option (a) is chosen)

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| Cache fan-out on role-permission edits leaves stale permissions for many users at once | Med | Med | Default to documenting the existing TTL/refresh lag (option (b) above) unless a stricter SLA is required |
| System-role immutability check missed on one of the 3 write endpoints | Low | High | Single shared guard in `RoleManagementService`, not per-controller; covered by AC7's security test suite |
| ~~Custom role carrying `role:write`/`user:write`/`tenant:write` lets a `TENANT_ADMIN` devolve admin-equivalent power to a differently-named role, escaping AC8's (US-012) lockout/admin-grant protections~~ | ~~Med~~ | ~~Critical~~ | **RESOLVED (Gate 1, AC11):** attaching any of the three dangerous permissions requires the caller to hold an active `TENANT_ADMIN` assignment, reusing US-012's own `hasActiveAdminAssignment` check; covered by AC11's security test suite (Test Scenarios 9-10) |
| Role/role-permission changes had no audit trail, despite being as security-consequential as a user-role assignment once AC11's gap is considered | Low (post-AC11) | Med | **RESOLVED (Gate 1, AC12):** `ROLE_CREATED`/`ROLE_PERMISSION_GRANTED`/`ROLE_PERMISSION_REVOKED` events reuse the existing `RbacAuditPort` pipeline; covered by AC12's test suite (Test Scenarios 11-14) |

### Out of Scope
- Role deletion (only creation/read + permission attach/detach in this story)
- Bulk permission assignment
- Role templates / cloning
- The Epic 3 Tenant Admin UI itself
