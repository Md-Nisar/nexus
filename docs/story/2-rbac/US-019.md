### User Story
As a tenant administrator,
I want an Access Management console where I can see every role in my tenant, build custom roles from the permission catalogue, and grant or revoke roles for my users — with the impact of each change shown before I commit it,
So that I can run least-privilege access control for my organisation without API calls, support tickets or the risk of locking my tenant out of administration.

### Background / Context
EPIC-002 shipped the whole RBAC backend (US-009 – US-018 M2): code-seeded permissions, tenant-scoped roles, role-permission management (US-015), role assignment (US-012), and the grant-subset / self-assignment rules (US-018 A1–A4). The frontend has the guard and directive (US-013) but **no screen that calls any RBAC endpoint**. Today a tenant administrator can only manage access with raw HTTP calls, so the RBAC model is unusable by the people it was built for.

**Scope change, to confirm at Gate 1.** EPIC-002's scope boundary (`EPIC-002.md` [PM] and [UX]) puts "UI for role management" in Epic 3 (Tenant Management). This story moves it into EPIC-002 for the same reason Open Decision #2 moved the role API (US-015) here: it is a pure `rbac`-context consumer, every API it needs is in this epic, and Epic 3 is not yet scoped. Epic 3 keeps tenant creation, tenant settings and user provisioning/invites. **PM must confirm this boundary change at Gate 1.** If it is rejected, this story moves to Epic 3 unchanged.

**Industry baseline.** The design follows the pattern common to AWS IAM, Google Cloud IAM, Microsoft Entra ID, Okta, Auth0, Datadog, GitHub and Grafana:
- Five areas: Roles list, Role detail (Permissions / Members tabs), Permission catalogue, Users, and Access review.
- Assignment can be made from both sides: add a user to a role, or add a role to a user.
- Managed (system) roles are read-only and carry a "Clone to customise" action (Datadog, Stripe).
- Permissions are grouped by resource, with readable labels and "sensitive / privileged" badges (AWS access levels, Entra PRIVILEGED, Datadog sensitive).
- Lockout-prevention rules for the last administrator (GitHub, Atlassian).
- A review step that shows the diff and its impact ("2 permissions added, affects 14 members"). Vendors only partly do this, so it is a deliberate differentiator here.
- An inline note on when a change takes effect (Azure documents its propagation delay).

The anti-patterns we avoid:
- Direct user-to-permission grants (Auth0 calls these an RBAC anti-pattern).
- Raw permission codes with no label.
- System roles that look editable.
- Silent saves on high-impact roles.
- Lockout errors found only on submit.
- Implying changes are instant.
- Colour-only cues.

**Current backend facts the UI is built against** (verified against code at `9820d4e`):
- `GET/POST /api/v1/roles`, `GET /api/v1/permissions`, `GET/POST/DELETE /api/v1/roles/{id}/permissions[/{pid}]` are live behind `feature.nexus-us015-rbac-role-management.enabled`.
- `GET/POST/DELETE /api/v1/users/{userId}/roles[/{roleId}]` are live behind `feature.nexus-us012-rbac-role-assignment.enabled`.
- Both flags default to `false`, and prod does not override them.
- Lists are unpaginated `{ data: [...] }`.
- Errors are RFC 7807 with `code`, `traceId`, `details[]` and `requiredPermission`. The 403 body does **not** say *which* rule denied the request (cross-tenant, grant-subset, self-assignment, not-admin or throttle all return `RBAC_001`).
- **There is no endpoint to list or look up users in a tenant.** US-018 C3's planned holder endpoints return user IDs only and expect "the client to join IDs to names through identity endpoints", which do not exist. Group C below closes that gap with a minimal backend slice.
- Role rename/delete (US-018 C1), pagination (C2) and access-review endpoints (C3) are designed (`docs/features/US-018/03-design.md` §11) but not built (US-018 M9).
- Effective permissions reach a user only when their token is refreshed: up to the 15-minute permission-cache TTL plus the access-token lifetime. US-018 A9/A10 (near-immediate revocation) are not built.

### Acceptance Criteria — DRAFT, not yet through Gate 1

Every criterion holds this rule: **frontend gating is UX only**. Every action is still enforced by `@RequiresPermission` and the US-012/US-015/US-018 service rules, and every server rejection is handled gracefully even when the UI predicted success.

### Technical Notes (ARC)
- **Frontend placement:** `src/app/features/access-management/` with `access-management.routes.ts` (lazy, standalone components, signals, `OnPush`). Pages: `roles-list`, `role-detail` (tabs), `role-editor` (create/clone), `users-list`, `user-access`, `permission-catalogue`. Data access: `RbacApiService` and `UserDirectoryApiService` in `features/access-management/data/`, using `APP_CONFIG.apiBaseUrl` and `ViewState<T>` (`shared/types/view-state.ts`). Use component-local signal stores, with no global state for console data.
- **Route table** (all `canActivate: [authGuard, permissionGuard]`):

  | Path | `data.permission` |
  |---|---|
  | `/admin/access/roles` | `role:read` |
  | `/admin/access/roles/new` | `role:write` |
  | `/admin/access/roles/:roleId` | `role:read` |
  | `/admin/access/users` | `user:read` |
  | `/admin/access/users/:userId` | `user:read` |
  | `/admin/access/permissions` | `role:read` |

  Tabs needing `audit:read` (Members, Effective permissions) are hidden, not routed.
- **Permission parsing / labels:** `resource = name.split(':')[0]`, `action = rest`. Readable labels come from a frontend `PERMISSION_LABELS` map keyed by the typed `Permission` union (F5), falling back to the backend `description`. A unit test asserts every catalogue entry has a label, so a new backend permission without a label fails CI rather than showing a raw code.
- **Admin / grant-subset hints:** derived from `AuthStore.roles()` and `AuthStore.permissions()`. Both can be stale for the token lifetime, so they only shape affordances. All decisions stay server-side (US-012/US-015/US-018 A2–A4).
- **Diff engine (B3/B4):** a pure function `diffPermissions(current, staged) → { added, removed }` with unit tests. Apply order: attaches first, then detaches (so a failure mid-way never leaves the role with less access than both start and end states). Concurrent edits are last-write-wins (no ETag, per US-018 design §11.1). A 409 `RBAC_005` or 404 `ROLE_PERMISSION_NOT_FOUND` during apply means someone else already made that change: treat it as converged, not failed.
- **Backend (C1 only):** `identity` context, hexagonal layout. A new `UserDirectoryController` + `ListTenantUsersUseCase`. The response DTO never exposes `tenant_id`, `email_hmac`, the password hash or lockout counters. Email is decrypted through the existing `EmailCipher` converter. Pagination uses the `api-design` standard (`PageMetadata`/`PageLinks` as planned in US-018 C2, shared). `@RequiresPermission("user:read")`, plus an ArchUnit-compliant annotation (US-018 A8). No migration is needed (`idx_users_tenant_id_status` covers `tenant_id + status` paging). Integration tests: two-tenant isolation, exact-email lookup hit/miss returning the identical 200 empty page (no enumeration difference beyond the tenant-scoped `user:read` boundary), paging bounds.
- **Optional additive backend fields (Gate 1):** `PermissionResponse.isSensitive` (A4) and `RoleResponse.memberCount` (D2). Both are additive and non-breaking. If rejected, use the fallbacks noted in A4/D2.
- **403 opt-out:** if US-018 C6 hasn't landed, this story adds the `HttpContextToken` itself (as designed in US-018 §11.5) so the two don't collide.
- **Feature flags:**
  - Backend: `feature.nexus-us019-user-directory.enabled` (default `false`, enabled in `dev`/`test`).
  - Frontend: the nav entry renders only when the user holds a relevant permission; F6 covers disabled backends.
  - No separate frontend flag is proposed (Gate 1 may add one to `AppConfig` if staged rollout is wanted).
- **Gates:**
  - Frontend: `npm run test:ci`, `npm run lint && npm run format:check`, and Playwright + axe e2e under `e2e/access-management/`.
  - Backend: `./mvnw verify` (C1 adds an `*IT`).
- **ADR:** none expected for the frontend. The C1 directory endpoint should be recorded as an addendum to ADR-0006 (email display/lookup surface), and confirmed at Gate 2 by a threat-model pass (user enumeration, PII exposure).

### Dependencies
- **Blocked by:** none for Groups A, B, C, F (all APIs used are merged, plus C1 built here). US-013 (guard/directive), US-015, US-012 and US-018 M2 are merged.
- **Group D blocked by:** US-018 M9 (C1 role PATCH/DELETE, C2 pagination, C3 holders).
- **Group E blocked by:** US-018 M9 (C3 access-review endpoints).
- **Coordinates with:** US-018 C6 (403 redirect + opt-out token), US-018 B5 (typed permission catalogue), US-018 A9 (shortens F3 copy).
- **Blocks:** Epic 3 Tenant Management UI (reuses the console shell, user directory and wrappers).
- **External:** none.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| Too large for one delivery unit (6 groups, ~40 criteria) | High | Med | Gate 1 splits it, e.g. (1) F2 wrappers + A1–A6, (2) B1–B7, (3) C1 backend directory, (4) C2–C7, (5) Group D, (6) Group E. This file stays the traceability anchor (US-018 precedent) |
| Scope boundary conflict with EPIC-002/Epic 3 ("UI for role management is Epic 3") | Med | Med | Explicit PM decision at Gate 1 (see Background). The story is portable to Epic 3 unchanged |
| Admins read UI affordances as the security boundary, or the frontend predicts wrongly from a stale token | Med | Med | Server remains authoritative; every predicted-allow path handles 403/409 inline (Test Scenario 10); developer guide restates "frontend gating is UX only" |
| Non-atomic multi-call saves (create + attaches, multi-assign) leave a half-applied role | Med | Med | Attach-before-detach ordering, partial-failure summary, refetch (B4). Bulk/atomic `PUT /roles/{id}/permissions` filed as a follow-up |
| User directory (C1) becomes a PII/enumeration surface | Med | High | `user:read`-gated, tenant-scoped, exact-match only, no email in logs, paged with `size` ≤ 100; Gate-2 threat model + ADR-0006 addendum |
| The holders/member data the UI shows exposes the tenant's administrator roster (US-018 RES-37) | Low | Med | Members tab requires `audit:read` (same gate as the API); no extra exposure beyond the API |
| Frontend sensitive-permission list drifts from the backend | Med | Med | Prefer backend-sourced `isSensitive` (A4 option a); otherwise a contract test |
| Generic 403 messages frustrate admins because `RBAC_001` carries no reason | Med | Low | Prevent most 403s up front (B6, C4, C5); show trace reference; Gate 1 may propose an additive, non-sensitive `reason` field (security review needed: it can disclose rule internals) |

### Out of Scope
- User invitation, provisioning, deactivation and profile editing (Epic 3)
- Direct user-to-permission grants (anti-pattern; not supported by the RBAC model)
- Time-bound / eligible (PIM-style) assignments (US-018 C4 decision pending)
- Access-review campaigns with reviewer workflow and recertification
- Least-privilege recommendations (unused-permission insights)
- Per-role audit History tab (needs an audit-read API; Epic 7 Audit Log UI)
- Bulk assignment across many users, CSV import
- Role hierarchy / inheritance, ABAC, resource-scoped assignments (EPIC-002 scope boundary)
- Platform / super-admin console
- i18n (no localisation framework exists yet; strings are centralised to ease a later move)
